1. EXISTING IMPLEMENTATION [VERIFIED at HEAD]
---------------------------------------------
- One document element <svg> (card "SVG"), with two content modes:
  - starter primitive (1.15.5): svgKind rectangle|circle|triangle|star,
    svgViewBox (default 0 0 100 100), svgFill (default #3b82f6),
    svgStroke (unset = none), svgStrokeWidth (default 1);
  - vector scene (1.15.6): svgScene = { objects[] }. It is SVG-local and
    deliberately not EditorElementNodes (no layout, Structure tree or
    HTML selection). An empty scene renders the starter.
    materializeSvgStarterIntoScene converts the starter into a scene.
- Objects:
  - rect{x,y,width,height}, ellipse{cx,cy,rx,ry}, line{x1,y1,x2,y2},
    polygon{points[]}, path{commands: M|L|Z, absolute};
  - each with an editor-local id plus optional fill, stroke,
    strokeWidth;
  - array order = paint order.
- Rendering (SvgVectorObjectRenderer):
  - fill = object.fill ?? "none";
  - stroke and stroke-width only when stroke is set;
  - a line always gets stroke = object.stroke ?? DEFAULT_SVG_FILL;
  - `d` from pathCommandsToD.
  Export (buildExportDocument.svgContent) mirrors this exactly; paint
  must pass isExportableColor or "none", otherwise it is dropped with an
  "invalid-svg-paint" warning.
- Finding F-SVG-1 (documentation only): the svgScene.ts fill comment
  names a resolveVectorObjectFill that does not exist, and claims that an
  unset fill resolves to the SVG's default. In reality both Canvas and
  Export use "none". There is no parity defect; the comment is stale.
  Recorded, not fixed (restricted checkpoint).
- Edit mode (UI state, not document data): svgEditingNodeId,
  selectedSvgObjectIds, primarySvgObjectId, activeSvgTool (select | rect |
  ellipse | line | polygon | pen), svgDraft.
  - Polygon/pen drafts live outside history (Enter commits, Escape
    discards).
  - Shape drawing = one transaction.
  - Move: useSvgObjectMoveSession.
  - Resize: rect/ellipse only.
  - Line endpoints have setters.
  - There is no vertex editing.
- Coordinates (resolveSvgPointerPosition): getScreenCTM().inverse(),
  correct under CSS transforms and scroll, rounded to 0.01.
  - Fallback (no CTM, jsdom): a linear map over the whole client rect,
    which ignores the preserveAspectRatio letterbox. Finding F-SVG-2,
    low risk; corrected in BC-17.18.
- Schema: z.strictObject discriminated union, finite numbers. There is no
  per-list size bound (only the global projectLimits). Integrity requires
  unique object ids. Clone regenerates object ids.
- Finding F-SVG-3 (lifecycle), confirmed again in useSvgObjectMoveSession:
  - pointercancel → endSession → COMMITS a moved gesture;
  - Escape restores the WHOLE document and selection from the
    transaction snapshot;
  - the SVG sessions are not registered with the editor's
    active-interaction registry.
  This differs from the BC-13.5/13.5.1 contract (exact, node-scoped
  rollback on Escape, pointercancel, lost capture, blur, unmount and
  Preview; commands cancel first) and from BC-13 D21 ("pointercancel
  must change from commit to restore"). It is UNSAFE: an OS-interrupted
  gesture commits a partial move, and an Escape restores unrelated
  document changes made since the gesture started (possible only through
  commands that do not cancel the gesture). The vector architecture
  replaces it (§6); it is not preserved.
- Paint data: the schema accepts any string for fill/stroke. The Canvas
  renders it as an attribute (no script execution through React
  attributes), and Export filters it. Finding F-SVG-4: validate at the
  schema and command layer too (BC-17.18).
- (NEW 17.1.3) Modifiers [VERIFIED]: useSvgObjectMoveSession uses
  Ctrl/Cmd at pointerdown to toggle and Shift to add, like the Canvas
  (CanvasInteractionBoundary); Free sessions read Alt (snap bypass) and
  Shift (axis lock) per frame.
- (NEW 17.1.3) Finding F-SVG-5 (architecture, not code): the BC-17.1.2
  plan put base transforms in the SVG transform attribute and state
  transforms in CSS; CSS `transform` replaces that attribute instead of
  composing with it. Corrected in §7.5.3.


2. OBJECT MODEL [ENG]
---------------------
Schema timing (CORRECTED 17.1.3, consistent with Report 1 §12.5): the
identity contract of §2.4 and §7.1 (persistent object ids; no stored
anchor, control-point or definition ids; no stored references except
keyframes) is LOCKED at (4,0) in BC-17.2 — it is already true at HEAD.
The new object fields below arrive with the BC-17.18 revision step,
together with the legacy paint mapping.
2.1 Objects keep their current types. Shared optional fields are added:
    paint: {
      fill?: Paint;  stroke?: Paint;
      fillOpacity?: 0..1;  strokeOpacity?: 0..1;  opacity?: 0..1;
      strokeWidth?: number ≥ 0;
      strokeDasharray?: number[] (≤ 32, each ≥ 0);
      strokeDashoffset?: number;
      strokeLinecap?: butt|round|square;
      strokeLinejoin?: miter|round|bevel;
      strokeMiterlimit?: ≥ 1;
      fillRule?: nonzero|evenodd;
      paintOrder?: normal|stroke
    }
    Paint = { kind: "none" } | { kind: "color", color }
          | { kind: "gradient", gradient: SvgGradient }
    transform?: SvgObjectTransform        // §4
    clip?: SvgClip                        // §7
    mask?: SvgMask                        // §7
    filter?: SvgFilterList                // §7.4
    objectRules?: SvgObjectRule[]         // states/motion (§7.5)
    The legacy fill/stroke/strokeWidth strings stay readable: the
    revision step maps them into paint (an identity transformation: a
    colour string → {kind:"color"}; absent → absent).
2.2 Gradients (value semantics):
    SvgGradient = {
      kind: linear|radial;
      units: objectBoundingBox|userSpaceOnUse;
      x1,y1,x2,y2 | cx,cy,r,fx,fy;
      stops: [{ offset 0..1, color, opacity 0..1 }] (2–32);
      spread: pad|reflect|repeat;
      rotateDeg?
    }
    Conic gradients do not exist in SVG paint → not applicable to vector
    objects (the HTML box can still use CSS conic gradients).
2.3 Paths: typed, absolute, normalized command set
      M x y | L x y | C x1 y1 x2 y2 x y | Q x1 y1 x y
      | A rx ry rotationDeg largeArc sweep x y | Z
    plus anchors?: AnchorMeta[] aligned with the drawing commands:
    { pointType: corner|smooth|symmetric }.
    - Existing M/L/Z data is unchanged (the union only grows).
    - H/V are stored as L (they only exist as printer optimizations).
    - S/T are stored as explicit C/Q plus pointType (robust editing: no
      hidden dependence on the previous segment).
    - Relative forms are never stored: there is no raw path import, so
      every path is editor-authored.
    - Arcs are stored as A (exact), never approximated.
    - Multiple subpaths: every M after the first starts a subpath.
2.4 Identity model (CORRECTED 17.1.3 — the single authoritative model;
    resolves SVG-Q3/ARCH-Q3. BC-17.1.2 Report 1 §12.5 said "anchors with

    Why anchors need no stored ids [ENG]: every operation that changes
    command indices is an editor command that knows exactly how it
    changed them, so it returns an INDEX REMAP and applies it to the
    vector selection in the same transaction:
    - insert anchor / split segment at k: indices ≥ k+1 shift by +1; the
      new anchor is k+1 and becomes the selection;
    - delete anchors: removed refs drop out of the selection; later
      indices shift down; a subpath that loses all anchors is removed;
    - open/close a subpath: a Z is removed/added; refs after it shift;
    - reverse direction: index i → (subpath end − i + subpath start);
      point types and handles swap c1/c2;
    - primitive → path: the object id is kept; the selection becomes the
      object (no anchors selected);
    - Undo/Redo: the vector selection is part of the history snapshot, so
      it is restored together with the commands it refers to;
    - copy/paste: new object ids; anchors are not copied as selection.
    A selection ref that no longer resolves (impossible after a correct
    remap; defended anyway) is dropped, never retargeted. Persistent
    anchor ids would add file size, a migration for every existing path
    and id-consistency integrity rules, and would buy nothing: no data
    outside the object ever refers to an anchor.
    A closing endpoint that coincides with its subpath's M is presented
    as ONE anchor: moving it moves both. The data is not rewritten.2.5 Primitive geometry stays parametric until the user converts it
    (N3.3).
2.6 Whole-SVG content clip/mask: svgScene.contentClip?: SvgClip and
    contentMask?: SvgMask, applied to a generated <g> wrapping all
    objects (in viewBox space).
    The SVG BOX can also use the HTML Shape & Mask category (CSS
    clip-path/mask on the <svg>, BC-17.9).
    Both are "whole-SVG" options with different coordinate spaces, and
    both are offered (N4.2).
2.7 Editor-only grid metadata: svgScene.editorGrid?: { spacing > 0 }
    (§5.3). It is document data so it travels with the file, but it is
    never exported or rendered outside vector edit mode. [PROPOSED]


3. CONVERSION, BENDING AND ARCS [OWNER N3.1–N3.3; math ENG]
-----------------------------------------------------------
3.1 Primitive → path (N3.3). An explicit command; one history entry;
    the object id is PRESERVED (selection, state rules and
    clipboard-independent references keep working); no automatic
    reverse conversion.
    - rect → M x y L x+w y L x+w y+h L x y+h Z.
    - ellipse → M cx-rx cy A rx ry 0 1 0 cx+rx cy A rx ry 0 1 0 cx-rx cy Z.
      Two arcs, so the geometry is exact.
    - line → M x1 y1 L x2 y2.
      The EFFECTIVE stroke is materialized: stroke = object.stroke ??
      DEFAULT_SVG_FILL, strokeWidth explicit, fill none. A line always
      renders a stroke, but a path does not, so leaving these unset would
      change the appearance.
    - polygon → M p0 L p1 … Z.
    - starter primitive → materialize into the scene first (existing
      command), then convert.
    - paint, opacity, transform, clip, mask, filter and objectRules are
      copied unchanged.
    - Acceptance: the rendered result is pixel-equal before and after
      (screenshot plus attribute check).
    - After conversion, the Inspector shows path geometry controls
      instead of the primitive controls.
3.2 Segment bending (N3.1): dragging on a straight L segment (P0 → P3)
    at parameter t₀ (the projection of the pointer onto the segment,
    clamped to [0.1, 0.9]):
    - The segment becomes C with initial handles P1 = P0 + (P3−P0)/3 and
      P2 = P0 + 2(P3−P0)/3, which renders the same straight line.
    - While dragging, the cubic is solved so that B(t₀) equals the
      pointer, using the least-norm "drag a point on the curve"
      solution:
        b1 = 3t₀(1−t₀)², b2 = 3t₀²(1−t₀), D = pointer − B(t₀);
        P1 += D·b1/(b1²+b2²), P2 += D·b2/(b1²+b2²).
      This moves B(t₀) by exactly D, with the smallest handle change.
    - The endpoints P0 and P3 never move.
    - Live feedback through the overlay. Commit = one entry.
      Cancel = exact restoration of the L.
    - The created handles are then ordinary handles (§3.4).
    - Bending an existing C segment uses the same solver.
3.3 Arc editing (N3.2): an interactive Canvas control plus numeric input
    for rx, ry and rotation; the endpoints remain editable anchors.
    - Endpoint → centre conversion per SVG 2, Appendix "Implementation
      Notes" (endpoint-to-centre parameterization, steps F.6.5):
        x1′ = cosφ·(x1−x2)/2 + sinφ·(y1−y2)/2,
        y1′ = −sinφ·(x1−x2)/2 + cosφ·(y1−y2)/2;
        centre′ = ±√(…)·(rx·y1′/ry, −ry·x1′/rx), with the sign chosen by
        largeArc ≠ sweep;
        centre = rotate(φ)·centre′ + midpoint;
        start angle θ1 and sweep Δθ from the vector angles.
    - Radius correction (F.6.6): Λ = x1′²/rx² + y1′²/ry². If Λ > 1, the
      renderer scales rx and ry by √Λ.
      Interaction rule: the handles show the EFFECTIVE (corrected) radii.
      Dragging a radius handle below the corrected minimum clamps at that
      minimum. A numeric value below it is stored as authored (valid
      SVG), with a note "rendered at the minimum radius".
    - Canvas controls:
      · two radius handles on the ellipse axes at the arc centre (the
        ellipse is drawn dashed as a guide);
      · a rotation handle on the rx axis extension;
      · flag toggles (large arc, sweep) in the Path subsection and by
        clicking the alternative arc ghost on the Canvas.
    - Degeneracy (F.6.2):
      · endpoints identical → the arc is omitted when rendering; the
        editor shows the anchor only and offers "Delete segment";
      · rx = 0 or ry = 0 → rendered as a straight line; the radius
        handles are hidden, and numeric input can restore a radius;
      · negative radii are stored as their absolute value (spec
        behaviour) and normalized on edit.
    - Transformed objects: the math runs in object-local coordinates
      after the inverse object transform (§4).
    - Live feedback, atomic commit and exact cancel, as every gesture
      (§6).
3.4 Handles and point types: smooth = collinear handles with independent
    lengths; symmetric = mirrored; corner = independent. (CORRECTED
    17.1.3) The temporary unlink for one drag is Ctrl (Windows/Linux) /
    Cmd (macOS), NOT Alt: Alt is reserved for the snapping bypass (§5.2).
    The permanent change is the point type (Path subsection, or the
    "Convert point" command). Converting a point type re-derives the
    opposite handle (smooth: keep its length and align it; symmetric:
    mirror).
3.5 Other path commands (O14, path command management):
    - add an anchor on a segment (exact split: de Casteljau for C/Q, the
      arc split at the parameter angle for A, the midpoint for L);
    - delete anchors (neighbours reconnect; Shift-delete removes the
      segment and opens the path);
    - open/close a subpath;
    - continue from an endpoint with the Pen (Pen: click = corner,
      drag = smooth with handles);
    - reverse the path direction (a needed fill-rule companion);
    - polygon/path bounding-box scaling (deferred since 1.15.6, now in
      BC-17.21).
    Not included (not approved): boolean operations, offset/outline
    stroke, simplification, freehand smoothing, text on path,
    knife/scissors, shape builder, raw path-data text, symbols.


4. COORDINATE SPACES AND TRANSFORMED OBJECTS [ENG]
--------------------------------------------------
Chain: client → getScreenCTM()⁻¹ → SVG user space (viewBox) →
       objectMatrix⁻¹ → object-local space.
- getScreenCTM covers ancestor CSS transforms, the SVG box transform,
  scrolling, preserveAspectRatio letterboxing and any future Canvas zoom
  implemented as a CSS transform.
- The jsdom fallback is fixed to apply the letterbox (F-SVG-2).
- SvgObjectTransform = { translateX, translateY, rotateDeg, scaleX,
  scaleY, skewXDeg, origin: "bbox-center" | { x, y } }
  - Rendered as one SVG transform attribute:
    translate(o) translate(t) rotate(r) skewX(s) scale(sx,sy)
    translate(−o).
  - The origin is the object's untransformed bbox centre by default.
  - CSS state transforms (objectRules) use transform-box: fill-box and
    transform-origin: center, matching that default [UNVERIFIED
    cross-engine equivalence → BC-17.19 test].
- Anchors are stored in object-local space. Pointer positions are
  converted through the inverse matrix, so dragging an anchor of a
  rotated path follows the pointer exactly.
- Bounds of a transformed object for selection, snapping and the
  clipboard = the AABB of its transformed geometry in user space (the
  same philosophy as BC-13 D23: AABBs, no angled snapping).
  Curve bounds use the exact Bézier extrema (derivative roots) and the
  arc extrema, not the control-point hull.
- preserveAspectRatio: today's default (xMidYMid meet). A typed setting
  (align × meet/slice/none) is added in BC-17.19 for the SVG box.
  Editing math is unaffected (the CTM includes it).


5. VECTOR SNAPPING (N4.1) [OWNER N4.1; details ENG]
---------------------------------------------------
5.1 Candidates (same SVG only; never HTML geometry):
    - other anchors: of other objects, and of the same path excluding
      the dragged anchors and their direct neighbours' handles;
    - object bounds: the edges and centres of the transformed AABBs;
    - the viewBox grid.
    Candidates are computed in user space, so transformed objects
    contribute their transformed anchors.
5.2 Preference, bypass and modifiers (CORRECTED 17.1.3 — resolves
    SVG-Q2; BC-17.1.2 let Alt unlink handles, so Alt could not bypass
    snapping during a handle drag, contradicting N4.1)

      governs vector snapping too; no second preference is introduced.

    §5.6); bend → grid only for the dragged curve point; arc handles →

    delta of the primary (the one under the pointer).

5.3 Grid:
    - spacing in viewBox units: svgScene.editorGrid.spacing, default =
      a "nice" step (1, 2, 5 × 10ⁿ) closest to 1/20 of the viewBox's
      shorter side;
    - visible only in vector edit mode, behind a toggle (per-viewer
      localStorage, guarded, like the other UI preferences);
    - grid snapping follows the global Snap preference;
    - origin = (viewBox.minX, viewBox.minY).
5.4 Threshold: 6 screen px (the BC-13 threshold), converted to user
    units per axis through the CTM scale (√(a²+b²) for x, √(c²+d²) for
    y), so snapping feels identical at any SVG size or zoom.
    Priority: anchors > bounds > grid; then the smaller distance; ties go
    to the earlier object in paint order (deterministic).
    Engine: snapEngine's pure 1-D ranking is reused; the producers are
    new.
5.5 Feedback: snap markers (point and guide lines) drawn in the vector
    overlay, non-scaling, editor-only (D38 policy).
5.6 Handles snap to anchors only (to help collinearity), never to the
    grid. [ENG]


6. GESTURE LIFECYCLE, CONFLICT-SAFE ROLLBACK, KEYBOARD, SELECTION
   (CORRECTED 17.1.3 — resolves SVG-Q1 and SVG-Q5; replaces F-SVG-3)
-----------------------------------------------------------------
6.1 One vector gesture transaction for every vector gesture (draw, move,
    resize, anchor, handle, bend, arc, transform, clip-geometry edit,
    Pen segment drags). States: idle → active → ending → done.
    BEGIN (pointerdown past the drag threshold, or the tool's start):
    - stopDesignPlayback (Report 1 §16.3);
    - interruptActiveInteraction is NOT needed (one pointer, one gesture),
      but the gesture REGISTERS with the active-interaction registry
      (registerActiveInteraction(cancel)), so Undo/Redo, clipboard,
      Delete, Duplicate, Copy/Paste CSS, Preview, document replacement and
      the project workflow cancel it first (BC-13.5.1 Option B, reused);
    - beginTransaction (BC-01);
    - records the gesture's OWNERSHIP RECORD:
        { token, svgNodeId, touched: [{ objectId, slice }],
          before: deep copy of each touched slice,
          lastWritten: null, selectionBefore }
      A "slice" is exactly the fields the gesture can write: commands
      (+anchors meta) for path tools; the geometry fields for primitives;
      transform for transform tools; the clip/mask geometry for clip
      editing. Never the whole document, never the whole SVG node.
    UPDATE (per animation frame, coalesced):
    - computes the new slice values (snapping per §5) and writes them
      with the "Live" actions inside the transaction; records lastWritten;
    - stale callbacks: every rAF/timer/pointer callback checks the token
      and state === active; otherwise it returns.
    COMMIT (pointerup with the pointer still captured, Enter for drafts):
    - ending → commitTransaction: exactly ONE history entry; a gesture
      that changed nothing records nothing;
    - unregister; done.
    CANCEL — each of: Escape; pointercancel; lostpointercapture without a
    preceding pointerup; window blur; unmount of the overlay; Preview;
    project New/Open/Import/Close/switch; a recognized editor command via
    the registry; selection change through a command; deletion or
    reparent of the SVG node or a touched object:
    - ending → conflict-safe rollback (6.2) → cancelTransaction: NO
      history entry, redo stack preserved; unregister; done.
    DUPLICATE TERMINAL EVENTS (pointerup after pointercancel, a second
    Escape, lostpointercapture after pointerup, a command after commit):
    the state check makes every terminal handler after the first a no-op.
    (F-SVG-3 behaviour — pointercancel commits, Escape restores the whole
    document snapshot, no registry — is removed. pointercancel and lost
    capture now CANCEL.)
6.2 Conflict-safe rollback (compare-and-restore, per touched slice):
    For each touched { objectId, slice }:
    1. If the SVG node no longer exists, or the object no longer exists →
       skip it. A cancelled gesture NEVER recreates a deleted object or
       a deleted parent.
    2. If the object's current slice deep-equals lastWritten (nobody else
       changed it since the gesture's own last write) → restore `before`.
    3. Otherwise (an external change landed on the same slice) → leave
       the current value, record a development diagnostic, and do not
       restore stale data.
    Nothing outside the touched slices is ever written, so unrelated
    edits — on other objects, other nodes, definitions, styling — are
    never overwritten. Restored values contain only the gesture's own
    fields, so no invalid reference can be reintroduced (definitions are
    inline values; there are no references to dangle).
    The transaction is then cancelled without recording history. Because
    the slice restore uses the transaction's write path, the document
    revision advances and caches invalidate normally.
6.3 Preventing conflicts in the first place:
    - The store's document-mutation boundary interrupts the active
      interaction before applying any mutation that is not the gesture's
      own live write (the same boundary that stops playback). So the
      known commands always run on committed state, and case 3 in 6.2 is
      a defended edge, not an expected path.
    - Project replacement (New/Open/Import/Close) calls
      interruptActiveInteraction first (existing projectWorkflow paths).
    - A history step while active is impossible: Undo/Redo interrupt
      first.
    - Clipboard operations interrupt first.
6.4 Relationship to the HTML gestures: createFreeInteraction keeps its
    BC-13.5 contract. BC-17.20 either generalizes it into a shared
    "gesture transaction" (begin/update/commit/cancel with ownership
    records and compare-and-restore) used by both, or adds a sibling with
    the identical contract; the contract tests are shared either way.
    The existing SVG move, resize and draw sessions migrate onto it in
    BC-17.20. Until then F-SVG-3 remains existing behaviour, and no new
    SVG gesture ships before BC-17.20 (17.18/17.19 add none).
6.5 Modes: object mode (today's Select tool) ⇄ path-edit mode (double-
    click a path/polygon, or "Edit path"; primitives first offer Convert,
    N3.3). Escape leaves path-edit, and a second Escape leaves vector edit
    mode (today's behaviour). While a gesture is active, Escape only
    cancels the gesture.
6.6 Keyboard routing (in vector edit mode the vector layer owns these
    keys before the element layer):
    - Arrows: nudge the selected anchors (path-edit) or objects (object
      mode) by 1 user unit; Shift = 10; the grid step when grid snapping
      is on. Each key press is one history entry (consecutive nudges may
      merge per the existing mergeHistory policy).
    - Delete/Backspace: delete the selected anchors (path-edit) or
      objects.
    - Ctrl/Cmd+C, X, V, D: the vector clipboard (§8) when vector objects
      are selected or the vector edit mode is active; otherwise the
      element/CSS clipboards (unchanged).
    - Enter: commit the draft (existing); Tab/Shift+Tab: cycle anchors in
      path-edit (editor accessibility; this is EDITOR focus, not
      authored SVG focusability, §7.5).
    - Ctrl/Cmd+A: select all anchors (path-edit) or objects.
6.7 Multi-anchor selection (CORRECTED 17.1.3 to match the existing
    convention): Mod-click toggles an anchor, Shift-click adds; a marquee
    in path-edit mode selects anchors inside it (Shift adds, Mod toggles).
    Moving several anchors translates them together (their handles move
    with them).
6.8 Pointer types: Pointer Events, so mouse, pen and touch share one path
    (BC-13 D16 policy). There is no pressure or multi-touch; a second
    pointer never joins an active gesture (it follows the BC-13 policy
    for HTML gestures, reused unchanged).
    Touch targets are at least 24 screen px for the hit areas.


7. STYLING, CLIP, MASK, FILTERS, STATES [OWNER O14, N4.2]
---------------------------------------------------------
7.1 Value semantics for all definitions [ENG]: gradients, clip shapes,
    masks and filter lists are stored INLINE on the object (or on the
    scene for content clip/mask), never as shared, user-managed
    definitions. Consequences (N4.2's required definitions):
    - ownership: the owning object (or the scene);
    - reuse: automatic, through compile-time deduplication. Identical
      definitions in one SVG compile to one <defs> entry. Users never
      edit a shared def, so editing one object never changes another
      (no hidden coupling);
    - reference remapping: no stored references exist. The compiler
      generates ids `ly-s<svgToken>-<kind><n>` per export (unique per
      document) and url(#id) references;
    - clipboard: definitions travel inside the object (§8);
    - deletion: they go with the object; there are no orphans to
      garbage-collect;
    - persistence: inside the object (v4 schema, §2);
    - Undo/Redo: part of the node snapshot;
    - export: <defs> generated per SVG, deduplicated, with ids unique per
      document.
    - Cost: duplicated data in the file when many objects share a look.
      It is bounded by the limits (§9).
    - (CORRECTED 17.1.3, consistency) The ONE referenced kind is motion:
      keyframes are document-level assets (styleAssets.keyframes, shared
      with HTML, Report 1 §4.5) referenced by id from objectRules. They
      are validated for resolution by integrity, carried and remapped by
      the vector clipboard (§8.2–8.3), the element clipboard and presets
      through the one shared asset utility. Gradients, clips, masks and
      filters remain inline values with no stored ids or references.
7.2 Clip (per object and the whole content):
    SvgClip = { shape: rect | ellipse | polygon | path(commands),
                units: objectBoundingBox | userSpaceOnUse, clipRule }
    - Clip geometry is editable numerically (BC-17.19) and with the
      vector tools in a "Edit clip path" mode (BC-17.21), using the same
      anchor/handle/arc tools.
7.3 Mask:
    SvgMask = { type: luminance | alpha,
                source: gradient (linear/radial with opacity stops) | shape
                        (fill, opacity) }
    - The units are as for clip.
    - Image masks are not included (no external references; an
      embedded-image mask would need the BC-07 pipeline inside SVG).
      CSS image masks remain available on the SVG BOX (BC-17.9).
7.4 Filters (the Effects category for vector objects): an ordered list of
    typed primitives (feGaussianBlur stdDeviation, feDropShadow
    dx/dy/std/colour/opacity, feColorMatrix saturate | hueRotate |
    matrix-free presets), compiled into <filter> in defs.
    - SVG filter primitives are used instead of CSS filter() functions on
      SVG children, because the cross-engine support of the latter is
      uneven [UNVERIFIED].
    - The SVG BOX keeps the CSS filter group.
7.5 States and motion on objects (CORRECTED 17.1.3 — resolves SVG-Q6 and
    a newly found transform-composition flaw, F-SVG-5)
7.5.1 Rules: objectRules: [{ id, condition, groups }] using the SAME
    StyleCondition type as HTML rules (Report 1 §4.3), restricted by the
    registry's vector profile:
    - groups: paint (fill, stroke, opacities, stroke width/dash/offset),
      opacity, filter list, transform (individual translate/rotate/scale),
      motion (transitions, animations).
    - self atoms: hover, active (pointer-driven only).
    - ancestor atoms (scope = the SVG node, or its parent/component per
      O6): hover, active, focus-visible, focus-within, and the runtime/
      document atoms of that ancestor element — expanded, open, selected,
      current, checked, disabled. Example: a chevron object rotates when
      its collapsible trigger is expanded; an icon recolours when its
      button shows focus-visible.
7.5.2 Focusability contract [ENG]:
    - Vector objects are NEVER focusable. Layoutry authors no tabindex,
      no links, no roles and no interactions on vector objects (none is
      approved), so the self focus atoms (focus, focus-visible,
      focus-within) are INAPPLICABLE on vector objects and not offered.
      Decorative objects are never made focusable to enable styling.
    - Focus styling of a graphic is authored on the FOCUSABLE element
      that contains it, through ancestor atoms (7.5.1), which is the
      accessible pattern (the focusable control owns focus; the graphic
      reflects it).
    - The SVG box itself follows the HTML element rules: it is focusable
      only if its own element semantics make it so; focus atoms on the
      SVG box are offered exactly when the registry offers them for
      that element.
    - Editor selection, editor keyboard focus (Tab cycling anchors in
      path-edit, §6.6) and Design state forcing are editor features and
      never add authored focusability.
    - Accessibility semantics: unchanged — the SVG box's existing
      accessibility fields (name or decorative) govern; vector objects
      carry no ARIA.
    - Design forces states per object in vector edit mode
      ([data-ly-force] on the object); Preview and Export use the real
      pseudo-classes and ancestor attributes. Parity per Report 1 §8.10.
7.5.3 Transform composition (F-SVG-5, an architecture flaw found in
    17.1.3): CSS `transform` on an SVG element REPLACES its transform
    presentation attribute; it does not compose with it. BC-17.1.2 put
    the base transform in the attribute and state transforms in CSS, so
    a hover "scale 1.1" would have discarded the object's base rotation
    or translation. Corrected model:
    - an object that has ANY transform-capable rule or motion is rendered
      inside a generated wrapper:
        <g class="ly-vo-<id>">            ← state/motion transforms (CSS),
                                            transform-box: fill-box,
                                            transform-origin: center
          <path class="ly-vs-<id>"         ← base transform attribute,
                transform="…" fill="…"/>    paint, clip-path, mask, filter
        </g>
      objects without such rules render as today (no wrapper);
    - state/motion transforms use the individual properties translate /
      rotate / scale on the wrapper, so they compose OUTSIDE the base
      transform and never replace it; their origin is the centre of the
      wrapper's fill box (= the transformed object's AABB in user space);
    - paint/opacity/filter states target the shape (`.ly-vs-<id>`) with
      the condition evaluated on the wrapper or ancestor, e.g.
        .ly-vs-a1:where(.ly-vo-a1:hover > *) { fill: … }
      so specificity stays (0,1,0);
    - clip-path, mask and filter stay on the shape, so they live in the
      object's local space (after its base transform) and move with it.
    [UNVERIFIED: individual transform properties on SVG <g> with
    fill-box in Gecko/WebKit → BC-17.19 targeted test; R-20]
7.5.4 Motion: transitions and keyframe animations of fill, stroke,
    opacity, stroke-dashoffset (on the shape) and translate/rotate/scale
    (on the wrapper), through the shared motion architecture (BC-17.11):
    keyframes are document assets (styleAssets.keyframes) referenced by
    id; Design safety, N11 playback, P-5 interruption and P-6 reduced
    motion apply exactly as for HTML.
    - SVG presentation attributes have zero specificity, so base =
      attributes and states = CSS: a clean cascade. Precedence follows
      Report 1 §6.
    - Gradient paint in a state → CSS fill: url(#generated) (state
      gradients compile to defs too).
7.6 Compile: SVG content rendering is generated by the same compiler
    module family as the HTML styles (Report 1 L3/L4), so Design, Preview
    and Export emit identical attributes, defs and rules.


8. VECTOR CLIPBOARD (N5) [OWNER N5; details ENG] (CORRECTED 17.1.3 —
   resolves SVG-Q3 dependencies and SVG-Q4 coordinate conversion)
-----------------------------------------------------------------------
8.1 Separation and routing:
    - A separate internal vector clipboard in editor UI state. It never
      touches the element clipboard, the CSS clipboard or the system
      clipboard text, and they never touch it.
    - Routing (§6.6): Ctrl/Cmd+C/X/V/D act on the vector clipboard when
      vector objects are selected or vector edit mode is active;
      otherwise the existing clipboards act, unchanged.
    - Like the element clipboard, it is app-level and survives document
      replacement [VERIFIED: useEditorStore documents that the clipboard
      and the Snap preference survive a document replacement], so
      cross-project paste in one session is supported.
8.2 Dependency discovery (copy time). For each copied object, in paint
    order:
    - inline definitions — gradients in paint (base and state rules),
      clip, mask, filter list — are part of the object value, so they are
      included by the deep copy itself (value semantics, §7.1);
    - objectRules — state styling, paint, transform and motion groups —
      are part of the object;
    - motion dependencies: every keyframes id referenced by an objectRule
      or the object's motion group is resolved in the source document's
      styleAssets.keyframes and copied into the payload;
    - nothing else: SVG-level settings (viewBox, preserveAspectRatio,
      contentClip/contentMask, editorGrid) belong to the SVG node and are
      not copied with objects.
    Payload (validated with the same Zod schemas as project data):
      VectorClipboardPayload {
        version: 1;
        sourceDocToken: string;          // per opened document (Report 1 §4.11.5)
        source: { svgNodeId; viewBox; preserveAspectRatio };
        objects: SvgObject[];            // deep copies, paint order
        keyframes: KeyframesDefinition[];// referenced only, with canonical hashes
        bounds: Rect;                    // the group's transformed AABB, source user space
      }
8.3 Paste, deduplication and remapping (one transaction):
    1. Validate the payload and the destination (exists, not protected
       for paint, limits not exceeded after paste). Any failure → nothing
       changes, a notice explains why.
    2. Keyframes: the shared asset utility (Report 1 §14). Equal canonical
       hash in the destination → reuse that id; otherwise insert with a
       fresh id and a unique display name ("Pulse", "Pulse (2)"). Every
       reference in the pasted objectRules is remapped. Identical assets
       are never duplicated; a dangling keyframe reference is impossible
       because every referenced keyframe is in the payload and is either
       matched or inserted before the objects are added.
    3. Fresh object ids (generateSvgObjectId) and fresh objectRule ids.
       Inline definitions need no remapping; generated def ids are
       compile-time only.
    4. Geometry placement and conversion (8.4).
    5. Insert at the top of the paint order, keeping relative order;
       select the pasted objects.
    History: copy records nothing; paste, cut (copy + delete) and
    duplicate are one entry each. Undo removes exactly the pasted objects and
    the keyframes inserted by that paste (they are part of the same
    snapshot); Redo restores both.
8.4 Coordinate spaces and cross-viewBox conversion
8.4.1 Spaces (distinct, never conflated):
    object-local  path/primitive geometry, clip/mask/gradient values in
                  userSpaceOnUse, filter primitive values
    object        T_obj = translate(o) translate(t) rotate(r) skewX(k)
    transform     scale(sx, sy) translate(−o) (§4); local → SVG user space
    SVG user      the viewBox coordinates
    space
    viewport      viewBox + preserveAspectRatio → the SVG's CSS box
    screen        CTM (CSS transforms, scroll, zoom)
    objectBoundingBox values (gradients, clips, masks, filter regions in
    bbox units) are relative to the object's own bbox and are unaffected
    by any placement.
8.4.2 Placement policy (ENG default; a parameter of one mechanism, so a
    different policy later changes no architecture): PROPORTIONAL
    placement — the pasted group keeps its size and position relative to
    its SVG's drawing area, with the aspect ratio of every object
    preserved.
      s  = min(dW/sW, dH/sH)                (uniform; sW,sH,dW,dH = viewBox sizes)
      p' = dCentre + s·(p − sCentre)        (for any user-space point p)
      then shift minimally so the scaled bounds lie inside the
      destination viewBox (always possible because s fits), then the
      paste offset.
    - Same SVG: s = 1, no shift; offset by the grid step (or 10 user
      units without a grid); repeated pastes cascade.
    - Different SVG with the same viewBox: s = 1, identical placement.
    Why proportional [ENG]: each SVG is its own drawing with its own
    coordinate system; the result is deterministic and does not depend on
    the two SVGs' rendered sizes, the zoom, or whether the destination is
    visible. The alternatives — keep user units (s = 1 always) or keep the
    on-screen size (s from the two CTMs) — are the same mechanism with a
    different s; neither is approved over the other, and the owner may
    choose one in the BC-17.22 brief without architectural impact.
8.4.3 Applying the conversion WITHOUT rewriting geometry [ENG]: the
    affine C = translate(c)·scale(s), with c = dCentre − s·sCentre plus
    the fit shift and the paste offset, is composed into each object's
    transform, exactly, because a uniform scale commutes with rotation,
    skew and the object's own scale:
      C·T_obj = translate(o) translate(t') rotate(r) skewX(k)
                scale(s·sx, s·sy) translate(−o)
      with t' = c + s·(o + t) − o
    Geometry, origin, rotation, skew and reflections (negative sx/sy) are
    untouched. Because the scale sits in the object transform, everything
    expressed in object-local space scales with it, exactly: stroke
    widths, dash arrays/offsets, userSpaceOnUse gradients, clip and mask
    geometry, filter blur/offsets, and shape-level animations
    (stroke-dashoffset, stroke-width keyframes).
    The only values outside object-local space are wrapper-level state
    and motion TRANSLATIONS (§7.5.3: translate in the user space above
    the object). They are lengths, so they are multiplied by s in the
    pasted objectRules and in the pasted keyframes. Scaled keyframes have
    a different canonical hash, so they dedupe/insert as their own asset.
    Rotations and scale factors are unitless and unchanged.
    Arcs are never approximated: they stay A commands in local space.
8.4.4 Where exact appearance is impossible or not the goal (documented,
    shown in the paste notice when it applies):
    - destination preserveAspectRatio "none": its viewport stretches all
      of its content non-uniformly on screen; pasted objects are stretched
      exactly like the destination's own objects. Similarity is preserved
      in user space, not on screen;
    - on-screen size changes whenever the two SVGs render the drawing at
      different scales (by policy, 8.4.2);
    - content clipped by the destination's contentClip/contentMask or its
      viewport is clipped (the source's whole-content clip is not copied);
    - state transforms whose origin is the fill-box centre stay centred
      (the fill box scales with the object), so they remain exact.
    Validation and safe failure: non-finite results, |v| > 1e6 or a limit
    breach after conversion refuse the whole paste (nothing changes).
8.5 Representative examples (source → destination)
    1. Equal aspect, different size: square 10×10 at (45,45) in viewBox
       0 0 100 100 → viewBox 0 0 1000 1000. s = 10. The object's transform
       gains scale ×10 and the translation that maps its centre (50,50) to
       (500,500); its geometry stays 45,45,10,10; stroke 1 renders as 10.
    2. Different aspect: 0 0 100 100 → 0 0 400 100. s = min(4, 1) = 1;
       the object keeps its size; p' = (200,50) + (p − (50,50)), i.e. it
       is centred horizontally the same way it was.
    3. Non-zero origins: viewBox −50 −50 100 100 → 200 200 50 50.
       s = 0.5; sCentre (0,0) → dCentre (225,225); an object at (−10,0)
       lands at (220,225).
    4. Transformed source: a path rotated 30° and skewed 10° with origin
       bbox-centre, pasted with s = 2 → rotate 30°, skew 10° unchanged;
       scale (sx,sy)·2; t' per 8.4.3; pixel-identical shape, twice the
       relative size.
    5. userSpaceOnUse gradient (x1=0..x2=20 in local units) on that
       object: unchanged numbers, rendered over the same part of the
       shape (it scales with the transform). An objectBoundingBox
       gradient is trivially unaffected.
    6. Per-object clip + mask: clip polygon and luminance mask gradient
       stay in local space and scale with the object; the destination's
       own contentClip still applies on top (8.4.4).
    7. Motion: a hover "translate(0, −4)" bounce on the wrapper and a
       "dash-draw" keyframe on stroke-dashoffset. With s = 0.5 the pasted
       hover becomes translate(0, −2); "dash-draw" needs no change (shape
       level) and dedupes to the destination's identical keyframe if one
       exists; a "Bounce" keyframe with translate values is scaled and
       inserted as "Bounce (2)" unless an identical scaled one exists.
8.6 Atomicity, protection and limits: one history entry per operation;
    paste is refused if the destination SVG is protected (Parent Style
    Protection applies to paint, as today) or a limit would be exceeded;
    nothing partial is ever applied.
8.7 Element-level copy of a whole SVG is unchanged (cloneNodeWithFreshIds
    regenerates the object ids, as today). Referenced keyframes travel
    with it per Report 1 §14 (the same utility).


9. SECURITY AND COMPLEXITY BOUNDS [ENG]
---------------------------------------
- Typed data only: no raw `d`, no raw markup, no <script>,
  <foreignObject>, <image>, external <use>, event attributes, external
  url(), data: URLs or authored ids.
- Paint colours are validated at the schema/command layer AND at export
  (F-SVG-4).
- Numbers are finite with |v| ≤ 1e6; radii ≥ 0 (normalized); dash
  values ≥ 0; opacities 0..1; at most 2 decimals from pointer input.
- Validation bounds for untrusted files (projectLimits rationale; not UX
  caps):
  - ≤ 20,000 commands per path;
  - ≤ 5,000 objects per SVG;
  - ≤ 200,000 total commands per SVG;
  - ≤ 32 gradient stops;
  - ≤ 16 filter primitives per object;
  - clip/mask shapes bounded by the same command limits.
  Final values are confirmed by measurement in BC-17.18. Files beyond the
  bounds are refused with the existing integrity error path; commands
  beyond them refuse with a notice.
- Generated ids use [a-z0-9-] from internal tokens only, with the
  collision-safe prefix against authored htmlIds (Report 1 §11); they are
  unique per document at export.
- Vector clipboard payloads are validated with the project schemas
  before paste, even though they never leave the process (§8.2).


10. PERFORMANCE [ENG; measured at implementation]
-------------------------------------------------
- A path-edit frame recomputes only the edited object's `d`, its overlay
  and its snap candidates (incremental). No stylesheet work happens
  during the gesture: vector geometry is attributes rendered from the
  live store (Report 1 §8.11).
- Snap candidates are indexed per SVG and per axis, and invalidated on
  document change (the BC-13 D26/D37 approach).
- Targets (provisional, NOT measured): ≤ 4 ms of engine+geometry time
  per frame for a 10,000-command path; ≤ 16 ms total frame time for
  1,000 objects in one SVG (Chromium, median, production build, 5 runs,
  CPU trace) — BC-17.20/17.21.
- Definition deduplication: linear hashing; 1,000 objects with 500 equal
  gradients compile to one def each per distinct value — BC-17.19.
- Vector paste with 200 objects + 20 keyframes: one transaction; no
  recompile outside the destination SVG — BC-17.22.
- Exact curve-bound computation is cached per command.
