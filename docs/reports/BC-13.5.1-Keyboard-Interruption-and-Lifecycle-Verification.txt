- The approved Option B policy is implemented:
  - Escape cancels an active Free drag/resize;
  - a recognized editor command cancels it from the command's own
    execution path, only when that command actually runs;
  - every other key (unassigned letters, numbers, punctuation,
    unsupported Ctrl/Cmd combinations, modifiers) leaves the interaction
    alone.
- The "any non-modifier key cancels" branch was removed from the
  lifecycle. The Canvas registers the active interaction in an
  editor-owned registry (editor/utils/activeInteraction). The
  authoritative paths call interruptActiveInteraction() first:
  - the store actions behind the shortcuts AND the menus/toolbar
    (Undo/Redo, Copy/Cut/Paste/Duplicate, Delete request/confirm,
    Copy/Paste CSS, Preview, replacing the document);
  - the project workflow and commands (Save, Save As, New, Open, Import,
    Close, Download);
  - Export Code.
  No second list of shortcuts exists, and no new shortcut system.
- Two real defects were found while verifying, both fixed:
  D1 Cancelling a gesture on a SAVED document left it "Unsaved". The
     node-scoped rollback built a structurally identical but new document
     object, and the unsaved check compares identity. This affected
     Escape, every BC-13.5 cancel path, and the no-op path. Fixed: the
     rollback reuses the snapshot's document object when it is
     structurally identical.
  D2 Dragging the same text element twice in a row: the first drag left a
     native text selection, so the second press became a native
     drag-and-drop. That fired pointercancel, which since BC-13.5 rolls
     back (before, it silently stopped the drag). Fixed in the shared
     lifecycle: no text selection during a gesture, and a native dragstart
     is prevented. A regression test fails without the fix.

3. ROOT CAUSE OF THE OVERLY BROAD POLICY
----------------------------------------
- In BC-13.5, createFreeInteraction's capture-phase keydown handler ended
  with `cancel("keyboard")` for every key that was not Escape or a
  modifier.
- It was a blanket stand-in for "a command might be about to run": the
  lifecycle had no way to know whether a key resolved to a command, so it
  cancelled on all of them.
- The knowledge of what a command is belongs to the command dispatch, not
  to the gesture.


4. CORRECTED COMMAND-DISPATCH AND CANCELLATION ARCHITECTURE
-----------------------------------------------------------
- The gesture owns only Escape (consumed: preventDefault +
  stopPropagation, so the Canvas's deselect never runs) and modifiers
  (they update Alt/Shift state).
- At start it calls registerActiveInteraction(() => cancel("command")).
  Cleanup unregisters, exactly once.
- Commands: each authoritative execution path calls
  interruptActiveInteraction() first. The interaction is rolled back
  (node-scoped), cleaned up, and unregistered; then the command runs on
  committed state.
  - Store actions: guarded by the action's own eligibility (below), so a
    disabled command never cancels.
  - Project workflow/commands: at the entry that reads or replaces the
    document.
- The keyboard shortcut hooks are unchanged: they keep their existing
  focus/preview/dialog restrictions, and only call the actions.
- Because the guard sits in the action itself, the Edit/File menus, the
  toolbar and a second touch pointer get the same contract.
- No duplicate cancellation: the registry clears itself before calling
  cancel, and cancel is idempotent. The command is called once by its
  single dispatcher.
Eligibility (no cancel when the command would do nothing):
- Undo: past > 0; Redo: future > 0;
- Copy, Duplicate, Delete, Request Delete: an existing non-root element
  is selected (Duplicate and Request Delete also require no pending
  confirmation);
- Cut: as Copy, plus no pending confirmation;
- Paste: clipboard non-empty and no pending confirmation;
- Confirm Delete: a pending confirmation;
- Copy CSS: a primary selection; Paste CSS: a CSS clipboard plus a
  selection;
- Preview: not already previewing;
- replaceDocument: always.
- Project shortcuts ignored while a dialog is open never reach the
  workflow, so nothing is cancelled (tested).

7. COMMAND EXECUTION ORDERING
-----------------------------
[VERIFIED U unless marked]
- Delete (drag and resize):
  - rolled back first, then deleted;
  - one history entry (the delete), no drag entry;
  - the release after it records nothing;
  - Undo restores the element at its committed geometry. [U + B]
- Undo:
  - cancel first, then undo the last committed edit once;
  - the cancelled gesture is never in history;
  - redo entry created by the undo only, then Redo restores it. [U + B]
- Redo: cancel first, then redo once (both chords). [U]
- Save:
  - commands.save → editInProgress → cancel → serialize;
  - the stored project has the committed geometry; cancel is called
    once. [U];
  - Ctrl+S in the browser: the element is back first, and the normal
    save flow follows. [B]
- Download: cancel first; the file holds the committed geometry. [U]
- New Project (workflow): cancel BEFORE the unsaved-changes check, so a
  saved, committed document doesn't prompt. [U]
- Copy/Cut/Duplicate: the clipboard and the copies carry the committed
  geometry; one entry for Duplicate/Cut. [U]
- replaceDocument (open/import/new/close all end here): the outgoing
  document has its committed geometry back before it is replaced. [U]
- Another, non-gesture open edit (an Inspector merge transaction or a
  drawing) is still refused by Save, as before. [U]

15. REMAINING LIMITATIONS OR UNRESOLVED DEFECTS
-----------------------------------------------
- Page switching: no page model exists (section 8).

  Inspector field edit, Structure moves) are not guarded. They need a

  second touch pointer could reach them; the BC-13.5 subscription safety
  net covers deletions/moves from such paths.

  (unchanged from BC-13.5).
- Touch/pen are simulated only.
- P1 (rendering performance) and C1 (containment) stay open; K1 is
  resolved (Option B).
No unresolved defects found in this checkpoint.
