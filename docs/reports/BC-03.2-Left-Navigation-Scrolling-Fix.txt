1. EXECUTIVE SUMMARY
--------------------
The Resource panel's Elements, Components and Structure lists now
scroll inside the panel. Every tile and tree row can be reached with the
mouse wheel, the keyboard and by dragging. The panel's title, search box
and filter chips stay in place.

- Collapsing and expanding the panel keeps the active list's position:
  the same item is at the top, within 2 px, in Chromium, Firefox, WebKit
  and Electron.
- Switching sections still starts the new section at the top.
- Dragging from a scrolled list still inserts exactly what a click
  inserts, and Undo restores the document.
- The Canvas, Inspector and page never scroll as a side effect.

One regression was introduced by the scroll fix, and fixed in this
checkpoint. The full Electron suite caught it (the persistence soak test
failed 3 of 3 times). With the lists scrollable, dnd-kit's drag
auto-scroll began scrolling the list while a tile was dragged out of it,
by 94 px per drag, so the next drag started on the search box. It is
fixed with dnd-kit's own canScroll option, and a regression test now
covers it.

The changes:
- 4 product files changed and 1 component added:
  - one class in ResourceSidebar;
  - a ResourceScrollRegion component used by the two list owners;
  - an auto-scroll opt-out in EditorApp.
- No change to the document model, Canvas drag architecture, Inspector,
  Workspace or Electron security.

The new browser spec fails against the BC-03.1 code: 20 of its first 22
tests fail, and the auto-scroll test fails without the canScroll change.
Everything passes after the fix. Section 12 has the counts.

Recommendation: CLOSE BC-03 (section 16).


2. ROOT CAUSE CONFIRMATION
--------------------------
Confirmed as found in BC-03.1.

The content wrapper in src/components/layout/ResourceSidebar.tsx was a
block box inside the panel card's flex row. ResourceContextPanel's
flex-1, and the list regions' min-h-0 flex-1 overflow-y-auto, therefore
never received a height limit. The lists grew to their full content
height and were clipped by the wrapper's overflow-hidden (B1). Focus
scrolling then scrolled that clipped box, hiding the header (B2).

Making the wrapper a flex container restores the chain. No min-height:
0 had to be added anywhere:
- the wrapper and ResourceContextPanel are row flex items, stretched on
  the cross axis;
- the tabpanel, the catalog root and both list regions already had
  min-h-0;
- ResourceContextPanel already had min-w-0.

Measured on the old code with the new spec (Chromium):
- the lists never scroll;
- Tab and selection scroll the wrapper and hide the controls;
- B3 can't even be exercised;
- 20 of 22 tests fail.

5. SCROLL-POSITION RESTORATION MECHANISM
----------------------------------------
How collapse works: AppShell sets collapsed; ResourceSidebar keeps the
content mounted and gives the wrapper display:none (UI-1.6). The
regions are therefore neither unmounted nor resized: they lose their
rendered box. Browsers then disagree on the scroll offset (BC-03.1:
Firefox kept it, WebKit reset it to 0, Chromium kept part of it).

ResourceScrollRegion:
- Remember: a passive "scroll" listener writes element.scrollTop into a
  ref, only while clientHeight > 0. A box that isn't rendered reports a
  meaningless offset.
  - No React state, so scrolling triggers no render.
  - The listener is added once per region and removed on unmount
    (unit-tested).
- Restore: useLayoutEffect on `hidden`. When the region becomes visible,
  the DOM already has display:flex, so it has layout. The remembered
  offset is written back before paint.
  - No timers, no animation-frame delays, no loop: it writes once per
    expand. The scroll event it causes stores the same value.
- overflow-anchor: none on the region.
  - The expand animates the panel width (240 ms), so the offset is
    restored while the list is still narrow and its tiles are taller.
  - With scroll anchoring, the browser then moved the offset as the
    list widened, to keep the narrow layout's top tile. Measured in
    Chromium: 900 → 532 (Elements), 473 (Components), 836 (Structure).
  - With anchoring off, the offset stays, and at the final width the
    same item is back at the top. No list here changes content above
    the visible area while the user is scrolled, so anchoring has
    nothing else to do.
- Scope:
  - The position is per region instance, so per section.
  - It isn't stored in the document, Zustand, localStorage or history.
  - There is no autosave trigger and no Undo entry. Section 6 has the
    integrity test.
- Section switching: both regions are keyed by section, so a switch
  creates a fresh region at scrollTop 0. This is the established
  behavior, now deterministic for Structure and the placeholders too.

7. DRAG-AND-DROP REGRESSION RESULTS
-----------------------------------
Test "the last tile, dragged from the bottom of the list" (Elements and
Components):
1. Wheel to the end of the list.
2. The lowest enabled tile is fully visible and under the pointer.
3. Drag it onto the bottom of the page sheet:
   - the exported code equals the exported code from clicking the same
     tile, so it is the same component in the same place;
   - the list's scrollTop is unchanged after the drop, so no jump;
   - the new node exists on the canvas, and clicking it selects it (one
     aria-selected row in Structure);
   - Undo restores the exported code exactly.
Result: it passes in all three browsers.

Regression found and fixed in this checkpoint:
- Found by e2e/desktop/persistence-soak.spec.ts: 3 of 3 failed on the
  first fixed build, and it passed in BC-02.6.
- Diagnosis (temporary probe): dragging the Container tile from an
  unscrolled list moved the list 0 → 94 → 184 px. The second drag then
  started on the search field and inserted nothing.
- Cause: dnd-kit auto-scroll scrolls the dragged item's scrollable
  ancestors when the pointer is in their edge band (y-threshold 0.2).
  The path to the Canvas crosses the list's bottom band. Before BC-03.2
  the list had nothing to scroll, so this was invisible.
- Fix: canScroll in EditorApp skips regions marked
  data-no-drag-autoscroll. Nothing is ever dropped into these lists, and
  the Structure tree has no drag support.
- New test, "dragging a tile out of an unscrolled list never scrolls the
  list":
  - it drags three times from the same spot, dwelling in the edge band;
  - it samples scrollTop at every step of every drag;
  - the list stays at 0 and all three drags insert.
  - It fails without the fix.
  - Soak after the fix: 3 of 3 passed. Full desktop suite: passed.
- One WebKit-only behavior was found on the way, also present before
  BC-03.2: a new drag started within milliseconds of the previous drop
  is ignored (dnd-kit's drop animation is still running).
  - The same test fails identically on the old product code in WebKit.
  - A 500 ms pause between drags (person-paced) makes it reliable in
    WebKit; Chromium and Firefox don't need it.
  - It isn't a scrolling issue and was left as a note (section 14).

11. PERFORMANCE OBSERVATIONS
----------------------------
Temporary probe (deleted): 30 wheel events over a list, at 1440×900.

  Browser    List        Long tasks             Panel DOM mutations   Time to next frame
  Chromium   Elements    0                      0                     0–0.1 ms
             Components  0                      0
  Firefox    both        API not available      0                     0.4–0.7 ms
  WebKit     both        API not available      0                     0.2–0.5 ms

- "0 DOM mutations in the panel while scrolling" means scrolling causes
  no re-render that touches the DOM. By construction there is no React
  state update per scroll event: the position is a ref.
- No scroll feedback loop: one write per expand.
- No listener build-up: one listener per region, removed on unmount
  (unit-tested). The lifecycle of the regions follows the existing
  section keying.
- No virtualization, which isn't needed (about 100 memoized tiles).
- WebKit's longer total time (6–8 s) is Playwright's WebKit dispatching
  wheel events slowly; the per-frame cost is small.

14. KNOWN LIMITATIONS
---------------------
- A real trackpad and dragging the OS scrollbar were not automated.
  Trackpads produce wheel events (tested); the scrollbar is native.
- Headless browsers use 0 px overlay scrollbars. The real 15 px
  scrollbar was measured only in Electron.
- The long-task API exists only in Chromium; Firefox and WebKit were
  measured through DOM mutations and frame timing.
- WebKit (before and after BC-03.2): a new drag started within
  milliseconds of a drop is ignored. No person can do that. Noted, not
  changed.
- Hiding the panel through the View menu unmounts it, so the position
  resets. That is by design (UI-1.6), and different from collapse.
- Windows 10 only (machine limits).
