PARSER, COMPONENT LIBRARY & INSPECTOR

Date: 2026-11-12
Type: Feature implementation (provider parsing, Inspector, Canvas

1. EXECUTIVE SUMMARY
--------------------
A new "Video Embed" card (Media > Video, next to Video) creates a video
element that reuses the existing Embed element (tag "iframe").

Paste a link in the Inspector and Layoutry:
- validates it with one central, security-hardened parser;
- detects the provider;
- rebuilds a canonical https embed URL from the validated video ID only;
- stores it as one Undo step.

Providers:
- Implemented: YouTube, Vimeo, Loom and Wistia.
- Recognized, but deferred with an exact blocker message: Dailymotion
  and Twitch.

The Canvas shows a static placeholder and loads no provider iframe,
image, script or metadata, in Design or in Preview. No provider request
is made; this is tested in Chromium, Firefox, WebKit and Electron.

Interim behavior until BC-08.3:
- Preview shows the same placeholder, labelled as such.
- Export writes the empty layout box with a warning, never an iframe.
So nothing can play without the lifecycle that stops it.

Unchanged:
- Generic Embeds behave exactly as before.
- No new document field, tag or format version.
- The iframe sandbox, CSP and Electron hardening are untouched.

Three real bugs were found and fixed while testing:
- B1: YouTube's playlist path "videoseries" is 11 characters and passed
  the video-ID pattern.
- B2: a free-layout Video Embed would have used the Embed's 400x300
  default size instead of 16:9.
- B3: the placeholder repeated the provider's default title ("Vimeo
  video" twice), visually and in its accessible label.

Validation:
- Vitest: 5912 passed, 1 skipped.
- Chromium full suite: 267/267.
- Video Embed and embed-safety specs in Chromium, Firefox and WebKit:
  117/117.
- Electron full suite: 81 passed, 2 skipped, 1 known media flake that
  passes 3/3 alone.
- Typecheck, ESLint, production build and desktop build: all clean.

QA recommendation: APPROVE BC-08.2. BC-08.3 adds playback, export and
lifecycle.

- YouTube [A-Za-z0-9_-]{11}, excluding "videoseries".
- Vimeo \d{1,12}; hash [0-9a-f]{6,20}.
- Loom [0-9a-f]{32}.
- Wistia [a-z0-9]{10}.

Patterns marked [ASSUMED] in BC-08.1 (Loom 32 hex, Wistia 10 lowercase
alphanumerics, Vimeo hash length) come from the providers' own examples,
not a published rule.


4. DEFERRED PROVIDERS AND EXACT BLOCKERS
----------------------------------------
Their links are recognized, so the user gets a specific message. No
embed URL is ever built for them, and nothing is stored.

DAILYMOTION. Pending product approval.
- The only documented iframe URL is
  geo.dailymotion.com/player/{PLAYER ID}.html?video=ID.
  The Player ID belongs to the owner's Dailymotion account; Layoutry
  cannot supply it.
- No player-ID-free form was found on the official pages; the fetched
  deprecation and migration pages returned 404 on 2026-11-11.
- Only video and playlist are documented iframe parameters. Autoplay,
  loop and start are configured in the account, not the URL, so the
  approved muted-only autoplay policy cannot be enforced (autoplay off
  cannot be guaranteed).
- Dailymotion documents its iframe embed as suitable only for AMP-like
  environments.
- It requires a Referer header (same problem as YouTube in desktop and
  local-file pages).
- Message shown: "Dailymotion videos aren't supported yet. Their embed
  needs a player set up in the owner's Dailymotion account, and autoplay
  can't be controlled from the page."
- Possible future path, for approval: let users paste their own
  geo.dailymotion.com/player/{ID}.html link and accept that autoplay is
  account-controlled. That conflicts with the autoplay decision.

TWITCH. Pending product approval.
- Every embed requires parent=<exact domain of the page>.
- Unknown while designing.
- Impossible for the desktop app (app://) and local files.
- Not known at export time either.
- Live channels also autoplay by default.
- Message shown: "Twitch videos aren't supported yet. Twitch requires the
  exact website address the video will appear on, which isn't known while
  you design."
- Possible future path: a "Published website domain" setting at export
  time (BC-08.3+). It needs a product decision.

WISTIA was evaluated against its "account-specific host" concern and IS
supported:
- the embed host is the account-independent fast.wistia.net;
- public links are on Wistia's own <account>.wistia.com hosts, matched as
  exactly one DNS label under wistia.com (not a substring check);
- custom domains are refused ("Only Wistia's own links are accepted").


5. PROVIDER REGISTRY DESIGN
---------------------------
src/lib/videoEmbed/ (framework-free; shared by Inspector, Canvas and
Export like src/lib/iframeSandbox.ts):

  videoEmbedProviders.ts
    VIDEO_EMBED_PROVIDERS: one typed record per provider.
      - id, displayName, defaultTitle, embedHosts;
      - capabilities: Record<VideoEmbedCapability,
        "documented" | "unverified" | "unsupported">;
      - unsupportedNotes (why, shown in the Inspector);
      - limitations (the provider's own rules).
    DEFERRED_VIDEO_PROVIDERS (id, displayName, blocker).
    Type guards: isVideoEmbedProviderId, isDeferredVideoProviderId.
    providerSupports(id, capability).
  parseVideoEmbedUrl.ts
    The only link parser.
    Each provider has a host predicate and path rules; deferred hosts are
    in a table.
    Returns { ok, reference: { provider, videoId, hash?, startSeconds?,
    privacy? } } or a typed failure reason (and provider when known).
  buildVideoEmbedUrl.ts
    The only place embed URLs are assembled:
      - buildVideoEmbedSource: the stored canonical src;
      - buildVideoEmbedPlayerUrl: src plus playback parameters, for
        BC-08.3; nothing loads it yet;
      - readVideoEmbedSource;
      - resolveVideoEmbedSourceInput: a pasted link becomes a src;
      - withVideoEmbedPrivacy, withVideoEmbedStart.
  videoEmbedTime.ts
    Start-time parsing and formatting ("90", "1:30", "1m30s"; at most
    24 h).

Adding a provider touches:
- one registry entry;
- one parser function;
- one case in each builder;
- test rows.
The Inspector and placeholder read the matrix and need no change.
Nothing provider-specific lives in a React component.


6. URL PARSING AND NORMALIZATION
--------------------------------
- WHATWG URL parser only. ASCII tab/newline are removed first, as a
  browser does.
- A scheme-less link ("youtu.be/ID") is read as https.
- Refused, each with its own reason:
  - "//host" and "\\host" (protocol-relative);
  - http: (not-https);
  - javascript:, data:, file:, blob:, ftp: and other schemes
    (unsafe-scheme);
  - user-info (credentials);
  - an explicit port;
  - unknown hosts;
  - unsupported paths and invalid IDs.
- Hosts are matched exactly (Set lookups). The Wistia account rule is
  structural: exactly three labels, ending "wistia.com", with the first a
  valid DNS label.
- Path segments: an empty segment ("//watch") is unsupported, and one
  trailing slash is allowed. pathname keeps percent-escapes, so encoded
  slashes and payloads fail the ID pattern.
- Query values are read only for known keys: v, start/t, h, dnt, time,
  doNotTrack, t (Loom). A repeated key counts as absent (ambiguous).
  Everything else (si, utm_*, sid, feature, list, autoplay, mute, …) is
  dropped.
- Output is always rebuilt with new URL() and searchParams on the
  provider's embed host. It is deterministic:
  buildVideoEmbedSource(readVideoEmbedSource(src)) === src (unit-tested
  for every provider).
- Privacy on paste:
  - the link's own statement wins (the nocookie host, dnt=0/1,
    doNotTrack=true/false);
  - otherwise the current choice is kept for the same provider;
  - otherwise a new provider starts with privacy ON (approved default).
  The start time comes from the pasted link only.
- No network: no redirects are followed and no oEmbed lookup is made.
  Shorteners (bit.ly) are unknown hosts.


7. SECURITY VALIDATION
----------------------
Unit-tested refusals (src/lib/videoEmbed/parseVideoEmbedUrl.test.ts), all
required by the brief:
- youtube.com.evil.example;
- evil.example/youtube.com;
- evil.example/?u=youtu.be/…;
- youtube.com@evil.example and evil.example@www.youtube.com;
- user:pass@;
- a trailing-dot host;
- a Cyrillic look-alike host (punycode);
- notyoutube.com and youtube.co;
- bit.ly;
- example.com/embed/ID;
- explicit ports;
- javascript: (any case, with a tab inside);
- data:text/html, data:video;
- file:///;
- blob:;
- vbscript:;
- ftp:;
- http:;
- "//" and "\\\\";
- malformed hosts (space, NUL, an unclosed IPv6 bracket);
- empty input;
- %3Cscript%3E and "\"><script>" IDs, and the double-encoded %2522;
- an encoded slash in the path ("/embed%2FID", "ID%2F..%2F");
- a backslash or encoded-slash user-info trick;
- empty or repeated v=.
An IDNA-normalized spelling of the real host (fullwidth letters) is the
real host. That is accepted, and the output is rebuilt anyway.

Defense in depth:
- the Canvas renders NO iframe for a Video Embed;
- the export renders no iframe either (section 19);
- so in BC-08.2 a stored src never reaches an iframe anywhere.
The stored src is also always one of four fixed https embed hosts.
A hand-edited project with a hostile src in a Video Embed is read back
as "no valid video" (readVideoEmbedSource returns undefined): the
placeholder shows the empty state, nothing loads, and the schema still
refuses javascript:.


8. PRIVACY DEFAULTS
-------------------
- YouTube: www.youtube-nocookie.com by default (approved).
  - Inspector text: "It reduces tracking until the video is played; it
    doesn't remove it."
  - Marked "Not yet confirmed with this provider's player": the nocookie
    host is not on YouTube's parameters page.
- Vimeo: dnt=1 by default (approved). "Some essential cookies remain"
  (Vimeo's own wording).
- Wistia: doNotTrack=true by default. This is Wistia's documented option
  ("Asks Wistia not to track viewing sessions"). The default follows the
  approved principle of "documented privacy options where available".
- Loom: no documented privacy option, so none is invented. "Loom has no
  privacy-enhanced mode."
- The user can switch privacy mode off (one Undo step).
- Design and Preview fetch nothing from any provider: no thumbnail, no
  metadata, no player.

11. COMPONENT IDENTITY
----------------------
Rule (src/features/editor/types/videoEmbed.ts, isVideoEmbedNode):
  tag === "iframe" AND `controls` is set (true or false).

Why this field:
- A new field or tag would need project format v3 (project-format.md),
  which is forbidden.
- `controls` already exists on every node and means the same thing here:
  the player's controls.
- createVideoEmbedNode always stores controls: true.
- No Layoutry code path ever sets it on a generic Embed: the Embed
  Inspector has no Controls control, and no bulk editor touches it
  (grep-verified).

What the rule guarantees:
- An empty Video Embed (no URL) is still a Video Embed and shows the
  Video Inspector.
- Save/reopen, copy/paste, duplicate, undo and redo keep it, because
  they keep every field (unit tests plus the browser save/reopen test).
- The URL host never decides identity, so an existing generic Embed with
  a YouTube URL stays a generic Embed (unit and browser tested).
- The Video Inspector never offers a Reset that would clear controls.

Compatibility:
- Only a hand-edited file putting `controls` on an iframe would be read
  as a Video Embed.
- An older Layoutry build opens a BC-08.2 file without error (all fields
  existed) and shows a generic Embed with the canonical embed URL.

Display name: getElementDisplayName returns "Video Embed" (a user-set
displayName still wins).

13. PLAYBACK SETTINGS
---------------------
- Muted, Autoplay, Loop and Controls are the existing generic one-shot
  setters (one Undo step each).
- They are stored on the node and preserved across provider switches.
  A setting the new provider can't use is hidden and explained, and
  comes back when switching back (browser test: Loop on YouTube, then
  Vimeo, Loom, back to YouTube).
- Muted-only autoplay:
  - The Inspector says "Starts by itself only when Muted is also on."
  - With Autoplay on and Muted off: "Autoplay won't start until Muted is
    on. Layoutry only autoplays muted videos."
  - Muted is never switched on automatically (unit and browser tests).
  - The Canvas summary lists "Autoplay" only when it would start.
  - buildVideoEmbedPlayerUrl emits autoplay only when autoplay AND muted.
- Pending verification in BC-08.3: real provider behavior of every
  parameter (especially YouTube mute=1 and muted autoplay without

30. KNOWN LIMITATIONS
---------------------
- No playback anywhere yet (by design, the BC-08.3 gate). Exported pages
  contain an empty box with a warning.
- Real provider behavior is unverified until BC-08.3's opt-in live
  suite: YouTube mute and nocookie, sandbox compatibility, autoplay
  without allow="autoplay".
- Provider rules Layoutry cannot override:
  - YouTube and Dailymotion require a Referer (desktop and local-file
    pages, BC-08.1 F3/F4);
  - owners can disable embedding or restrict domains (YouTube, Vimeo);
  - Vimeo hides controls only on the owner's paid plan;
  - Loom videos must be shared with "Anyone with the link";
  - browsers block unmuted autoplay.
- ID patterns for Loom, Wistia and the Vimeo hash are taken from
  provider examples, not a published rule. A valid but unusual ID would
  be refused.
- Wistia custom-domain links are refused by design.
- Paste replaces the start time with the pasted link's own (or none).
- No Shorts-specific 9:16 default (16:9 always, per decision 12).
- Identity rides on `controls`: a hand-edited file with controls on an
  iframe becomes a Video Embed.
