1. EXECUTIVE SUMMARY
--------------------
Every provider was reproduced live in the real Electron app before
anything changed.

Baseline (BC-08.3.1 build, real network, the app's own security):
- YouTube: "Error 153 – Video player configuration error".
  - Requests leave app://layoutry/ with NO Referer, because Chromium sends
    none from a custom scheme.
- Vimeo: player UI loads, never plays; Vimeo shows "Rights issue — We're
  having trouble authorizing playback".
- Wistia: plays (muted autoplay).
- Fullscreen: unavailable (no allow= in desktop since BC-08.3).

Root causes (each separated by experiment, section 4):
- YouTube: a missing Referer. That is all; it is not a sandbox, codec or
  permission problem.
- Vimeo: the Widevine DRM component, which stock Electron does not ship.
  - Vimeo's own official embed, unsandboxed and with every permission it
    asks for, fails identically in Electron.
  - Fixing it means adding a DRM component (e.g. a Castlabs Electron
    build): a product decision (section 32). Not done.
- Fullscreen: the deny-all permission handler (BC-08.1 F2).

Implemented, all bound to a verified FRAME, never to a hostname:
1. Video Embed frame authorization.
   - The editor names each player iframe it mounts with a random
     ly-video-<128-bit hex> token and registers {token, provider} over IPC
     before the iframe gets its src. It unregisters on unmount.
   - The main process authorizes a frame only if ALL hold, checked from
     its own frame tree:
       - the frame is a direct child of the main window's top frame;
       - its current name is a registered token of that window;
       - its URL is on that provider's exact https player origin.
   - Generic Embeds are never named or registered.
2. Referer: Referer: app://layoutry/ — Layoutry's TRUE origin, no website
   claimed.
   - Added only to an authorized player's own document request (a
     subFrame navigation), only when no Referer exists.
   - Implemented with a webRequest listener filtered to the exact player
     origins.
   - YouTube then plays in Electron: live, muted autoplay at 7.6 s.
3. Fullscreen: the deny-all permission handler gains ONE exception.
   - A "fullscreen" request is granted when every frame showing the
     requesting URL is an authorized player of the main window.
   - Ambiguity (a generic Embed at the same URL) is denied.
   - Everything else stays denied, permission checks included.
4. Fullscreen lifecycle:
   - Escape leaves element fullscreen (Electron doesn't do this itself).
   - A player that is fullscreen when it should go away is kept for that
     moment, leaves fullscreen, then is removed.
   - The main process restores the window if the fullscreen player's
     registration ends while the window is still in element fullscreen.

Electron results (live): YouTube plays; Wistia plays; Vimeo is blocked
(DRM, documented); a generic Embed showing the same YouTube video still
gets Error 153 and no fullscreen, so no privilege leaks to it.

Deterministic Electron tests (fake players on the exact provider hosts):
- authorized fullscreen, and Escape;
- denial for generic Embeds, unregistered, renamed, stale and ambiguous
  frames;
- revocation on hide, Preview exit and project switch;
- reduced motion.

4. ROOT CAUSES OF FAILURES
--------------------------
The categories the brief asks to separate:
- Provider-side restriction: none hit with these videos.
- Electron security restriction: fullscreen only (deny-all handler).
- Network: none.
- Media codec/DRM: Vimeo.
  - In the Vimeo frame, H.264 and AAC are supported, and ClearKey EME
    succeeds, so the approved encrypted-media Permissions Policy works.
  - com.widevine.alpha is "Unsupported keySystem", and Vimeo then reports
    "Rights issue".
  - Control: Vimeo's own official embed code, no sandbox, its full allow

    cause is not Layoutry's sandbox or permissions.
  - In BC-08.3.1 the same video played in Edge, which ships Widevine.
- Missing Referer: YouTube.
  - Injecting Referer: app://layoutry/ only on the player's own document
    request made it play.
  - document.referrer stays empty, and that is fine: YouTube checks the
    request.
- Sandbox/Permissions Policy: none. The BC-02.3 sandbox is unchanged,
  and all working players run under it.


5. ORIGIN / REFERER ANALYSIS
----------------------------
- The renderer origin and the Preview document origin are both
  app://layoutry. It is a registered standard, secure custom scheme
  (ADR-0002), not file://.
- Players are cross-origin subframes. Their navigation request has no
  Referer, because Chromium never derives one from a non-HTTP(S) origin.
  The explicit referrerpolicy is irrelevant here: there is nothing to
  send.
- YouTube requires one (RMF terms: "provide identification through the
  HTTP Referer"; desktop clients must set it themselves). Empirically it
  ACCEPTS app://layoutry/.
- Chosen value: app://layoutry/, the editor's actual origin. It is not a
  spoof: no website or domain Layoutry doesn't control is claimed. A
  Layoutry-owned https identity domain could be used later (section 32);
  none exists today.
- Scope: one listener (session.webRequest.onBeforeSendHeaders),
  registered with URL filters for the exact player origins only.
  - It acts only for the main window, only on resourceType "subFrame",
    only for an authorized player frame (verified in the probe:
    details.frame is the navigating iframe and carries its name), and
    only when no Referer exists.
  - Every other request is untouched: editor, generic Embeds, player
    sub-resources, media, analytics.
  - No local path, project location or app state is sent.
- Redirects: the provider's own redirects stay in the sandboxed frame;
  will-frame-navigate still allows only http/https and about:blank.
- Exported pages: unchanged. No Referer is forged in exports. Hosting on
  https is still required for providers that need a Referer (BC-08.3,
  file:// limitation).

8. FULLSCREEN AUTHORIZATION DESIGN
----------------------------------
- Electron 44's PermissionRequest exposes only { requestingUrl,
  isMainFrame }: no frame object. A hostname check would therefore treat
  a generic Embed and a Video Embed showing the same page as the same.
  That is not acceptable.
- Instead (desktop/security/videoEmbedFrames.ts):
  - The renderer registration is only a claim. It must name a frame the
    main process then finds itself, via
    webContents.mainFrame.framesInSubtree, in the right place and on the
    right origin.
  - isFullscreenRequestAuthorized grants only when:
    - the request is not from the top frame;
    - at least one frame shows requestingUrl;
    - EVERY frame showing it passes authorizedPlayerProvider.
  - So an ambiguous URL is denied.
- The registry is per window (webContents id).
  - Payloads are strict {token, provider}; the token pattern is
    ^ly-video-[0-9a-f]{32}$.
  - The provider must be one of youtube/vimeo/loom/wistia.
  - Duplicate tokens are refused; there is a cap of 256 per window.
- IPC: two new channels, layoutry:video-embed:register-frame and
  :unregister-frame.
  - Both use the existing isTrustedSender check: only the main window's
    top frame on app://layoutry/.
  - The preload has two string-checked functions,
    registerVideoEmbedFrame and unregisterVideoEmbedFrame.
  - The bridge apiVersion is now 4. Nothing else is exposed.
- Renderer (canvas VideoEmbedFrame → VideoEmbedPlayerFrame):
  - a token from crypto.getRandomValues (128 bits);
  - name={token};
  - the src is set only after register() resolves, so the first request
    is already recognisable;
  - a failed registration leaves the frame without a source (fail
    closed);
  - unregister on unmount.
  - Browsers: no name, no registration (getDesktopVideoEmbedFrames
    returns null).


9. FRAME IDENTITY VERIFICATION
------------------------------
What Electron actually exposes was verified with probes (deleted):
- A fullscreen request arrives as permission "fullscreen" with
  requestingUrl = the frame's URL and isMainFrame=false. The frame tree
  shows each frame's name and URL.
- Granting enters window fullscreen; exiting restores it.
- A frame can rename itself (window.name = …); the main process then sees
  the new name. Authorization therefore fails closed for a renamed frame.
- For a subframe navigation, webRequest's details.frame is the navigating
  iframe (its name is visible, its parent is the main frame), not the
  editor.
- A nested frame or a frame on another origin fails the checks.


10. AUTHORIZATION REVOCATION
----------------------------
Authorization ends when:
- Preview closes, the embed is hidden, or an ancestor is hidden: the
  iframe unmounts, so the token is unregistered.
- The source or provider changes: the player is keyed on its
  configuration, so it remounts with a new token, and the old one is
  unregistered.
- The project changes or the editor unmounts: unmount, so unregister.
- The window reloads (main-frame cross-document navigation), its renderer
  is lost, or it is destroyed: registry.clearOwner.
- The frame navigates to an unapproved destination: the origin check
  fails at use.
- The frame renames itself: the name check fails at use.
- Tokens are random and never reused. A removed player's token is
  refused: a frame carrying a stale name is tested and denied.
- No transfer: a new registration never authorizes an old frame (unit),
  and a generic Embed cannot learn a token (frame names are not readable
  cross-origin).

16. HIDDEN-STATE LIFECYCLE
--------------------------
- Ancestor hidden while fullscreen: the player leaves fullscreen first,
  then is removed. The window returns to normal.
- Shown again: a fresh player with a new name, which can enter
  fullscreen again (Electron test).
- Fullscreen release (canvas VideoEmbedFrame + useFullscreenElement):
  - a player that is the fullscreen element when it should go away is
    kept mounted for that moment;
  - document.exitFullscreen() is called;
  - the player unmounts when fullscreenchange reports the exit.
  - Removing a fullscreen iframe abruptly left Chromium/Electron state
    stale: the window stayed fullscreen, or the next request never
    completed (diagnosed, section 31).
- Main-process safety net: if the granted player's registration ends
  while the window is still in element fullscreen, setFullScreen(false)
  is called.

31. OPEN DEFECTS
----------------
E1  Electron fullscreen exit race. LOW: not reachable by a user.
    - If element fullscreen ends within ~50 ms of entering, Electron 44
      leaves the window but never emits leave-html-full-screen. Its
      element-fullscreen state then stays set, and the next
      requestFullscreen never completes.
    - Reproduced only by a scripted hide 46 ms after entering.
    - A person cannot hide or exit within that time: the player covers
      the editor, and Escape is handled after the transition.
    - Tests use a realistic 1 s pause (watchFullscreen, documented).
    - Possible follow-up: an Electron upgrade or upstream report.
E2  Generic YouTube Embeds in the desktop app show Error 153. That is by
    design: no privileges for generic Embeds. Users should use Video
    Embed.
Carried: D3 (WebKit stale aspect-ratio after resize), D4 (native-video
reduced-motion rule), D5 (Loom test video), PRJ-K1.
