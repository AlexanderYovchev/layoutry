LAYOUTRY — BC-04.2: INTERACTION CONTROLS GUIDANCE & TARGET SELECTION
=====================================================================
Date: 2026-11-08
Type: Targeted UX implementation + behavioral correction + regression tests
Base: HEAD 27a33f4 (BC-04.1 report untracked, unchanged)
Status: implemented and validated; NOT committed


1. EXECUTIVE SUMMARY
--------------------
The Interactions section of the Inspector now explains itself, asks for an
explicit target, and fails safely:

- A one-line description opens the section: what an interaction does, where
  to set it up, and how to test it (Preview), with exported pages behaving the
  same.
- Initial state, Action and Target each have a help icon. It is the
  existing Inspector help pattern. Each control is described by its help
  for screen readers, the icon is reachable by Tab, and Escape now hides
  the tooltip.
- Two notes appear only when they apply:
  - a keyboard note, for click interactions on elements keyboard users
    can't activate;
  - an "initially hidden" note, while Initial state is Hidden.
- "Add Interaction" no longer picks the first element on the page (U1).
  - The new row shows "Select an element…" and does nothing until a
    target is chosen.
  - Choosing it adds the complete interaction as one Undo step.
  - An unfinished interaction never reaches the document, Preview, the
    export or the saved file.
- Target names no longer show internal ids:
  - duplicates are told apart by their text ("Paragraph — Details"), or
    by position ("Section (1 of 2)");
  - the selected element itself is marked "(this element)".
- A missing target shows "The target was deleted. Choose another element."
  It is marked invalid, keeps the binding unchanged, and is repaired by
  choosing a replacement.

Two real defects were found and fixed along the way:
- D1, pre-existing, HIGH:
  - Pasting a copied trigger after its target was deleted (or undone)
    inserted a binding to a missing element.
  - Saving, autosave snapshots and Export Code validation all reject
    such a document ("An interaction targets element …, which does not
    exist"). The project then silently could not be saved.
  - Paste now applies the existing rule "deleting a target removes the
    interactions aimed at it".
  - Proven by tests that fail on HEAD.
- D2, found live, MEDIUM:
  - At the Inspector's narrowest width (260 px), help tooltips (192 px
    wide) ran up to 10 px past the panel and window edge.
  - This affects every Inspector help icon, not only the new ones.
  - The help icon now measures its tooltip and shifts it back inside the
    Inspector.

No schema, file-format, export-output or Preview-runtime change.

Recommendation: CLOSE BC-04 (section 17).

3. HELP-ICON IMPLEMENTATION
---------------------------
Reuses the existing InspectorPropertyRow `help` prop (Tooltip + HelpCircle).
No tooltip library and no dependency were added.

The icon button was extracted from InspectorPropertyRow into
InspectorHelpButton.tsx, unchanged in look, with three additions:
- Description: a new optional `helpId` on InspectorPropertyRow renders a
  hidden copy of the help text with that id.
  - The control references it with aria-describedby. Initial state,
    Action and Target are each read with their help.
  - A hidden copy is used because a button's aria-label is not reliably
    used as a description (jsdom's computation ignores it).
- Escape (WCAG 1.4.13) hides the tooltip while it shows on hover or focus,
  without moving focus.
  - The Escape is consumed. Otherwise the editor's own Escape would clear
    the selection and empty the Inspector.
  - A second Escape is the editor's again.
  - If a text field has focus while the pointer rests on an icon, the
    tooltip hides but the field keeps its Escape (e.g. numeric fields'
    restore).
  - The tooltip returns once pointer and focus have both left.
- Containment (D2): on hover or focus, the tooltip is measured against its
  nearest scrolling ancestor, the Inspector's content area without its
  scrollbar.
  - It is shifted sideways to stay 4 px inside (inline translateX: a
    runtime-measured value).

Tooltip.tsx gained three optional props: `suppressed`, `offsetX` and
`tooltipRef`. All default to the old behavior, so every other tooltip is
unchanged.

The help icon was already a focusable button named by its text, so help
was never hover-only. Every existing InspectorPropertyRow help (15 rows)
gains the Escape and containment fixes for free. Their markup is otherwise
identical.


4. CONDITIONAL GUIDANCE BEHAVIOR
--------------------------------
Keyboard note:
- When it shows: the element has at least one interaction (finished or
  being set up) and its tag isn't natively operable.
- Natively operable tags: button, a, input, select, textarea.
- The rule (NATIVELY_OPERABLE_TAGS / isKeyboardOperableTrigger) moved
  from the export's buildExportBehaviors into
  editor/utils/triggerAccessibility.ts. The Export dialog's
  "non-operable-trigger" warning and the Inspector note now use the same
  function.
  - A unit test runs the export over 11 tags and asserts the warning set
    equals the rule.
- Rendered semantics checked:
  - links always export with an href (default "#"), so they are focusable;
  - nodes have no "disabled" field, so no tag is conditionally inert.
- It disappears when the last interaction is removed or a draft is
  discarded.
- No tabIndex, role, key handler or synthetic button behavior was added.

Initial-hidden note:
- Below Initial state, only while it is Hidden.
- Informational style: the existing px-0.5 text-[11px] text-fg-secondary
  note, no warning color.
- Also part of the select's description.
- Visibility behavior is unchanged.

Description: always present when the section is open. It costs no space
while collapsed (the section still starts collapsed for unconfigured
elements).


5. TARGET SELECTION: BEFORE AND AFTER
-------------------------------------
Before (HEAD):
- "Add Interaction" immediately created { action: toggle, targetId:
  candidates[0] }, the first element of the page.
- On the starter page, the hero heading targeted its own Section, so one
  Preview click hid it.

After:
- "Add Interaction" adds an unfinished row:
  - Action = Toggle;
  - Target = "Select an element…" (a disabled, selected placeholder),
    aria-required;
  - described by "Choose a target to finish…".
  - Focus moves to the Target select, and the Add button is hidden while
    the row is unfinished.
- Choosing a target calls addInteraction once, with the chosen Action.
  - It is one history entry, and focus stays on the new row's Target.
- The trash button discards an unfinished row without touching history.
  Focus returns to Add Interaction.
- An unfinished row is dropped when:
  - another element is shown in the Inspector;
  - Preview starts (the Inspector is replaced in Preview);
  - the Inspector unmounts.
- Removing a finished interaction moves focus to Add Interaction (or to
  the unfinished row's Target, if one is open). Before, focus fell to
  <body>.
- Several interactions stay independent; a test proves a new one never
  changes an existing one.

Target labels (U5), limited to this selector:
- Names come from getElementDisplayName (the Structure names).
- Repeated names get the element's text, Structure's "Option — Bulgaria"
  style. Texts over 24 characters are cut with "…".
- Names still shared after that get "(n of N)" in document order.
- The selected element is marked "(this element)".
- Starter page: Section (1 of 2), Heading (this element), Paragraph,
  Primary Button, Section (2 of 2), Image.
- The Target select is capped at 160 px (max-w-40), so long names can't
  widen the panel.


6. SCHEMA AND PERSISTENCE IMPACT
--------------------------------
None. Why no schema change was needed:
- The schema requires targetId to match NODE_ID_PATTERN.
- checkDocumentIntegrity, run on open, save and recovery snapshots,
  rejects a binding whose target doesn't exist.
- So an empty or null target can't be represented safely without a
  .layoutry format change.
- The unfinished interaction is therefore Inspector-only state, and the
  document only ever holds complete bindings.

Consequences:
- Existing projects open unchanged. Valid targets are kept exactly
  (tested: unit "keeps an existing interaction's target exactly as saved";
  e2e "an existing project's interactions open unchanged").
- Nothing to migrate; older builds read new files as before.
- Known limitation (section 15): an unfinished row is not saved and is
  lost on selection change or Preview.

The paste fix (D1) keeps the existing invariant that editor documents
always pass checkDocumentIntegrity. Before the fix, that invariant could
be broken by an ordinary copy → delete → paste.


7. MISSING-TARGET HANDLING
--------------------------
How a binding to a missing element could arise:
- Deleting or cutting a target already removed the bindings aimed at it
  (removeInteractionsTargeting, the established product rule).
- Opening a file with a dangling binding is rejected.
- The one path that produced one was paste (D1):
  - the clipboard keeps a copied trigger's external target id unchanged;
  - so copy button → delete its panel (or Undo past the panel's creation)
    → paste inserted a binding to nothing.
  - Measured: checkDocumentIntegrity then reports "An interaction targets
    element "panel-1", which does not exist", which makes serializeProject
    throw ("callers should treat that as a bug").
  - Fixed: pasteClipboard runs the new pure command
    removeInteractionsWithMissingTargets on the result, inside the same
    single history entry.
  - Bindings whose target still exists, and self or internal targets, are
    kept. Undo removes the paste in one step.
- Preview's executor and the export already skip missing targets. That is
  unchanged.

Inspector display (defensive, for any remaining path):
- The select shows the disabled "Missing target" option and is
  aria-invalid.
- It is described by its help and by the error.
- The error is role="alert": "The target was deleted. Choose another
  element."
- The binding is never deleted or retargeted by the Inspector.
- Choosing a replacement repairs it, and the error disappears.
- The old empty "Missing target" option was selectable in principle and
  could have written targetId "". It is now disabled, and "" is ignored.


8. ACCESSIBILITY VERIFICATION
-----------------------------
Measured in Chromium, Firefox, WebKit and Electron unless noted:
- Help icons:
  - focusable buttons named by the help text;
  - the tooltip shows on hover and on keyboard focus;

  as the Autoplay and Protection notes. No new colors.
- Reduced motion: nothing new animates. The tooltip keeps its existing
  150 ms opacity fade. Offsets are applied instantly.
- No unsupported ARIA: role="tooltip" was deliberately not added. The
  tooltip stays aria-hidden, as before.
- Narrow width (260 px Inspector minimum, Chromium/Firefox/WebKit):
  - every note, select and help icon stays inside the section, with no
    sideways scrolling;
  - all 5 help tooltips stay inside the Inspector (this failed before the

- Visual review (Chromium screenshots, temporary probe, deleted): open,

15. KNOWN LIMITATIONS
---------------------
- An unfinished interaction lives only in the Inspector:
  - it is not saved;
  - it is discarded when another element is selected, on entering
    Preview, or with Escape (which clears the selection).
  - This is deliberate (no schema change), but a user could lose a
    half-set-up row.
- The Initial state "Hidden" is still not marked on the Canvas or in
  Structure (U3 visual). Only explained in the Inspector; a design
  question for a later checkpoint.
- Target names are clearer but still generic for unnamed, textless
  elements ("Section (1 of 2)"); there is no Canvas picker.
- Escape for a tooltip shown only by hover is caught at window level while
  the pointer rests on the icon. In a text field, the field keeps its
  Escape.
- Help remains a tooltip.
  - Touch: tapping focuses the icon, which shows it.
  - Screen readers: the help is the button's name and the control's
    description.
- WebKit on this machine is frame-starved under parallel load (section
  11). The new spec is reliable when run serially there.
- No study with real users; copy follows the approved BC-04.1 proposal.
- Windows 10 only, light theme only, as in earlier checkpoints.
