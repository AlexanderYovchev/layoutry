1. EXECUTIVE SUMMARY
--------------------
BC-07 was re-verified end to end. That covered real behaviour in Chromium,
Firefox, WebKit and Electron, a cross-engine security matrix, a parity
matrix at five widths, document immutability, stress and resource
lifecycle, and real-folder failure recovery.

Three real defects were found and fixed:

BC07-A1 (Medium): damaged images passed upload validation in Firefox and
WebKit.
- A PNG with perfect structure but garbage compressed image data was
  accepted in Firefox (shown blank) and in WebKit (stored, shown broken).
- WebKit also accepted a GIF with garbage image data.
- Cause: those engines' createImageBitmap is lenient.
- Fix:
  - PNG image data is now inflated with the browser's own zlib
    (DecompressionStream) and must produce the bytes its header needs;
  - every upload must also decode through an <img>, the path the Canvas,
    Preview and export use. Its object URL is always revoked.
- Now refused in all three engines.

BC07-C1 (Medium): a late upload overwrote newer intent.
- If the user typed a Source URL (or undid that image's source) while an
  upload was still reading, the finished upload silently replaced it.
- Now the commit is refused unless the Image still has the source it had
  when the upload started. The user gets an alert, and nothing changes.

BC07-G1 (High-priority audit item): the invalid-embedded-image fallback.
- BC-07.3 kept an invalid embedded raster image inline, with a warning,
  in a Separate files export.
- That is inert: no browser runs script from an image source, which is
  proven below.
- But it shipped a broken image in a "portable" site, which fails the
  brief's condition 4 (no broken or misleading export).
- Now:
  - Separate files: an export-blocking error naming the element and how
    to fix it.
  - Single HTML file: the source is kept exactly as authored (as before
    BC-07), with an accurate warning that it will show as a broken image.
- SVG, AVIF and BMP data URLs keep their pre-BC-07 behaviour. An SVG
  carrying onload and <script> was proven never to run, in the editor and
  in the exported page.

Validation:
- typecheck (web and desktop) and ESLint are clean;
- Vitest: 5710 passed, 1 skipped;
- Chromium full suite: 257/257;
- Firefox and WebKit BC-07 specs: 54/54;
- Electron full suite twice, with the rebuilt bundle: 80 passed and 2
  skipped each time;
- production and desktop builds succeed.

Recommendation: CLOSE BC-07.

6. PROJECT-SIZE BOUNDARY TESTS
------------------------------
The preflight uses documentFitsProjectFile:
- formatProjectFileText, the very function serializeProject writes with;
- worst-case metadata;
- against the same maxFileCharacters that parseProjectFile enforces;
- the desktop write limit is the same 16 Mi characters.

Tests (commitImageUpload, projectSaveLimit, store and e2e):
- small image: ok;
- one about 5 MB: ok (e2e near-limit);
- several up to the limit, then one more: refused with no change (unit
  and e2e, 3 × 4.8 MB);
- large replaced by smaller: ok, and the project shrinks;
- small replaced by larger past the limit: refused;
- replacement is measured as a replacement;
- duplicate, copy/paste and container paste of large images: refused with
  a notice past the limit (unit and e2e);
- cut+paste: allowed;
- near the limit, every state Undo and Redo can reach still saves
  (verified state by state);
- the project grows while a file is read: the late upload is measured
  against the latest document and refused;
- exact boundary: the largest payload that fits saves with the longest,
  most-escaped name; one character more doesn't fit.

Critical invariant holds: no BC-07 operation (upload, replace, paste or
duplicate of embedded data) can create a state the save path rejects
because of the image data it introduced.

Outside BC-07 (pre-existing, documented in BC-07.2): data URLs typed into
the Source URL or Background image fields, and Navigation "Add link"
copying a link's background (BC-06). Save still refuses an oversized
project with its existing error.

10. INVALID EMBEDDED IMAGE FALLBACK AUDIT (HIGH PRIORITY)
---------------------------------------------------------
What reaches packaging:
- only image-context sources (<img src>, <video poster>, CSS
  background-image) that the URL policy already accepts as
  data:image/(png|jpeg|jpg|gif|webp|avif|bmp|x-icon|svg+xml);
- data:text/html and other types are dropped by the URL policy before
  that, with "unsafe-url".
- An upload can never produce invalid data. Invalid data can only come
  from older or hand-edited project files, or text typed into a URL
  field.

Can anything execute? No.
- Browsers never run script from an image source, SVG included (scripts
  and onload are disabled in image documents).
- Proven in e2e (all engines) with an SVG carrying onload plus <script>,
  and with an HTML/script payload declared as PNG, in:
  - the editor Canvas;
  - Preview;
  - the downloaded Single HTML file opened from disk.
  The window flag the payloads would set stays unset.
- The fallback bypasses no upload restriction: it never creates files.
  Rejected data now creates no file in any mode.

Old behaviour (BC-07.3): Separate files kept invalid raster data inline,
with a warning. That was inert, but it shipped a broken image in a
"portable" site (fails condition 4). FIXED (BC07-G1).

New behaviour, per case. Unit test "invalid and unusual embedded sources
(BC-07.4 fallback audit)", plus e2e:

| Case | Separate files | Single HTML file |
|---|---|---|
| Valid legacy raster PNG | EXTRACTED (assets/image-001.png) | embedded |
| JPEG declared as PNG | EXTRACTED as .jpg + info diagnostic | embedded |
| Malformed base64 (declared PNG) | BLOCKED: error | PRESERVED + warning |
| Truncated JPEG | BLOCKED | PRESERVED + warning |
| Truncated WebP | BLOCKED | PRESERVED + warning |
| HTML/script declared as PNG | BLOCKED | PRESERVED + warning |
| Oversized decoded data (>16 MiB) | BLOCKED | PRESERVED + warning |
| SVG data URL with script | PRESERVED (inert) | PRESERVED (inert) |
| Unsupported format (BMP) | PRESERVED | PRESERVED |
| HTML data URL | dropped by URL policy (warning) | dropped by URL policy (warning) |

Messages:
- BLOCKED: "The embedded image in src can't be exported as a file because
  <reason>. Replace or remove this image, then export again." The dialog
  shows "This design can't be exported until the errors below are fixed"
  and every Download/Save button is disabled.
- PRESERVED + warning: "…isn't a valid image (<reason>). It was exported
  as it is, and browsers will show it as a broken image. Replace or
  remove this image."

The Single HTML file keeps legacy content as it always was; it stays one
self-contained file, and the user is told accurately. The SVG, AVIF and
BMP preservation is the pre-BC-07 policy, safe as shown above.

Documented in docs/architecture/export-engine.md.

26. REMAINING LIMITATIONS
-------------------------
- Export can't decode images (it is synchronous), so a legacy data URL
  that is structurally valid but has a garbage body (only possible from a
  hand-edited file, or a pre-BC-07.4 upload in Firefox/WebKit) is packaged
  byte-for-byte. It renders exactly as it did on the Canvas.
- A PNG+HTML polyglot is accepted as the valid PNG it is. It is inert in
  every image context.
- Not guarded (pre-existing): data URLs typed into the URL fields, and
  BC-06 Add link copying a background data URL. Save refuses an oversized
  project with its existing error.
- File names are shown for the session only. Format 2 has no field for
  them, by decision.
- The desktop export writes a folder, with no ZIP. Images from an older
  export with more images stay unused in assets/; Layoutry never deletes
  files it didn't write in that export.
- The uncapped Undo history keeps replaced images in memory, as before.
- Windows has no atomic multi-file replace: staged renames with rollback.
