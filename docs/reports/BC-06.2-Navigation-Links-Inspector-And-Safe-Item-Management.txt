--------------------

  - count line;
  - one row per direct link (label, destination, Move up, Move down,
    Remove);
  - "Add link".
- New links:
  - copy the last link's styling;
  - get the text "New link", destination "#" and a fresh id;

3. NAVBAR ELIGIBILITY RULES
---------------------------

Rule: the section shows for a single selected element whose tag is `nav`.
Its "navigation links" are the nav's DIRECT `<a>` children, in document
order (isNavigationLinkContainer / getNavigationLinks in
src/features/editor/commands/navigationLinkCommands.ts).

Why this rule:
- Navbars carry no marker after insertion (1.15.6.3 decision). Adding a
  persisted type just for detection was forbidden.
- Requiring existing links would hide the section on a nav whose links
  were all removed. The brief requires the empty case to work ("Do not
  crash or assume a last link exists").
- The rule never assumes a nav contains only links (mixed content, below).

Covered: Basic / Centered / CTA Navbars, Breadcrumbs, Pagination, Sidebar
Navigation, the Simple Footer's nav, and a blank HTML Nav.

Mixed content:
- Non-link children (a CTA Button, Breadcrumbs' "/" Paragraphs,
  Pagination's Previous/Next Buttons, a nested Container) are never
  counted, listed, moved or removed, and keep their exact index.
- Links nested inside a Container within the nav are not direct links and
  are not listed. This is a documented limitation (BC06-C2).

Multi-selection: not shown. The multi-selection Inspector is a separate
summary, the same rule the List/Table/Select sections follow.

5. ADD LINK BEHAVIOR
--------------------

Store action addNavigationLink(navId) (useEditorStore.ts):
1. Finds the nav and its direct links.
2. Builds the new link: createNavigationLink(lastLink).
   - It is passed through resolveFreeDestinationPlacement, so a
     Free-layout nav places it like any insertion.
3. Inserts it with insertNavigationLink:
   - right after the last direct link;
   - first, when the nav has no links (before a CTA);
   - refused (same document returned) at 12 links, for a non-nav id, or
     for a non-link node.
4. Pushes one history entry. A refused add pushes none.
5. Leaves the selection unchanged (the nav), so Add can be pressed
   repeatedly.

New link: tag `a`, id `a-<8 hex>` (generateNodeId), text "New link",
href "#".

Empty nav: uses createNavbarLinkNode("New link"), the same starter link
the Navbar presets use (newly exported from navigationCompositions.ts),
not the generic blue Link.

----------------------

  shape, boxShadow, filters, display, aspectRatio, sizeConstraints,
  transition, transform, className;

Verified:

7. MAXIMUM-COUNT ENFORCEMENT
----------------------------

- canAddNavigationLink: under 12 direct links (non-link children are not
  counted).
- Enforced at two levels:
  - the command refuses (no document change, no history entry);
  - the UI sets aria-disabled on "Add link", adds the title tooltip, and

8. REMOVAL BEHAVIOR
-------------------

Store action removeNavigationLink(navId, linkId):
- Removes exactly that node, and only if it is a direct `<a>` child of
  that nav.
  - A CTA id, another nav's link or an unknown id is a no-op with no
    history entry.
- Goes through commitStructuralEdit (section 13), in one write:
  - interactions targeting the removed link are removed;
  - interactions on other nodes survive;
  - a binding ON the removed link leaves with it.
- One history entry. Undo restores the node exactly (id, label, href,
  styles, metadata, position) and the removed bindings, because history
  entries are whole-document snapshots.
- Selection stays on the nav. It falls back to the nav if a removed node
  had been selected.
- No confirmation dialog. This matches the Delete key: explicit,
  one-at-a-time, one Undo step.
- Removing every link is allowed. The section then shows "No links yet"
  and "Add link".

Focus after Remove: the next row's Remove button, else the previous row's,
else "Add link".


9. REORDERING BEHAVIOR
----------------------

Store action moveNavigationLink(navId, linkId, "up" | "down").

Policy: swap the link with its neighbouring LINK. Each of the two nodes
takes the other's slot.
- Every non-link child keeps its exact index.
- For adjacent links (all Navbar presets) this is identical to moving one
  position.
- Breadcrumbs: Home ↔ Products leaves both "/" separators in place.
  Moving among ALL children would have produced "/ Products Home /", a
  broken trail.
- Navbar with CTA: the last link cannot move past the CTA, so its Move
  down is disabled. Moving among all children would leave the list
  visibly unchanged after the click.

Why not moveElement (useMoveElement / moveNode):
- It moves one node relative to a sibling, so a swap would take two
  writes. It also re-selects the moved node.
- The swap is one small immutable command that reuses the same node
  objects: ids, styles and interactions are untouched, and nothing is
  recreated.

Other guarantees:
- Disabled at the ends (real `disabled`).
- A no-op pushes no history entry.
- One entry per move. Undo and Redo restore and reapply the order.
- Focus stays on the same control of the moved row. When the row reaches
  an end, focus moves to its other Move button.

- Wrap is not already on.

12. INTERACTION-REFERENCE BUG ROOT CAUSE (BC06-D1)
--------------------------------------------------

- setListItemCount, setOptionCount, setTableColumnCount,
  setTableBodyRowCount and setTableHeader/Footer/CaptionEnabled each
  dropped children inside their own command (`slice` / `filter`).
- Their store actions pushed the result directly. Unlike deleteSelection
  and cutSelection, they never called removeInteractionsTargeting.
- A Show/Hide/Toggle binding aimed at a trimmed node was left dangling.
- checkDocumentIntegrity then rejected the document, so serializeProject
  threw and Save, autosave and recovery failed ("This project couldn't be
  written … An interaction targets element …, which does not exist").

Additionally affected, beyond BC-06.1's list: the Table Caption toggle (a
caption is a valid target).

Audited and unaffected:
- setElementTag only renames, never drops children.
- setSelectSelectedOption removes nothing.
- SVG object removal: vector objects are not interaction targets.
- Paste already used removeInteractionsWithMissingTargets; Delete and Cut
  already used removeInteractionsTargeting.


13. SHARED DELETION CLEANUP IMPLEMENTATION
------------------------------------------

- interactionCommands.removeInteractionsForRemovedNodes(before, after):
  - collects the ids that existed before and are gone after, at any depth;
  - passes them to the existing removeInteractionsTargeting, the same
    primitive and policy the Delete key uses;
  - returns `after` unchanged when nothing was removed.
- useEditorStore.commitStructuralEdit(state, edited, fallbackSelectionId):
  - applies that helper in the same write;
  - prunes a stale selection to the container;
  - pushes ONE history entry;
  - returns `{}` for a no-op.
- Used by all 7 count/toggle actions and by removeNavigationLink.
- Design choice: a before/after diff rather than computing the removed ids
  per command. It needs no changes to the six commands and covers nested
  descendants (a removed row's cells) and any future removal path
  uniformly.
  - Cost: two id walks per structural edit, comparable to Delete's own
    walk.
- deleteSelection and cutSelection were left unchanged. They already use
  the same primitive, so refactoring them was out of scope.
- No change to the interaction system, its behaviour or its types.
