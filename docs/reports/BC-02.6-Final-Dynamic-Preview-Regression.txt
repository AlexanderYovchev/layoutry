1. EXECUTIVE SUMMARY
--------------------
All eight BC-02 defects (B1–B8) are still fixed. They were checked on the
committed tree, each on its own and in combination.

New evidence comes from one new spec, e2e/bc02-final-regression.spec.ts,
which adds three things:
- A component matrix. All nine built-in interactive components are
  driven step by step: by click, repeated clicks, Enter, Space, Escape
  and a Tab walk. At every step one full runtime snapshot from Preview
  is compared with the same snapshot from the exported page.
- An 18-step combined workflow, run under both reduced-motion settings.
  One project goes through Design → Preview → Design → Preview → Export
  → save → reload → reopen. Document, history and storage integrity are
  checked along the way.
- A repeated-session lifecycle measurement over 25 Preview sessions
  (Chromium, Chrome DevTools Protocol).

It passes in Chromium and Firefox. In WebKit it passes everything except
the media steps. Those were skipped with an explicit "not verified" note:
the WebKit build Playwright uses on Windows still cannot load any media,
and this run confirmed that again.

Full suites (exact counts, and where each failure comes from, in
section 13):
- Typecheck, lint and production build: clean.
- Vitest: 5256 passed, 1 skipped.
- Chromium: 183/183 passed.
- Electron: 63 passed, 1 failed, 2 skipped. The failure is an
  intermittent window-close test, and it fails on the pre-BC-02 build as
  well.
- Firefox: 178 passed, 4 failed. Three of the failures fail identically
  on the pre-BC-02 commit. The fourth is a BC-02.5.1 media test that
  passed in the first full run and 3/3 times in isolation (load
  flakiness).
- WebKit: 159 passed, 23 failed.
  - 12 failures are the known media limitation.
  - 8 also fail on the pre-BC-02 commit.
  - 3 pass when rerun (flaky).
- No failure in any environment comes from BC-02 code.

New findings:
- No new defect in B1–B8.
- No high- or medium-severity issue.
- One low-severity accessibility observation, already a documented
  limitation. When a control hides its own container (the Toast's Close
  button, the Alert's Dismiss button), focus is not moved anywhere
  useful. Depending on the browser it falls to the page or stays on the
  now-hidden button. This happens in both runtimes and is not a BC-02
  regression.

Recommendation: CLOSE BC-02 (section 17).

4. INTERACTIVE COMPONENT MATRIX
-------------------------------
Inventory (from the factories in src/features/editor/factories):
- Dropdown (buttonCompositions)
- Collapsible, Tabs, Modal, Drawer (interactionCompositions)
- Dismissible Alert, Toast, Popover (feedbackCompositions)

All eight components BC-02.1 identified are implemented. The four plain
Alert variants (Info, Success, Warning, Error) have no interaction, so
they are not in the matrix.

The fixture holds two Dropdown instances and a Collapsible nested inside
another one, so 9 components with 15 triggers in total. Ids t-1 … t-15
are given in document order.

How each component is driven, in both runtimes at once:
- Pointer: three rounds over all of its triggers that are visible.
- Keyboard: Enter, then Space, on every trigger that can be reached.
- Escape: after opening the component with its first trigger.
- After every action, one in-page snapshot is compared between Preview
  and the exported page. It records:
  - every trigger's aria-expanded, aria-controls and aria-haspopup, and
    whether it is visible;
  - whether each of the 12 targets is visible;
  - how many dialogs are open;
  - in the keyboard steps, which element has focus.
- Also checked at every step: no duplicate id, and every aria-controls
  id exists exactly once.

Steps compared, and what Escape does:

  Component                    Triggers  Steps  Escape
  Dropdown                         1       5    closes
  Dropdown (2nd)                   1       5    closes
  Collapsible + nested             2       7    n/a (1)
  Popover                          1       5    closes
  Drawer (dialog)                  2      10    closes
  Modal (dialog)                   2      10    closes
  Tabs                             3      15    n/a (2)
  Toast                            2      10    n/a (2)
  Dismissible Alert                1       2    n/a (3)

Notes:
- (1) The content starts open. Its first action closes it, so there is
  nothing for Escape to close.
- (2) Shown content is not a disclosure (no aria-expanded), so Escape
  doesn't apply.
- (3) It hides itself and can't come back.

Initial ARIA, the same in Preview and Export:
- Dropdowns, Collapsibles, Popover: aria-expanded
  (false / false / true / true / false) plus aria-controls.
- Modal and Drawer openers: aria-haspopup="dialog" plus aria-controls,
  no aria-expanded.
- Close buttons, Tabs, Toast, Alert: aria-controls only.
- Tabs: each tab controls all three panels.

Tab walk, initially and with a Dropdown open, in both runtimes:
- Order: t-1, t-2, t-3, t-4, t-5, t-6, t-8, t-10, t-11, t-12, t-13,
  t-15. That is 12 stops; Chromium and Firefox are identical.
- Hidden triggers (both Close buttons, the Toast's Close) are never
  reached, and no stop is ever inside hidden content.
- With the Dropdown open, its three links are added: 15 stops in
  Chromium. WebKit doesn't put links in the Tab order by default (as
  Safari), so it stays at 12 stops in both runtimes.

No document change: the exported code, saved status and Undo were the
same before and after the whole matrix.

Exceptions by component:
- Tabs have no tablist/tab semantics in either runtime (documented in
  BC-02.5, intended).
- Toast and Alert: focus is lost when a control hides itself
  (finding N1, section 15).
- WebKit: when a native dialog is closed with its Close button or with
  Escape, focus stays on the hidden dialog or Close button instead of
  returning to the opener. This happens in both runtimes and is WebKit's
  own dialog behavior.
- Intended difference: with nothing dismissible open, Escape in Preview
  exits Preview. The exported page has no mode to exit. Verified at the
  end of the matrix.

  DOM nodes             5024 5024 5024 5024 5024

  JS event listeners    1019 at every sample
  DOM nodes             5024 at every sample
  Active intervals      1 at every sample
  JS heap used, MB      19.5 19.7 19.9 19.0 19.3

  JS event listeners    1019 at every sample
  DOM nodes             5024 at every sample
  Active intervals      1 at every sample
  JS heap used, MB      19.5 19.8 20.0 20.2 19.2
  Media playing         0 at every sample

The assertion thresholds are deliberately loose:
- listeners: no more than +10 over the warm-up value;
- nodes: no more than +150;
- intervals: no growth;
- heap: below 1.25 × the warm-up value + 5 MB.
The measured deltas were exactly 0 for listeners, nodes and intervals.

Observations:
- Listeners, nodes and intervals were exactly flat across 20 sessions
  after warm-up, in every run. The heap moved within about 1 MB with no
  trend.
- This is evidence that per-session growth is bounded. It is not proof
  that there are no leaks: CDP counts are coarse, and only Chromium
  exposes them.
- No unnecessary remounting: the same media element survives hide/show
  and new sessions. The iframe's identity is kept across sessions
  (embed-safety spec).
- No unbounded timers: the instrumented setInterval count stayed at 1
  (the dev server's own).
- React console errors: none in the editor in any browser (combined
  workflow).
- Unexpected network requests: none (combined workflow).
- Stale interaction state: none. Every new session starts from the
  authored state (combined step 12, and the lifecycle end check).

15. NEW DEFECTS
---------------
No new defect was found in B1–B8, and none of high or medium severity.

N1 LOW — focus is lost when a control hides its own container.
- Affects: the Toast's Close button, the Dismissible Alert's Dismiss
  button (and any authored control that hides its own ancestor).
- Environment: Preview and Export, every browser.
- Symptom: after activation, focus falls to the page, or stays on the
  now-hidden button, depending on the browser and the runtime. A keyboard
  user must Tab again from wherever the browser resumes.
- Regression from BC-02? No. BC-02.5.1 already documented it ("If focus
  is inside a panel when it is hidden, focus is lost (to the body), as
  on the exported page"). Before BC-02.5.1, Preview lost focus too,
  through unmounting.
- Test: recorded on every run by the matrix as a "focus-finding"
  annotation. It is not an assertion, because there is no approved
  target behavior yet.
- Blocks closure? No. It is low severity, it occurs in both runtimes,
  and there is no approved requirement.
- Corrective checkpoint (suggested, outside BC-02): a small focus
  management rule. When a trigger hides the element that contains focus,
  move focus to a sensible place (the trigger's opener, or the next
  focusable element), the same way in Preview and Export.

N2 LOW — WebKit doesn't return focus to the dialog's opener.
- Environment: WebKit only, in both runtimes.
- Cause: WebKit's own <dialog> behavior. Layoutry uses native
  showModal() / close().
- Blocks closure? No.

Test-side corrections made while writing the new spec (not product
defects):
- The exported page needed the editor's viewport, so its media is on
  screen.
- Escape with nothing open exits Preview by design. The matrix now
  presses Escape only after opening something.
- The Tab walk had to stop when focus leaves the page (Firefox).
- WebKit doesn't Tab to links.
- The muted autoplay resume check is now read immediately after showing,
  with hiding done while the clip is between 0.8 and 2.0 s. Before this,
  a 4 s clip could loop past its end during the other checks and read
  as "restarted" (seen once in Firefox). The Preview and Export results
  are the same with the corrected check.
- Drags now confirm, before moving the mouse, that the pointer is on the
  element. In the first version the free child was below the visible
  canvas, so a drag could miss it.
