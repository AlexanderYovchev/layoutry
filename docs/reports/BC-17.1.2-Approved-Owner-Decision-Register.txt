3. GENUINELY UNRESOLVED PRODUCT DECISIONS (none block BC-17.2)
--------------------------------------------------------------
P-1 Existing Basic Tabs instances under N2
    Q: Are Basic Tabs already in user projects upgraded to semantic Tabs?
    Facts [EXIST]: Basic Tabs carry no component marker (ComponentMarker
    = "pagination" only). Existing instances are plain buttons with
    show/hide bindings, so they can only be recognized structurally.
    Options:
     A) Automatic upgrade in a revision step when the structure EXACTLY
        matches the factory pattern (tab group + panel group + one show
        and N−1 hide bindings per tab). Non-matching instances stay
        visual.
        + seamless; − heuristic, and it changes markup/keyboard
          behaviour on open.
     B) An explicit "Convert to semantic Tabs" command offered on
        recognized structures; new insertions are semantic.
        + user control, no surprise; − legacy projects stay
          non-semantic until converted.
     C) No legacy upgrade.
        + simplest; − legacy tabs never gain semantics.
    Consequences: A needs a revision step and fixtures; B a command +
    an Inspector notice.
    Recommendation: B (preserves "existing appearance and behaviour"
    literally and avoids heuristic markup rewrites).
    Blocks: BC-17.14 only.

P-2 Logical properties and writing modes
    Q: How should logical CSS properties be offered alongside the
    existing physical ones?
    Facts: physical and logical longhands for the same side conflict by
    order. All engines support both. writing-mode is visual styling;
    `direction` should come from the HTML dir attribute.
    Options:
     A) A per-group "Physical | Logical" representation (spacing, size,
        insets, borders, radii). Exclusive per element and group;
        lossless conversion in horizontal-tb LTR; writing-mode and
        text-orientation added in Typography.
     B) writing-mode only; no logical properties.
     C) A, plus a dir attribute (ltr/rtl/auto) on elements in component
        properties → Accessibility/Content.
    + A/C make the logical properties meaningful and future-proof;
    − more Inspector states.
    Recommendation: A (C if the owner wants RTL authoring now).
    Blocks: the logical part of BC-17.7 only.

P-3 Custom Progress label formatting (N1.2 details)
    Q: How are label numbers formatted, and what does the label show while
    indeterminate?
    Options:
     A) percent decimals setting 0–2 (default 0, round half up);
        {value}/{max} printed as authored numbers; locale-neutral
        formatting (no grouping, "." decimal); indeterminate → a separate
        authored "indeterminate text" (default: no label).
     B) As A, but locale-aware formatting using the document language
        (the export must then embed formatting behaviour; the runtime
        is affected).
     C) As A, but an indeterminate label that shows the template with
        the tokens blank.
    Recommendation: A (deterministic, export-static; B adds runtime
    locale behaviour).
    Blocks: BC-17.13 only.

P-4 CSS counters in pseudo-element content
    Q: Add a typed "counter" content kind (counter-reset/increment +
    counter()/counters() with list-style types) for numbered headings,
    custom list numbering and step indicators?
    Facts: applicable CSS in all engines, but not among O7's approved
    kinds (empty, glyph, text).
    Options:
     A) Include in BC-17.6 (headings/containers) and BC-17.17 (lists).
     B) Exclude from BC-17.
    Recommendation: A. It fits the typed model with no raw CSS.
    Blocks: nothing earlier than BC-17.6.
