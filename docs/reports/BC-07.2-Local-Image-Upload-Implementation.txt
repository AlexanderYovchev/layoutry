LAYOUTRY — BC-07.2: LOCAL IMAGE UPLOAD IMPLEMENTATION
=====================================================
Date: 2026-11-11
Type: Feature implementation + security validation + persistence + regression tests
Base commit: a31387d (main). Nothing committed.
Author: Claude (implementation engineer), for ChatGPT QA review


1. EXECUTIVE SUMMARY
--------------------
Users can now upload a PNG, JPEG, GIF or WebP file from their computer
into an Image element. The upload works the same in the browser editor
and the desktop app.

How an uploaded image is stored and used:
- The file's exact bytes are embedded as a data URL in the Image's
  existing `src` field.
- Canvas, Preview, Save, Reopen, crash recovery and Export all use that
  value unchanged.
- Project format stays 2. There is no migration, no asset registry and
  no new desktop IPC.

Checks before anything is committed:
- Each file is checked by its bytes: signature, header structure and
  completeness, then a real browser decode.
- Limits: 5 MB per file and 8192 pixels per side.
- SVG is refused.
- The proposed document is measured with Save's own serializer against
  Save's own size limit, before commit.

Undo/Redo:
- Upload, Replace and Remove are one Undo step each.
- A rejected or cancelled upload changes nothing: document, history and
  unsaved state are all untouched.

Alt text:
- A new Alt text field writes the value the Canvas, Preview and Export
  already render as `alt`.

Duplicate and Paste:
- These now refuse a copy of embedded data that would make the project
  unsaveable. The user sees a notice and nothing changes.

Two findings came out of cross-browser testing and are fixed here:
- Firefox and WebKit "decode" a cut-off PNG, JPEG or GIF as a partly
  blank image instead of failing. A decode alone therefore cannot prove
  a file is complete.
- The validator now also checks each format's structural completeness:
  - PNG: chunks fit the file, with IDAT before IEND;
  - JPEG: an end-of-image marker after the scan;
  - GIF: the trailer byte;
  - WebP: the RIFF size.

Validation:
- typecheck and lint are clean;
- Vitest: 5622 passed, 1 skipped (+88 tests);
- Chromium full suite: 247/247;
- image upload in Firefox and WebKit: 6/6 each;
- Electron full suite: 76 passed, 2 skipped;
- production and desktop builds succeed.

The full Chromium run caught one real defect in this checkpoint: the
hidden file input had no accessible name (inspector-final-regression's
"every Inspector form control has an accessible name"). Fixed with
aria-label "Upload image file".

Recommendation: ready for QA review.

5. FILE VALIDATION ARCHITECTURE
-------------------------------
validateImageUpload(file, decode):
  src/features/inspector/utils/validateImageUpload.ts

It never throws, and the cheapest checks run first:
1. Name and reported type. An .svg/.svgz name or an image/svg+xml type
   gives the SVG message. A name extension or a non-empty type outside
   the raster allow-list is refused. A matching name or type proves
   nothing.
2. Size from File.size: an empty file, or more than 5 MB. This runs
   BEFORE the file is read.
3. Read once (arrayBuffer). The size is re-checked on the bytes actually
   read, in case the file changed on disk.
4. sniffRasterImage(bytes) (src/features/inspector/utils/sniffRasterImage.ts)
   identifies the format by signature and validates header structure and
   completeness:
   - PNG: a 13-byte IHDR first, then every chunk must fit the file, with
     IDAT before IEND.
   - JPEG: marker segments are walked with every length bounds-checked
     (fill bytes, standalone markers). A frame header (SOF0–3, 5–7, 9–11,
     13–15) must come before the first scan, and an end-of-image marker
     must exist after the scan. An EXIF thumbnail's end marker sits in an
     APP segment before the scan, so it can't satisfy this.
   - GIF: a GIF87a/89a header and logical screen; the file must end with
     the 0x3B trailer (zero padding after it is allowed).
   - WebP: "RIFF"…"WEBP"; the RIFF size must fit the file; then a
     VP8/VP8L/VP8X header with its signature.
   - Markup (optional BOM or whitespace, then "<") gives the SVG message;
     anything else is "unsupported".
5. Header width/height: zero or invalid means damaged; more than 8192 is
   refused BEFORE any decode.
6. Real decode: createImageBitmap(Blob), closed immediately. A failure
   means damaged. The decoded size is checked again independently (EXIF
   rotation can swap it).
7. Base64 of the original bytes.

The decoder is injectable, so unit tests run without a browser decoder.
No custom image decoder was written: only headers are parsed.


6. SIZE AND DIMENSION LIMITS
----------------------------
- 5 MB = 5,242,880 bytes.
  - Exactly 5,242,880 is accepted; one byte more is refused before
    reading or decoding (unit-tested with a spy on arrayBuffer and the
    decoder).
  - Message: "Image is too large. Maximum file size is 5 MB."
- 8192 px per side.
  - 8192×1 is accepted and 8193×1 refused, from the header, without
    decoding (unit and browser tests use real fixtures).
  - Message: "This image is 8193 × 1 pixels. The maximum is 8192 pixels
    on each side."
- Memory:
  - One ArrayBuffer of the file (≤ 5 MB).
  - One decoded bitmap, held only for its size and closed in `finally`.
    Worst case 8192² × 4 B = 256 MB, transient; reached only after the
    size and header gates.
  - The base64 string.
  - No object URL is created anywhere: the decode takes a Blob directly,
    so there is nothing to revoke and nothing can leak.


7. DATA URL GENERATION
----------------------
- Format: `data:<sniffed type>;base64,<base64 of the original bytes>`.
- Base64 is built in 32 KiB chunks with String.fromCharCode, then btoa.
  A test confirms it equals Node's encoder across chunk boundaries.
- There is no re-encoding, resizing or format conversion, so GIF
  animation, alpha and colour data survive. Unit tests compare decoded
  data URL bytes with the fixture bytes.
- Never stored: file:// paths, absolute paths, blob: URLs or asset ids.


8. TOTAL PROJECT-SIZE PREFLIGHT
-------------------------------
Shared logic (no second limit):
- serializeProject's text building is extracted, unchanged, into
  `formatProjectFileText(project)` (src/features/project/utils/
  serializeProject.ts). serializeProject still runs its integrity check,
  then this function, then its full re-parse.
- `documentFitsProjectFile(document)`
  (src/features/project/rules/projectSaveLimit.ts):
  - measures `formatProjectFileText` against the same
    DEFAULT_PROJECT_LIMITS.maxFileCharacters (16 Mi characters) that
    parseProjectFile enforces when saving;
  - uses the WORST-CASE metadata the schema admits: a 128-character id
    and a 256-character name of lone surrogates, which JSON escapes to 6
    characters each. A later rename can therefore never push an accepted
    document over the limit.
  - The conservative margin is about 1.6 KB of 16 Mi (tested < 2 KB).
- Environments: the browser library and recovery store this same text.
  The desktop write limit (MAX_PROJECT_TEXT_LENGTH) is the same 16 Mi
  characters, and the desktop read limit (48 MiB) is above it. So a
  document that fits saves in both environments, and no
  environment-specific policy is needed.
  - Browser IndexedDB quota is not predictable. The existing
    QuotaExceededError message ("There isn't enough storage space…")
    still applies at Save.
- Boundary test: bisection finds the exact largest payload that fits; one
  character more does not. Whatever fits saves and reopens even with the
  longest, most-escaped names.

Commit (commitImageUpload, src/features/inspector/utils/commitImageUpload.ts),
synchronous, all in one turn of the event loop:
1. Read the latest store state.
2. Check the document session and that the target exists and is an
   `img`.
3. Build the proposed document with the store's own pure setElementSrc
   command. The replaced source is gone from it, so a replacement is
   measured as a replacement (tested: two 7.5 Mi images, a third
   replacing one of them is accepted).
4. Measure it, then commit.

No other edit can land between measuring and committing.

Refusal message: "This image would make the project too large to save.
Choose a smaller image or remove unused content." The document, history,
redo stack and saved-state baseline are all identical objects afterwards
(tested with toBe).

Cost: one canonical copy plus one JSON.stringify per committed upload,
never per render or keystroke. Measured in the browser size test: three
4.8 MB uploads plus the checks finished well inside the test's timeouts
(section 20).


9. ATOMICITY AND ASYNCHRONOUS LIFECYCLE
---------------------------------------
useImageUpload (src/features/inspector/hooks/useImageUpload.ts) gives
every upload a ticket.

The ticket is invalidated by:
- a newer upload;
- the section switching to another Image;
- the section unmounting: selection cleared, multi-selection, Inspector
  closed, or another project opened, which clears selection.

A result arriving on an invalid ticket is dropped silently.

A second start while reading is ignored. The guard is a ref, so two
clicks in one frame can't both start.

A valid result is still committed only to the Image id and document
session captured at start:
- A new store field, `documentSessionId`, is advanced by every
  replaceDocument. The store's field-contract test was updated to record
  that decision, and a new test proves loads advance it and edits don't.
- An upload whose Image was deleted is refused ("…removed before the
  upload finished. Nothing was changed.").
- So is an upload whose project was replaced.
- Edits made while reading are kept: the commit applies to the latest
  document.

Picker cancel: no change event or an empty file list, so nothing happens.
Selecting the same file again works: the input is cleared after every
choice.
Failed reads and decode errors give user messages, never exceptions.

All of these cases are tested in commitImageUpload.test.ts and in
InspectorImageSection.upload.test.tsx (switch, unmount, busy, cancel).


10. UPLOAD / REPLACE / CLEAR
----------------------------
- Upload: the picker opens, then validation, preflight and commit, in
  one history entry.
- Replace: the same flow. The old image doesn't need removing first. Alt
  text and all CSS (size, fit, border, radius, opacity, visibility) are
  untouched; a test compares the node before and after except `src`.
- Clear: "Remove" calls setElementSrc(undefined), the existing valid
  empty source: the Canvas shows the icon placeholder and export emits
  the existing missing-source warning. One history entry. Focus moves to
  the Upload button.
- Choosing the identical image again adds no history.

------------

  already render as `alt`. There is no new document field and no schema
  change.
- New command setImageAltText (editor/commands/documentCommands.ts) and
  store action setElementAltText.
  - Only `img` nodes change.
  - "" or undefined removes the field, which renders `alt=""` for a

- UI: "Alt text", with visible helper text linked by aria-describedby:

12. UNDO/REDO
-------------
- Upload, Replace, Remove and each Alt text commit are exactly one
  history entry.
- Rejected or cancelled uploads add zero entries.
- File reading never creates an entry; only the final commit does.
- Undo and Redo restore each source (unit tests; browser test: PNG →
  JPEG → Undo → PNG → Redo → JPEG).
- Memory: history snapshots share unchanged node objects, so each
  distinct image string is held once, however many entries reference it
  (BC-07.1 probe).

17. COPY/PASTE AND DUPLICATION
------------------------------
- Duplicate and copy/paste give new ids, keep src and alt, and are one
  Undo step each, with Undo and Redo. Save/reopen of the copies equals
  the store.
- Duplicating a parent also works.
- A copy is independent: replacing the copy's image leaves the original
  alone (browser test).

New guard (the smallest that closes the easy path):
- pasteClipboard and duplicateSelection check the save limit ONLY when
  the copy carries inline `data:` in src, poster or background image.
- If the result would not fit, they refuse with the editor notice "This
  copy would make the project too large to save. Remove unused images, or
  use an image URL instead of an uploaded image."
- No change and no history.
- Tested: duplicate, paste of a container, cut+paste allowed, and the
  browser duplicate after two 4.8 MB uploads.

Mechanism:
- The editor can't import the project feature, which already depends on
  the editor.
- ProjectWorkspace registers `documentFitsProjectFile` into
  editor/rules/documentSaveLimitGuard.ts on mount.
- With nothing registered (editor-only unit tests) nothing is refused.

Pre-existing paths NOT guarded (reported, not changed):
- Typing or pasting a huge data: URL into Source URL or Background image
  URL.
- Adding thousands of elements past the 20,000-element limit.
- Save already refuses these with its existing error.


18. SECURITY REVIEW
-------------------
- Raster-only allow-list by bytes. Signature, structure and completeness
  are checked before a real decode, and the decode result is checked too.
- Spoofing: renamed HTML, SVG and text files with .png/.jpg names and
  image/* types are all refused (unit and all three browsers). A JPEG
  named .png is stored correctly as image/jpeg.
- SVG: refused by name, by type, and by content (any markup).
- Uploaded content is never executed: it is shown only through
  <img src="data:image/…">.
- No filesystem access beyond the user-chosen File, no path ever in the
  renderer, and no new IPC.
- Electron sandbox, context isolation, fuses and CSP are unchanged.
- No object/blob URLs created or persisted. Data URL media types are
  generated, never copied from input.
- Errors are fixed user messages with no exception text.
- Resource exhaustion: there are size and dimension gates before decode;
  the JPEG/PNG walks are bounded and always move forward.
