The new tests fail against the original code (9 unit tests, 5 Playwright

2. ROOT CAUSES ADDRESSED
------------------------
Both controls handle Enter and Escape by updating React state and then
calling input.blur() to release focus. In a real, focused input, blur()
synchronously dispatches a real blur event. React runs the onBlur handler
from the CURRENT render, before the state updates from the keydown are
applied, so the handler still sees the typed draft (and, in the slider,
touched === true):
  - Enter: commit() ran in keydown and again from the blur, giving two
    history entries (BUG B).
  - Escape: setDraft(original) was still pending, so the blur committed
    the typed draft (BUG A).
InspectorColorFieldShell also had no `touched` flag, so a blur after
merely focusing a set color re-committed the same string. The store does
not dedupe this, because the style commands always return a new node
object, so guardedStyleMutation pushed a history entry and the project
became "unsaved" (BUG C).

InspectorSliderField already had `touched`, so BUG C did not apply there.

Why existing tests missed it: the old tests fired keyDown at an input
that was never focused. blur() on an unfocused element dispatches
nothing, so the second commit never happened in jsdom.

4. IMPLEMENTATION DETAILS
-------------------------
InspectorColorFieldShell.tsx
  - Added `touched` state: set by onChange, cleared on commit, on Escape
    and when the external value changes (Undo/Redo, picker, selection).
  - commit() returns early unless touched. An empty draft, or a draft
    identical to the stored string, reverts the draft without calling
    onCommit. The identical-string rule is safe because every caller
    passes the authored value (`?? null`, or a gradient stop's own stored
    color), never a displayed default. All 9 call sites were checked.
  - Added suppressNextBlurCommitRef + handleBlur(): the one blur that
    Enter/Escape's own blur() dispatches is ignored.
  - releaseFocus(): arms the suppression ONLY if the input is actually
    focused (document.activeElement === input). This avoids a stale flag
    swallowing the next, unrelated blur when blur() dispatches nothing.
    This is a small hardening over the 5.5 pattern, kept local to these
    two files (InspectorNumericValueControl was not changed).
  - Native color picker path unchanged: it still commits once, on the
    native `change` event.

InspectorSliderField.tsx (exact-value number box only)
  - Added suppressNextBlurCommitRef, handleNumericBlur() and
    releaseNumericFocus(), same as above.
  - The range input, its begin/commit/cancelTransaction gesture and its
    Escape-mid-drag handling are untouched.

Validation semantics are unchanged: callers still validate (e.g.
isValidCssColor in Typography); the slider still clamps to min/max; an
empty or non-numeric slider draft still reverts.


5. TRANSACTION AND HISTORY BEHAVIOR
-----------------------------------
No new history mechanism was added. A text commit is still one call to
the section's existing one-shot setter (e.g. setElementTypography ->
guardedStyleMutation -> one pushHistory). The fix only guarantees that
call happens at most once per edit, and never for Escape or no-ops.

begin/commit/cancelTransaction were inspected and deliberately NOT used
for these text fields: a commit-on-blur field writes the document exactly
once, so a transaction would add nothing. Transactions become necessary
in BC-01.3, when typing writes live.

Resulting lifecycle (VERIFIED in Chromium unless noted):
  Focus input              no document or history change
  Type                     draft only (unchanged behavior)
  Enter                    commit once; focus released
  Blur after editing       commit once
  Escape                   draft reverts; nothing committed; focus released
  Focus + blur, no edit    nothing (unset and set colors; slider box)
  Focus + Enter, no edit   nothing
  Retype identical color   nothing (VERIFIED in jsdom only)
  Undo / Redo              one step restores / reapplies the edit
  Invalid color            error shown; document and history unchanged
  Empty draft              reverts; unset stays unset
  Out-of-range slider      clamped, committed once (VERIFIED in jsdom only)
  Project dirty state      unchanged after Escape and no-ops (VERIFIED in
                           jsdom via selectHasUnsavedChanges)

9. REMAINING RISKS AND LIMITATIONS
----------------------------------
KNOWN LIMITATION  Programmatic selection change with no blur. If the
  selection changes while a field stays focused (no current UI path does
  this: canvas and Structure clicks blur first, and editor shortcuts are
  ignored inside inputs), and the new element has the SAME stored value,
  the draft is not reset, and a later blur would commit to the new
  element. This is shared by every draft-based Inspector control
  (NumericValueControl, NumberFieldRow, ...), not specific to these two.
  Not changed here because it needs a global policy (e.g. key fields by
  node id, or commit/cancel on selection change). Recommend deciding it
  in BC-01.3, where live editing makes it matter more.
KNOWN LIMITATION  A validation error shown by a section (e.g. "Enter a
  hex color ...") stays visible after Escape reverts the draft, until the
  next valid commit or selection change. Same as the existing numeric
  font-size error behavior; the section owns error state and the shell
  has no cancel callback.
KNOWN LIMITATION  An Opacity value typed equal to its displayed default
  (100 when unset) still commits and makes it explicit. This is
  intentional and matches InspectorNumericValueControl ("make an implicit
  default explicit"); only true no-edit focus/blur is a no-op.
NOT VERIFIED  Background, Border, Box Shadow, Gradient-stop, SVG and
  vector color fields individually in a browser. They use the same fixed
  component and pass authored values (checked by code reading); only
  Text color was exercised end to end.
NOT VERIFIED  Gap (Layout) exact-value box in a browser (same component;
  covered by unit tests using label "Gap").
NOT VERIFIED  Bulk (multi-selection) Inspector sections: they use
  InspectorBulkTextField / InspectorBulkNumberField, which already had
  these guards and were not changed.
NOT VERIFIED  Save/reopen of a .layoutry file and HTML/CSS export after
  these edits. The fix only changes how often an existing setter is
  called, never what it writes; the existing persistence/export
  Playwright specs passed in the full run.
NOT VERIFIED  Firefox/WebKit (the project Playwright config runs
  Chromium only), and the Electron desktop shell.
NOT VERIFIED  The real native OS color dialog (only its events were
  simulated).


10. RECOMMENDATION FOR BC-01.3
------------------------------
Proceed with the BC-01.1 plan: decide the history strategy for live
typing before changing any field.
  1. Choose between (A1) per-family *Live store setters, or (A2)
     guardedStyleMutation skipping pushHistory while a transactionSnapshot
     is open. Add store tests: "N live writes + commit = 1 entry",
     "cancel restores the snapshot", "unmount / selection change closes an
     open transaction".
  2. Decide the selection-change policy (commit or cancel a pending edit)
     as part of that, since it resolves the first known limitation above.
  3. Then switch InspectorNumericValueControl / InspectorNumberFieldRow
     to live mode (handle "-" / "1." partial number input, Escape restores
     the snapshot), followed by the color and slider-box fields reusing
     this checkpoint's lifecycle.
Keep the focus-first test pattern (unit + Playwright) for every control.
