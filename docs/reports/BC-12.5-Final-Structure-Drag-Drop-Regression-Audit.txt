BC-12.5 — Final Structure Panel Drag-and-Drop Regression Audit
==============================================================
Date: 2026-11-23
Milestone: BC-12 (Structure Panel Drag-and-Drop Ordering)
Status: audit complete, one targeted performance correction, focused
validation passed, NOT committed (waiting for ChatGPT QA)
Baseline: BC-12.4 is committed (400d23a).


1. EXECUTIVE SUMMARY
--------------------
Functional audit: all 16 decisions are verified against the current code
and focused tests. D1–D15 PASS. D16 is PARTIAL (performance, section 16).
No blocking functional defect was found.
- Document order, atomic multi-move, nesting, interactions, Navbar /
  Pagination structure, Undo/Redo, selection, cancellation and indicators
  all hold.
- Cross-browser subsets pass in Firefox and WebKit.
Performance investigation (profiled, not assumed):
- The ~1 s drag start/end reported in BC-12.4 was React re-rendering every
  dnd-kit consumer — ~1,000 Canvas elements AND ~1,000 Structure row
  handles — whenever the ONE shared DndContext started or ended a drag.
- Fixes:
  (1) Structure drags now run in their own nested DndContext;
  (2) the tree uses ONE shared drag source instead of one draggable per
      row;
  (3) rows subscribe to their own selection and tab-stop state, and their
      callbacks no longer change with the document.
- Measured at 1,000 elements (median of 5, Chromium dev mode):
  - drag start 578 → 44 ms;
  - drag end 793 → 380 ms;
  - a Structure row click (selection change) 510 → 187–274 ms;
  - hover unchanged (~22 ms per move, including the Playwright round
    trip).
- The remaining drop cost (~0.4 s at 1,000 elements in dev mode) is not
  drag-specific. It is the document re-render when a container with ~1,000
  direct children changes. Any edit to such a container pays it: the
  Canvas siblings re-render and the Structure parent re-creates ~1,000
  child elements. It is documented, with a recommended follow-up.
Recommendation (section 22): CLOSE BC-12, with D16 recorded as PARTIAL and
a separate large-container rendering follow-up. This is not a BC-12
regression: every measurement improved on BC-12.3/12.4.

4. SINGLE-ELEMENT DRAG AUDIT
----------------------------
Verified (unit and e2e):
- handle-only start;
- row click only selects;
- Ctrl/Cmd toggle;
- Shift range (BC-10.2 spec 26/26 with the delete spec);
- 4px mouse threshold;
- right-click never drags;
- touch press delay and swipe;
- pen direct;
- Escape (jsdom and Chromium) and a drop outside the tree cancel;
- invalid drops don't mutate;
- no-op drops record nothing.
Targets: before, after, inside, first child (the "after" band of an open
container), last child / nested end-of-container by indentation, an empty
container, the end of the page. The indicator geometry is asserted for the
indentation level (e2e test 10) and the edge/box shape (unit tests). The
drop uses the same hit-test at release.
Expanded and collapsed trees: auto-expand, plus the "after" band of a
closed container = after it (unit tests).


5. MULTI-ELEMENT DRAG AUDIT
---------------------------
- Activation: a selected row moves the selection's minimal roots; an
  unselected row moves alone; parent + child are not duplicated;
  cross-container roots move together; document order is kept; no cap
  (100 selected measured).
- Roots: parent + child, parent + several descendants, nested branches,
  noncontiguous selections, cross-container roots. Each subtree moves

- Atomic validation:
  - all compatible;
  - one incompatible;
  - several incompatible (bc12Audit);
  - a destination inside a moved subtree;
  - a target inside the set (the gap rule);
  - same-parent no-op;

  - a Free group that doesn't fit.
  Each refusal leaves the document and selection untouched, adds no
  history and doesn't dirty the project.
- Targets: all of section 4 for batches (multiMove and structureDragDrop
  tests; e2e tests 11–12).

- Identity: moved nodes are the same objects (object-identity assertions

15. PERFORMANCE METHODOLOGY
---------------------------
- Environment: Windows 10, Chromium (Playwright), the Next.js DEV server
  (React development build, so absolute numbers include dev-only
  overhead), one worker.
- Tree: a section with N−3 paragraphs plus a small target section.
- Method (temporary specs, deleted):
  - drag start = the pointermove that activated the drag → the first
    animation frame after the chip is in the DOM;
  - drag end = pointerup → the first frame after the chip is gone and the
    row is in its new parent;
  - hover = 20 pointer moves over another section, per move, including
    the Playwright round trip.
  Each is measured in-page with performance.now(): 5 samples per
  scenario, median reported. The rows are restored by Undo between
  samples.
- Attribution: CDP CPU profiles (200 µs sampling) of one drag start and
  one drop at 1,000 elements, grouped by self time and by inclusive time
  per app component.
- Selection click: row click → the first frame after aria-selected flips,
  7 samples, median.

17. OPTIMIZATIONS APPLIED
-------------------------
1. A nested StructureDragContext. A Structure drag no longer changes the
   editor's DndContext, so the Canvas's ~1,000 draggables/droppables don't
   re-render at drag start/end. Canvas and catalog drags no longer
   re-render the Structure handles either.
2. One shared drag source for the whole tree. Handles are plain buttons.
   On press, the hook records the row, the drag source's node is pointed
   at the pressed handle (rect and scroll container) and dnd-kit's own
   sensor starts. The same sensor, threshold, touch delay and Escape
   behaviour apply.
3. Per-row subscriptions for selection (zustand selectors) and the roving
   tab stop (useSyncExternalStore), plus stable row callbacks (reading the
   current document and open branches from a ref). Selection changes and
   moves re-render only the affected rows.
Behaviour is unchanged. It was re-verified by the full Structure unit
suites and the browser specs.

19. REMAINING LIMITATIONS
-------------------------
- D16: a drop into or out of a container with ~1,000 direct children
  still costs ~0.4 s (dev mode). The cause is document re-rendering
  (Canvas siblings and Structure child elements). It isn't drag-specific
  and affects any edit of such a container. Recommended: a separate
  performance follow-up (e.g. memoized Canvas element components, keyed
  children reuse). Production-mode numbers weren't measured: a production
  build would share the dev server's build folder.
- Keyboard reorder is single-element (by design).
- Touch and pen: simulated input only.
- Free batch placement stacks groups from different containers
  (deterministic, by design).
- The shared Grid clamp limits a placement's start and span separately
  (e.g. column 3 span 2 in a 2-column grid → start 2 span 2, still one
  track over). This predates BC-12 (the same rule applies when a grid
  shrinks); raised, not changed.
- Escape during a Canvas drag still clears the selection (predates
  BC-12.3.1, unchanged).
- Keyboard refusals can be spoken twice (section 10).
- Pagination paste/duplicate page limit (predates BC-12, unchanged).
