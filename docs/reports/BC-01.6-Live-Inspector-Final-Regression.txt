1. EXECUTIVE SUMMARY
--------------------
The live CSS Inspector (BC-01.2 to BC-01.5) was exercised end to end.
Real Inspector typing across 9 sections was checked on the Canvas
before blur. The edited project was saved, read back from IndexedDB and
exported with the real export engine. Preview was then compared with the
exported page over every property the existing export-parity harness
measures: 7 elements, 623 property checks, 0 differences. The project
was reopened after an app reload, again with 0 differences. History,
keyboard, validation, accessibility, listener cleanup and keystroke
latency were measured. Tests ran in Chromium, Firefox and WebKit, and
in the Electron desktop app.

One real defect was found and fixed (D1, introduced by BC-01.3). A store
mutation from outside a field during an open live edit (for example a
programmatic delete) was folded into that edit's undo step. Worse, an
Escape or an invalid final draft then restored the pre-edit snapshot
over it, bringing a deleted element back. No UI path triggers it today
(every pointerdown, shortcut and selection change ends the edit first),
but it was a data-integrity hole. Its fix is narrow, in the store and
the hook, and covered by 6 new tests.

No critical or high-severity regression remains. Recommendation: CLOSE
BC-01, with the limitations in section 13.

3. TRANSACTION AND UNDO/REDO FINDINGS
-------------------------------------
Each item is VERIFIED unless marked.
 1  One continuous edit = one entry (Chromium: multi-keystroke font
    size, rapid "9876", Arrow steps; jsdom).
 2  Escape: no history (Chromium + jsdom).
 3  Enter commits once; 4 Blur commits once (Chromium + jsdom).
 5  No-op focus/blur: no history (Chromium + jsdom).
 6  Invalid final input reverts safely (Chromium + jsdom).
 7  Unset stays unset after cancellation (Chromium + jsdom; also checked
    in the saved file).
 8/9  Undo/Redo (Chromium + jsdom).
10  Selection change cannot redirect edits (Canvas click, Structure tree,
    programmatic).
11  Collapsing the section mid-edit commits; Ctrl+S then succeeds,
    proving no transaction was left open (project commands refuse to run
    while one is open). (Chromium)
12  Deleting via Edit > Delete mid-edit: the edit and the delete are
    separate steps; nothing orphaned (Chromium). A programmatic delete:
    see D1 (jsdom).
13  Ctrl+Z / Ctrl+Y inside a focused field are the browser's native text
    undo (observed: "40" -> "4"); the Canvas follows the restored text
    live, the document never holds an invalid value, and Escape still
    restores the pre-edit value. Outside a field, Ctrl+Z is the editor's
    Undo. (Chromium)
14  Consecutive edits to different properties (Font size, Tab, Line
    height) are separate Undo steps. (Chromium)
15  Canvas resize drag and slider drag after a live edit: each one step,
    in order. (Chromium)
mergeHistory inspection:
  - Nested transactions: impossible. beginTransaction is a no-op while
    one is open, and the session falls back to one commit at the end
    without touching the foreign transaction.
  - Stale references: ownership is compared by snapshot identity, and
    every snapshot-clearing path also clears historyMergeSnapshot.
  - Accidental merging: FOUND and FIXED (D1, section 10).

10. DEFECTS FOUND AND FIXES APPLIED
-----------------------------------
D1 — FIXED
  Severity: Medium (data integrity; no known UI trigger).
  Introduced: BC-01.3 (merging transaction).
  Reproduction (jsdom, real store and Typography section):
    focus Font size, type 24 then -5, then call store.deleteSelection()
    (or setElementTypography on another node) while the field is still
    focused.
  Expected: the delete/other change persists, as its own undo step.
  Actual (before the fix):
    (a) the deleted heading came back (the revert restored the pre-edit
        snapshot);
    (b) Escape undid the other element's change;
    (c) the edit and the other change were one undo step.
  Root cause: pushHistory folded EVERY one-shot mutation into an open
    merging transaction, not only the field's own writes. The hook's
    revert/Escape then restored that transaction's pre-edit snapshot.
  Fix (store + hook):
    - store: a new action, mergeTransactionWrite(write), marks the
      session's own writes (a module-level depth counter, never
      outliving the synchronous call). Any other one-shot mutation while
      a merging transaction is open first closes it (the edit's entry,
      unless it changed nothing), then records itself.
    - hook: all live/final writes go through mergeTransactionWrite. When
      the field sees its transaction closed by someone else, it ends the
      session in an "adopt" mode that never touches the document.
  Files: src/features/editor/stores/useEditorStore.ts,
    src/features/inspector/hooks/useInspectorEditSession.ts.
  Tests: 3 reproduction tests (useInspectorEditSession.test.tsx, failing
    before the fix and passing after) and 3 store tests
    (useEditorStore.mergeTransaction.test.ts).
  Contract change: a write inside a merging transaction now merges only
    through mergeTransactionWrite. The 3 BC-01.3 store tests that wrote
    directly were updated to use it; that is the new API, not a
    weakened assertion.
  Regression risk: low. Only merging transactions (Inspector edits) are
    affected; plain transactions (drags, sliders) are unchanged. The
    full suites pass.

Not defects (test-only mistakes found and fixed while writing the spec):
  "Add Shadow" button name; the button's default radius is 6px (an
  authored 6 looks unchanged); typing 250 previews 25 first; a button's
  padding floors its width; WebKit float precision; a timeout under
  WebKit load.

Pre-existing / environmental (not BC-01 defects; documented, not fixed):
  E1 Vitest: EditorApp.test.tsx "clicking each semantic sectioning
     catalog card..." times out (15s) in the full suite at default
     parallelism on this machine (about 15 workers on 16 threads). It
     reproduces on HEAD with the BC-01.6 changes removed (verified by
     swapping the 4 files back, then restoring them byte-identical). It
     takes about 4.5s alone and passes in the full suite with
     --maxWorkers=4. It passed in the BC-01.4/01.5 full runs. Its
     timeout was not changed.
  E2 WebKit (Windows build) has no color input (section 8).
  E3 Electron lifecycle flake (section 8).
Observations carried forward (documented earlier, unchanged):
  Chromium ignores line-height on <select>/<option>. Recovery snapshots
  wait while a field is mid-edit. If a field stays focused after typing
  (no blur) for a long time, a crash in that window would lose that
  last edit from recovery. Severity low.
