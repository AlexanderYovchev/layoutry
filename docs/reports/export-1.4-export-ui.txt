LAYOUTRY — EXPORT-1.4 — Export UI, Code Preview, Downloads & Desktop Integration
Date: 2026-10-28        Branch: main        HEAD at start: a749d85 (see A)
Status: implemented and validated (all suites green). NOT committed. EXPORT-1.5 is not
started.

==========================================================================================
SUMMARY
==========================================================================================
Users can now export code from Layoutry. File › Export Code… (or the header's Export
button) opens the Export Code dialog. It does the following:
- generates HTML and CSS from the current design, including unsaved edits, with the
  existing engine (exportHtmlCss, the function the parity suites validate);
- shows each generated file as plain text, with the engine's diagnostics;
- copies, downloads (browser) or saves natively (desktop) exactly the files on screen.

Main properties:
- Two output structures:
  - Single HTML file: index.html with the CSS and any interaction script inside;
  - Separate files: index.html + styles.css (+ script.js when the page has
    interactions).
- Stale previews: if the design or project name changes while the dialog is open, the
  preview is marked stale and nothing can be copied, downloaded or saved until
  Regenerate.
- Diagnostics: severity, message, element and property for every finding. Errors block
  export (no files exist to export); warnings don't.
- Browser: Blob downloads, one per file, with per-file buttons; object URLs revoked.
- Desktop: native Save dialog (one HTML file) or folder picker (separate files), through
  two new IPC channels with their own tokens. The renderer never sends a path; only the
  three fixed file names are accepted. Multi-file writes are staged to temporary files
  and rolled back on failure.
- Entitlement: an ExportEntitlement boundary asked when the dialog opens. The
  development implementation allows everyone. No billing, accounts or paid badges.
- Exporting never saves the project or changes its unsaved state.

Results:
- TypeScript, ESLint and the production build pass.
- Vitest: 5,029 passed, 1 skipped (pre-existing).
- Browser Playwright: 58/58, twice (44 existing + 14 new).
- Electron Playwright: 57 passed, 2 skipped (the opt-in benchmark), 0 failed.
- Packaged Layoutry.exe: 51/51 passed, with the genuine Windows Save dialog and folder
  picker.

F. CODE PREVIEW
==========================================================================================
- One ARIA tab per generated file (name and size). Arrow keys, Home and End move between
  them, with a roving tabindex.
- The file is a <pre> holding a single text node, in monospace with whitespace: pre:
  - indentation and line breaks are preserved;
  - text is selectable;
  - it is focusable and named, e.g. "index.html source code";
  - long lines scroll inside the box.
- Generated markup is never parsed: the <pre> has no child elements. A test document
  whose text contains <img onerror> and <script> runs nothing in the editor (unit and
  browser tests).
- Bounded: a file over 400,000 characters shows its first lines, cut at a line
  boundary, with "Showing the first N of M lines. Copy and download always use the
  complete file."
  - Measured <pre> layout in Chromium: 92 ms at 400k characters, 209 ms at 1 MB,
    484 ms at 2 MB, 1,056 ms at 5 MB.
- There is no syntax highlighting and no editor dependency.

==========================================================================================
H. SNAPSHOT AND STALE-STATE HANDLING
==========================================================================================
- Snapshot = the exact document object from the editor store, plus the title. The store
  replaces the document object on every edit, so identity is the revision. It is the
  live, in-memory design, including unsaved edits. It is never an autosave, a recovery
  snapshot, the last save or a cached export.
- Stale = the store's document is no longer that object, or the project name changed.
  - Shown: an amber banner, "The design changed after this code was generated.
    Regenerate to export the current design.", with a Regenerate button.
  - Copy, Download and Save are disabled while stale. The old code stays visible as it
    was generated.
- Desktop saves check again after the native dialog closes. If the design changed
  meanwhile, nothing is written: "The design changed while you were choosing where to
  save, so nothing was saved. Regenerate the code, then save again."
- Exporting never calls a project command and never touches the project store. A
  browser test checks that the status after editing, exporting and downloading is what
  the edits made it, and that no save toast appeared.
- Observed while testing: the editor's document shortcuts (Ctrl+Z…) still reach the
  editor while a modal dialog is open. This is existing behaviour and was not changed.
  The stale check is what keeps an export consistent in that case, and a browser test
  relies on it: Ctrl+Z with the dialog open → stale → Regenerate.

Generation states:
- checking (entitlement);
- generating ("Generating code…" with a spinner, painted before the synchronous
  generation runs);
- ready ("Code ready: N files, …" announced);
- refused (error diagnostics);
- failed (the engine threw: "Layoutry couldn't generate code for this design. Nothing
  was exported. …" + Try again);
- denied (entitlement message).
Transfer states:
- busy ("Saving…", "Copying…", "Choose a folder for the files…");
- conflict (desktop);
- done;
- error (role=alert).
Success is only reported after the platform accepted the operation. A single guard
prevents a second copy, download or save while one is running.

==========================================================================================
I. COPY CODE
==========================================================================================
- Copy code copies the selected file's exact text with navigator.clipboard.writeText.
- Fallback: a hidden read-only textarea, focused and selected, then
  execCommand("copy"). It is placed inside the open modal, because content outside it
  is inert. The textarea is removed afterwards and the previous focus restored.
- Feedback: "Copied styles.css to the clipboard.", or "Layoutry couldn't copy … Select
  the code in the preview and copy it with Ctrl+C." (role=alert).
- Tests:
  - unit: the exact string, the fallback, and failure;
  - browser: the string Layoutry hands to writeText equals the engine's file byte for
    byte.
- Platform note: reading the clipboard back on Windows returns CRLF line endings.
  Windows stores clipboard text that way; the text is otherwise identical.

==========================================================================================
K. ELECTRON SAVE ARCHITECTURE
==========================================================================================
- Main process: desktop/export/exportFileService.ts. It is free of Electron and
  unit-tested on a real disk with fault injection.
- IPC: two new channels, added to the fixed allowlist:
  - layoutry:export:choose-destination with {mode, suggestedName};
  - layoutry:export:write with {token, files: [{path, content}], overwrite}.
- Preload (apiVersion 3):
  - chooseExportDestination(mode, suggestedName);
  - writeExportFiles(token, files, overwrite).
  Arguments are type-checked, and only {path, content} per file is copied across.
- Renderer: src/features/export/desktop/desktopExportFiles.ts. Every result is
  Zod-validated; malformed results become an honest error.
- Single file: the native Save dialog.
  - Title "Export HTML File", filter HTML (.html/.htm), default name index.html in the
    last export folder or Documents, and Windows' replace confirmation.
  - A name without .html/.htm gets .html added, but only if that file doesn't exist.
- Separate files: the native folder picker ("Choose Export Folder", button "Export
  Here", createDirectory allowed).
- Tokens:
  - random 128-bit, kept in their own registry, separate from project-file tokens;
  - at most 4 per window, bound to the window;
  - single-use on success;
  - revoked when the window closes or its renderer crashes (wired in main.ts next to
    the project tokens).
- The service follows the project-file conventions:
  - exact-key payloads and the token pattern;
  - temporary file + flush + rename;
  - transient-lock retries (50–800 ms);
  - read-back verification;
  - user-facing messages that never contain full paths.
- Project-file writing is untouched; it reuses no write capability of the project
  service.

==========================================================================================
L. DESKTOP FILE CONFLICT HANDLING
==========================================================================================
- Single file: Windows' own Save dialog confirms replacing an existing file. The service
  records that file's hash when the dialog closes:
  - if the file is unchanged at write time, it is replaced without asking again;
  - if it changed or appeared in between, the result is a conflict and Layoutry asks.
- Separate files: if any of the target names exist, Layoutry lists them and asks:
  "index.html, styles.css already exist in “Site”. Replace them? Other files in the
  folder are not touched." The answers are Keep existing files or Replace (an
  alertdialog). Nothing is written before the answer.
- Overwrite race: just before each rename, the target is checked again. A file that
  appeared or changed since the conflict check stops the export, with rollback.
  Remaining window: the instant between that check and the rename. Windows has no
  compare-and-swap rename (same documented limit as project saves).
- Partial writes:
  1. Every file is first staged to .<name>.<random>.layoutry-export-tmp and flushed.
     If staging fails (disk full, permission), the temporaries are removed and nothing
     visible changed.
  2. Then the renames, index.html last.
  3. If a rename fails:
     - files already replaced are restored to their previous bytes, atomically;
     - newly created files are deleted only if they still hold exactly what this
       export wrote;
     - the user is told which files, if any, couldn't be put back.
  Rollback never deletes unrelated files.
- Errors handled with specific messages:
  - permission denied / protected folder;
  - file open in another program (EBUSY/EPERM after retries);
  - disk full;
  - folder missing;
  - name is a folder;
  - path too long;
  - link destination;
  - existing file too large to back up (>64 MiB);
  - read-back mismatch.
  Each says whether anything changed.
- Limit: a hard crash between renames can leave a mix of old and new files, never a
  partly written file. Temporary files are identifiable by their extension.

==========================================================================================
M. DESKTOP SECURITY
==========================================================================================
- No Node.js, no ipcRenderer and no filesystem access in the renderer. The bridge stays
  a frozen object of functions; it now has 16 functions plus apiVersion.
- Sender checks: the same isTrustedSender as every channel (the main window's
  webContents, its top frame, app://layoutry/). Other frames and windows are refused.
- Payloads:
  - exactly the expected keys;
  - mode ∈ {standalone, separate};
  - a token matching [0-9a-f]{32};
  - 1–3 files, names exactly index.html, styles.css or script.js (case-sensitive), no
    duplicates;
  - content a string of ≤ 16 Mi characters, ≤ 32 Mi in total;
  - overwrite a boolean.
  Single-file destinations accept exactly index.html; folders require index.html and
  styles.css.
- Paths: never accepted from the renderer. Fixed names are joined to the chosen folder,
  and dirname(target) === folder is asserted. The suggested name is reduced to a bare
  sanitized file name (the drive and folder parts are dropped).
- Links:
  - the folder itself and every target must not be a symbolic link or junction
    (lstat);
  - targets must be regular files;
  - exclusive temp creation never follows an existing entry.
- Token isolation: project tokens fail on the export channel, and export tokens fail on
  the project channel. Tested in the real app.
- CSP, fuses, sandbox, navigation and permission policies are unchanged.

AI. KNOWN LIMITATIONS
==========================================================================================
- Browser multi-file download is one download per file. Browsers may ask permission
  or block repeated downloads; the per-file buttons are the fallback. ZIP is
  EXPORT-1.8.
- A browser download only "starts": Layoutry can't know whether the user kept it.
- Multi-file desktop writes aren't atomic as a set:
  - a rename failure is rolled back;
  - a hard crash between renames can leave a mix of old and new files, never a partly
    written file;
  - temporaries are recognizable by .layoutry-export-tmp;
  - the check-then-rename instant can't be closed on Windows.
- External http(s) resources are not bundled. Viewing them needs a connection, and the
  dialog says so.
- The preview shows the first ~400,000 characters of a very large file. Copy and
  download use the full file.
- Windows' clipboard stores CRLF line endings.
- The code preview has no syntax highlighting.
- The entitlement check is client-side only (development implementation).
- Editor shortcuts (undo, delete…) still act on the document while modal dialogs are
  open. This is existing behaviour; the stale check covers export.
