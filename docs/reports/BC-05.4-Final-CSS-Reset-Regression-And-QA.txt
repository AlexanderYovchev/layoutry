3. DESKTOP MIGRATION SAVE WORKFLOW
----------------------------------
Where the rule lives: the desktop main process, the single choke point every save to a file passes through. This covers:
- Save and Ctrl+S;
- Save from the close-window and switch-project "Unsaved Changes" prompt;
- saving work restored from a crash.

Design:
- desktop/files/fileCapabilities.ts: each file token records `formatVersion`, the project format of the file as this window last read or wrote it.
  - It is set on open (from the text just read).
  - It is set on a recovery restore (from the original file's current text; recoveryService already reads it).
  - It is updated after every successful write.
  - It is null for a Save dialog destination.
- desktop/files/projectFileService.ts `write`:
  - New required payload key `upgradeFormat` (boolean), validated like `force`.
  - If the token's formatVersion < the incoming text's formatVersion, and neither `upgradeFormat` nor `force` is set, it returns `{ status: "older-format", fileName, formatVersion }` and writes NOTHING.
  - `force` comes only from the external-change dialog, which can only be reached after this check has passed, so the user is never asked twice.
- desktop/preload/preload.ts: `writeProjectFile(token, text, force, upgradeFormat)`. The 4th argument must be a boolean, or the call throws as for every other argument. No new channel, and no change to sandboxing, the CSP or the capability model.
- Renderer:
  - The bridge schema accepts "older-format".
  - projectCommands.saveToFile takes `upgradeFormat` and maps the result to `{ ok: false, olderFormat }`.
  - The workflow shows the new "older-format" dialog.
  - `resolveOlderFormat("save-as" | "overwrite")`; Cancel = close the dialog.
- UI: `OlderFormatDialog` in ProjectConfirmDialogs.tsx, the same Dialog primitive and button styles as the existing File Conflict dialog.
  - Title "Upgrade Project File?".
  - Initial focus is Save As… (Recommended).
  - Escape and Cancel write nothing.

Workflows checked:

| Workflow | Result |
|---|---|
| Save / Ctrl+S on a format 1 file | Prompt; file untouched until a choice |
| Save As from the prompt | New format 2 file; original byte-identical; the project moves to the new file (existing Save As identity rules); later saves go there with no prompt |
| Save As dialog cancelled | Nothing written; still dirty |
| Overwrite Original | Original replaced with format 2; next save has no prompt |
| Cancel / Escape | Nothing written; still dirty; the next Save asks again (no conversion happened) |
| Save failure during Overwrite | Error dialog; original untouched; still dirty |
| Closing a dirty format 1 project → Save | Prompt; the window stays open (the close is cancelled, as the File Conflict dialog does today); original untouched |
| Opening another project | Its "Save" goes through the same saveInPlace path, so the same prompt applies |
| Application quit | Same as closing |
| Autosave | Layoutry has no autosave to the project file. Recovery snapshots go to separate recovery storage and never write the original (recoveryCoordinator → storage.write) |
| Restored recovery work whose original is format 1 | Prompt (gap closed: before BC-05.4 this would have saved straight over the original) |
| Existing format 2 file | Saves in place, no prompt |
| New project | Native Save dialog, no prompt (the token has no recorded format) |
| Save dialog destination replacing an existing format 1 file | No second prompt: Windows' own replace confirmation already asked |

Browser library projects are outside Decision A, which covers desktop files.

5. MULTI-SELECTION COMPUTED SPACING RESULTS
-------------------------------------------
- `useRenderedPaddings(ids)` generalizes BC-05.3's hook. One layout effect measures every listed node (one getComputedStyle each).
  - Only nodes with an unset padding side are listed.
  - An empty list does no work and causes no re-render.
- `useRenderedPadding(id)` is now a thin wrapper, so single selection is unchanged.
- Effective value per side: authored (0 included), else rendered padding, else 0 for margin (the base stylesheet's value; no default presentation adds margin).
- The field shows a number only when every side of every selected element has it; otherwise it shows Mixed.
- Row state follows authored data:
  - "set" when any selected node authors a side, an authored 0 included;
  - "unset" when none does;
  - "mixed" when the shown values differ.

| Case (unit tests in InspectorBulkSpacingSection.test.tsx, 8) | Shows |
|---|---|
| 16 vs 8 computed | Mixed |
| Authored 16 vs unset rendering 16 | 16, row set |
| Two buttons with their own 8/16 | Mixed (BC-05.3 showed 0) |
| Authored 0 vs unset rendering 0 | 0, row set (the distinction is kept) |
| Authored 0 vs a button's unset 8/16 | Mixed |
| Nothing authored, everything 0 | 0, no set state |

- Editing a Mixed field writes exactly the typed value to all four sides of every node, in one history entry. Nothing measured is ever written.
- After a style change and an Undo, the values re-read (not stale).
- e2e (bc05-final-regression.spec.ts) confirms the same in a real browser: two buttons read Mixed; heading + authored-0 paragraph read 0 with "Explicitly set"; editing Mixed → 4px on both; margin untouched; Undo.
- Multi-selection reset: none existed and none was added, per scope.

17. PERFORMANCE OBSERVATIONS
----------------------------
- Multi-selection measuring:
  - one layout effect per document change;
  - one getComputedStyle per selected node that has an unset padding side;
  - no full-document scans, no polling, no new store subscriptions (the hook reads the same `document` signal as before);
  - nodes with all four padding sides authored are not measured;
  - an empty list does nothing, not even a state update.
- Trade-off: a large multi-selection of unset elements costs N style reads per edit. These are reads, not writes, so no layout thrash.
- Single-selection cost is unchanged: 2 getComputedStyle per keystroke, median 39–40 ms in Firefox.
- Desktop: the format check is one JSON.parse of text the main process already holds (on open, on write, on restore). No extra disk reads, except restore, which already read the original.
