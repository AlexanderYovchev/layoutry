3. V3 SCHEMA DESIGN
-------------------
- The envelope is unchanged apart from formatVersion: literal 3
  (projectFileV3Schema). Format 3 only ADDS optional element fields.
- The element schema stays strict: an unknown field is still refused,
  never dropped. This applies to future-version fields too.
- Added fields (editorDocumentSchema.ts):
    ariaLabel    string, 1-250 chars, not blank, no control characters
    ariaCurrent  "page" | "step" | "location" | "date" | "time" | "true"
                 ("false" refused: it means the same as absent)
    disabled     literal true (enabled = absent; false is refused, so
                 there is one representation)
    component    "pagination"
- Placement is an integrity rule (checkDocumentIntegrity →
  findMisplacedAccessibilityField). A misplaced field fails the load with
  code "integrity" and a path:
    ariaLabel    nav, header, footer, main, aside, section, form, a, button
    ariaCurrent  a
    disabled     a, button
    component    "pagination" only on nav
  (The Dialog already has a DERIVED accessible name from its heading, so
  it doesn't accept ariaLabel.)
- The TypeScript drift guards (assertSameType) cover the new fields, so
  the schema and EditorElementNode can't diverge.
- Serialization needed no change: keys are sorted and undefined is
  omitted.


4. ACCESSIBILITY ATTRIBUTES
---------------------------
Decision: three generic fields, plus the marker. Investigated:
- aria-label: yes (ariaLabel). Needed for the nav landmark name.
- aria-current: yes (ariaCurrent).
- aria-disabled: NOT a separate field. One generic `disabled` field maps
  to the right semantics per element type, as the brief asked ("disabled
  semantics appropriate to the element type"):
    link   → no href + role="link" + aria-disabled="true"
             (aria-disabled alone does NOT stop navigation, so the href is
             removed; role="link" keeps it announced as an unavailable
             link, since an <a> without href has no role)
    button → native `disabled` in Preview and Export;
             aria-disabled="true" on the Design Canvas (a native disabled
             button swallows the clicks that select it)
- role: not stored. It is derived only for a disabled link.
- No other attribute is needed by Pagination. No free attribute bag: event
  handlers, style or arbitrary attributes can't be expressed (tests try
  `onclick`, `attributes`, `ariaDisabled`; all refused).
- One renderer, resolveAccessibilityAttributes (rules/
  accessibilityAttributes.ts), is used by:
  - the Canvas, which is also the Preview;
  - the export (identity() in buildExportDocument.ts).
  So Preview and Export can't disagree.
- aria-current="page" also makes a link non-navigable (isNavigableLink):
  it renders without href. Other tokens ("step", ...) keep the href. The
  stored href is never deleted, so BC-09.3's "set current page" can move
  the state and the old current page gets its URL back.
- Escaping: React on the Canvas, the export printer on export. Tested with
  `"><img src=x onerror=...>` and `"><script>...</script>&`.
- Reusable later by Navbar (aria-current on the active item), Breadcrumbs
  (nav label, current page) and others.


5. MIGRATION IMPLEMENTATION
---------------------------
The existing step chain (PROJECT-1.5), with one new step:
  { from: 1, migrate: migrateSpacingZerosToUnset }        (BC-05.3)
  { from: 2, migrate: migrateToAccessibilityFields }      (BC-09.2)
- Version paths:
  - 1 → 2 → 3, 2 → 3, and 3 (passed through untouched);
  - 4 or newer → "unsupported-version" ("saved by a newer version of
    Layoutry (format 4)").
- 2 → 3 is pure and deterministic:
  - it runs on the dispatcher's structuredClone;
  - it changes only formatVersion;
  - no node, id, interaction, CSS or media value is touched;
  - it never converts an old Pagination.
- Version-bypass guard: if a format 1 or 2 file contains ariaLabel,
  ariaCurrent, disabled or component anywhere (root included), the step
  throws.
  - The load fails with "migration-failed", and the message names the
    field.
  - The file is untouched.
  - Why: no older build could write those fields, so such a file is
    forged. Accepting it would let a file claim an old version while
    carrying new data.
- Unavoidable serialization difference: re-saving a format 2 file
  changes exactly one line, `"formatVersion": 2,` → `3,`. Tested
  byte-for-byte on two frozen format 2 fixtures.
- Measured cost (section 24): about 16 ms on a 3,265-element, 1.7 MB file.


6. LEGACY SAVE PROTECTION
-------------------------
- The BC-05.4 rule lives in the desktop main process
  (projectFileService.write): a write that would RAISE the version the
  window read returns "older-format" and writes nothing, unless the
  renderer sends upgradeFormat (only after Overwrite Original).
- It compares versions, so with CURRENT = 3:
  - a format 1 or 2 file now asks;
  - a format 3 file saves straight back.
  No product change was needed there.
- Proven for BOTH older versions, in unit tests and in the real Electron
  app:
  - Save asks first and writes nothing;
  - Save As keeps the original byte-identical and writes a format 3 copy;
  - a cancelled Save As dialog writes nothing;
  - Cancel and Escape write nothing, and the next Save asks again;
  - Overwrite only on that explicit choice, and it never asks again;
  - a failed Overwrite reports the error, keeps the original and the
    unsaved work, and is not marked as migrated;
  - closing with unsaved work: Save asks about the format first and the
    window stays open (the unsaved-close flow can't bypass it);
  - a format 3 file saves in place without asking.
- Crash recovery: the BC-05.4 recovery path records the ORIGINAL file's
  version on the restore token, so saving restored work is protected the
  same way. Its tests (desktop/recovery, projectRecoveryWorkflow) were
  re-run and pass. Recovery snapshots never write to the original file.


7. BROWSER SAVE BEHAVIOR
------------------------
No prompt is needed in the browser, and none was added. This keeps the
BC-05.4 product decision, which covers desktop files. It is now
documented in project-format.md ("Browser storage (BC-09.2 review)"):
- one origin serves one deployed build, so after an update every tab that
  loads the app is the new build;
- the browser never writes back to a file it imported: Save writes the
  library record, and Download always creates a new file;
- an older build still open in another tab refuses a format 3 library or
  recovery record with the "newer version" message and doesn't change it,
  so nothing is lost;
- browser recovery records hold their own copy of the text and are
  migrated in memory on restore.
Browser code changed: none. Browser import of a format 2 file, which
migrates in memory, is covered by the Chromium spec (section 11).

9. PAGINATION COMPONENT IDENTITY
--------------------------------
- The marker is `component: "pagination"` on the nav.
  - It is set only by createPaginationNode, and only on the root.
  - isPaginationNode(node) = tag "nav" && component === "pagination".
- Never inferred: a nav with the exact new structure but no marker is an
  ordinary nav (test). Navbars and Breadcrumbs never get it (test).
  Legacy Paginations don't get it.
- Preserved by save/reopen, copy/paste, duplicate and Undo/Redo: the
  clone copies every field (store tests, desktop relaunch).
- There was no existing generic marker architecture (BC-08's Video Embed
  reuses the iframe's own fields). `component` is the smallest addition,
  validated as an enum and limited to its root tag.
- Interim choice (please confirm): a MARKED Pagination no longer gets
  the generic "Navigation links" section; its commands are no-ops on it.
  - Why: its Previous/Next are now links. Generic Add would copy Next
    and append "New link" after it, and Remove could delete the current
    page.
  - BC-09.3 adds the dedicated section.
  - Until then a page can be added by duplicating a page link, which
    never copies the current state (section 19).
  - Legacy (unmarked) Paginations keep the generic section exactly as
    before (tests).

13. CURRENT-PAGE BEHAVIOR
-------------------------
- Visual: dark background plus white text, so it isn't shown by colour
  alone.
- Semantic: aria-current="page".
- Non-navigable: no href in Design, Preview and Export. With JavaScript
  turned off, clicking it on the exported page doesn't navigate (tested).
  It isn't a Tab stop.
- Selectable and CSS-editable in Design: it is an ordinary Link node, and
  a click reaches selection (unit and Chromium tests).
- Survives save/reopen, Undo/Redo and export (tests).
- Exactly one:
  - the factory makes one;
  - duplicating or pasting a node never copies aria-current on the
    copy's root (withoutCopiedCurrentState), so a duplicated current
    page is an ordinary page;
  - duplicating the WHOLE Pagination keeps its own single current page.
  - Not enforced at load: that would make a project unopenable over a
    styling matter.

18. SECURITY REVIEW
-------------------
- URLs: no new path.
  - Enabled links go through the existing checkExportUrl ("link").
  - A disabled or current link writes NO href at all.

24. KNOWN LIMITATIONS
---------------------
- No Inspector UI for the new fields yet. A user can't type an aria-label,
  set the current page or disable a control. Only the factory sets them
  (BC-09.3 scope).
- The Link section of a current or disabled link still edits its stored
  href, which doesn't render while that state is set. BC-09.3 should
  explain this in the UI.
- A marked Pagination has no page add/remove UI until BC-09.3 (section
  9). Duplicating a page link is the workaround.
- Cut then paste of the current page drops its current state (the paste
  is a copy root). Undo restores it.
- A disabled or current link that the author gave a click interaction
  still runs it in Preview and on export (only navigation is blocked). No
  factory creates this. BC-09.4 (interaction regression) should decide.
- No ul/li list semantics (section 12).
- No hover/focus styles (cross-cutting CSS-model gap; BC-09.1 G7).
- Playwright quirks, test-only:
  - WebKit Tab skip (section 17);
  - force-click on aria-disabled elements (section 16).
- An older Layoutry (format 2 build) refuses format 3 files. That is
  intended ("made by a newer version").

27. QA RECOMMENDATION
---------------------
APPROVE BC-09.2. It delivers format 3 with an explicit, guarded migration
and first-save protection proven for format 1 and 2 originals. It adds
generic, validated accessibility fields and an accessible, static, wrapped
Pagination for new insertions, while old projects and old Paginations
stay byte-identical.
Please confirm or redirect these engineering choices (all reversible):
1. One `disabled` field (per-type semantics) instead of an aria-disabled
   field.

   Pagination.

   BC-09.3.
4. Copies never carry aria-current on their root (this includes
   cut+paste).

   (migration-failed).
Then BC-09.3 (the Pagination Inspector) can start.
