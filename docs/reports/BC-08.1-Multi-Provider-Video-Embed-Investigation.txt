Confidence markers used below:

1. EXECUTIVE SUMMARY
--------------------
Layoutry already has the right building blocks:
- An Embed component: a real <iframe> with a fixed sandbox, a URL
  policy shared by Canvas and Export, and an interaction shield.
- A native Video component with the muted-only autoplay policy.

There is no YouTube, Vimeo or other provider support, and no video-
specific embed. All of BC-08 can be built without a new node type and
without changing the project format (it stays version 2).

Key findings:

F1 [PROBE] Fullscreen is technically easy in browsers.
  Adding allow="fullscreen" to today's sandboxed iframe enables
  fullscreen in Chromium, Firefox and WebKit. No sandbox token changes,
  and none is needed. Without it (today), fullscreen is refused.

F2 [PROBE] Electron is different.
  With allow="fullscreen", the embed is told fullscreen is available,
  but its request never completes: it neither succeeds nor fails. The
  cause is the shipped permission handler, which denies every
  permission.
  Enabling fullscreen on desktop therefore needs a reviewed change to
  desktop/security/hardenSession.ts. That is an Electron security
  change and needs explicit approval.

F3 [PROBE] The desktop app sends no Referer header to embeds.
  Requests from app://layoutry/ arrive without one.
  [DOCS] YouTube requires an HTTP Referer from every embedding client.
  [DOCS] Dailymotion blocks playback without one.
  [ASSUMED] So YouTube and Dailymotion embeds will likely refuse to
  play in the desktop app until this is addressed.

F4 [PROBE] An exported page opened as a local file sends no Referer.
  This covers file://, i.e. double-clicking index.html, in all three
  browsers. The same providers will likely refuse to play there
  [ASSUMED]. They should work once the page is served from a website.
  The export dialog should say so.

F5 [CODE] The Embed component has no media lifecycle.
  Native video and audio are paused when Preview ends and when an
  interaction hides them (BC-02.2 / BC-02.5). An <iframe> is not:
  - it is never remounted on mode change;
  - the export runtime only pauses <video>/<audio>.
  A provider video playing in Preview would keep playing, with sound,
  after Preview exits or after its parent is hidden. BC-08 must solve
  this before players can be used.

F6 [CODE] The Embed component loads its page live on the Design canvas.
  A provider iframe there would contact the provider as soon as the
  project opens, before the user ever presses Play.

F7 [DOCS] Twitch cannot work for Layoutry's exports.
  Every embed must name the exact parent domain, which Layoutry cannot
  know at export time; for the desktop app's app:// origin it may not
  be possible at all.
  [DOCS] Dailymotion's iframe embed is documented as suitable only for
  JavaScript-restricted environments (AMP), and it needs a per-account
  player ID for configuration.

Recommendations (each needs approval; see section 22):
- Providers: Option A, YouTube + Vimeo first. Loom is a cheap later
  addition; Dailymotion, Wistia and Twitch are deferred.
- Model: reuse the existing iframe tag and the existing node fields. A
  new "Video Embed" toolbar item creates it; the provider is derived
  from the URL, never stored.
- Canvas: a static placeholder in Design (zero third-party requests).
  The real player loads only in Preview and on exported pages.
- Lifecycle: tear the player down on Preview exit and when hidden. The
  playback position is NOT kept; this is stated honestly.
- Autoplay: provider autoplay only when autoplay AND muted (existing
  getEffectiveAutoplay), and no allow="autoplay" delegation.
- Privacy: youtube-nocookie.com and Vimeo dnt=1 by default; an explicit
  referrerpolicy; no thumbnails fetched in Design.
- Fullscreen: ENABLE (restricted) for recognized provider embeds only,
  after approval:
  - browsers: in Preview and on exported pages;
  - desktop: only with a scoped permission allowance, in its own
    checkpoint.
  Generic embeds stay without fullscreen.
- Roadmap: five checkpoints rather than three (section 23). The desktop
  fullscreen/Referer work is security-sensitive and isolated in its own
  checkpoint.

QA recommendation: APPROVE BC-08.1 as complete, and record the product
decisions in section 22 before BC-08.2 starts.

3. CURRENT VIDEO AND IFRAME BEHAVIOR
------------------------------------
NATIVE VIDEO (tag "video") [CODE]
- Source: node.src (any http/https/relative URL or data:video).
- Inspector (InspectorVideoSection + InspectorMediaPlaybackFields):
  Source URL, Poster URL, Controls, Autoplay, Muted, Loop, media fit.
- Canvas Design:
  - a real <video> with no autoplay attribute (gated on Preview);
  - a MediaInteractionShield blocks the controls so clicks select;
  - an empty source shows MediaGuideOverlay.
- Canvas Preview:
  - the shield is removed;
  - usePreviewMediaPlayback (canvas/hooks) calls play() on entry only
    for muted autoplay, and pause() on exit, unmount and hide;
  - RuntimeHiddenContext keeps hidden media mounted, but paused.
- Export:
  - <video src poster controls autoplay muted loop>, where autoplay
    comes from getEffectiveAutoplay;
  - an "unmuted-autoplay" warning appears when autoplay is dropped;
  - exportInteractionRuntime.ts pauses video/audio in hidden targets.
- Save/reopen: plain fields, project format 2.

IFRAME / EMBED (tag "iframe") [CODE]
- Source: node.src.
- Inspector (InspectorIframeSection.tsx):
  - Source URL, refused unless isValidLinkHref and the iframe policy
    allows it;
  - Title.
  - No playback fields.
- Canvas Design:
  - a real <iframe> that LOADS THE PAGE (F6);
  - sandbox and src come from resolveIframeSourcePolicy
    (src/lib/iframeSandbox.ts); the iframe is keyed on the sandbox
    value;
  - no src until the host origin is known (useHostOrigin);
  - a MediaInteractionShield is required, because clicks inside a
    frame never reach the editor;
  - a refused source shows MediaGuideOverlay's REFUSED_EMBED_HINT.
- Canvas Preview: the same iframe, with the shield removed. Nothing
  pauses or reloads it on exit or hide (F5).
- Export:
  - checkExportUrl(..., "frame") allows http/https/relative only;
  - then <iframe sandbox="..." src title>, using EXPORTED_PAGE_ORIGIN
    to decide allow-same-origin.
- Save/reopen: plain fields.
- Attributes never written anywhere: allow, allowfullscreen,
  referrerpolicy, loading, srcdoc. The strict schema refuses
  sandbox/srcdoc/allow/referrerPolicy fields at import (BC-02.3).


4. EXISTING SECURITY MODEL
--------------------------
Iframe policy (src/lib/iframeSandbox.ts, BC-02.3) [CODE]:
- Frameable protocols: http: and https: only (relative and protocol-
  relative URLs resolve to them).
- Never framed: data:, blob:, file:, about:, javascript: and everything
  else.
- sandbox is always present: "allow-forms allow-popups allow-scripts".
  "allow-same-origin" is added only when the URL's origin differs from
  the host page's origin.
- Never granted:
  - allow-top-navigation (and its -by-user-activation and
    -to-custom-protocols forms);
  - allow-popups-to-escape-sandbox;
  - allow-modals, allow-downloads, allow-pointer-lock,
    allow-presentation, allow-orientation-lock,
    allow-storage-access-by-user-activation.
- No allow= (Permissions Policy) at all, so embedded fullscreen is OFF.
  Verified again this checkpoint (F1 baseline).

Web hosting (next.config.ts):
- frame-ancestors 'none' plus X-Frame-Options DENY, so the editor can
  never be framed, not even through a redirect.

Export URL policy (src/features/export/utils/exportUrlPolicy.ts):
- Per-context scheme allowlists.
- Scheme detection is hardened against tab/newline/control-character
  tricks.

Electron (desktop/) [CODE]:
- main.ts webPreferences: contextIsolation: true, nodeIntegration:
  false, sandbox: true, webSecurity: true, webviewTag: false.
  app.enableSandbox().
- security/contentSecurityPolicy.ts:
  - frame-src http: https:;
  - script-src 'self' 'unsafe-inline' (no eval, no remote script);
  - object-src 'none'; base-uri 'none'; form-action 'none';
    frame-ancestors 'none'.
- security/hardenWebContents.ts:
  - setWindowOpenHandler denies every popup;
  - will-navigate / will-redirect only allow app://layoutry/;
  - will-frame-navigate only lets subframes go to http/https/
    about:blank;
  - will-attach-webview is always prevented.
- security/hardenSession.ts: every permission request and check is
  denied, explicitly including fullscreen.
- The preload bridge is exposed to the main frame only; embeds have no
  require/process/bridge (e2e/desktop/embed-safety.spec.ts).

Approved BC-02 product decisions that BC-08 must keep:
- sandboxed iframes;
- no top navigation;
- no unrestricted same-origin;
- safe URL validation;
- no weaker Electron security;
- muted-only autoplay;
- fullscreen disabled until BC-08 decides it.

5.1 YOUTUBE
- Public URL forms [ASSUMED from common usage, needs a test table]:
  - www./m./music.youtube.com/watch?v=ID (other query keys ignored);
  - youtu.be/ID;
  - youtube.com/shorts/ID;
  - youtube.com/live/ID;
  - youtube.com/embed/ID and youtube-nocookie.com/embed/ID.
- Official embed URL [DOCS]: https://www.youtube.com/embed/VIDEO_ID.
  The privacy-enhanced host www.youtube-nocookie.com/embed/ID is not
  described on the parameters page [ASSUMED from Google's support
  article; verify].
- Video ID: 11 characters, [A-Za-z0-9_-] [ASSUMED; widely relied on,
  not formally promised].
- Parameters [DOCS]:
  - autoplay 0/1; controls 0/1; start (seconds, keyframe-rounded);
    end; fs 0 (hides the fullscreen button); playsinline 0/1;
  - loop 1, which for a single video REQUIRES playlist=VIDEO_ID;
  - enablejsapi 1 together with origin, for the IFrame API;
  - cc_load_policy, cc_lang_pref, iv_load_policy, disablekb, hl, color.
  - rel=0 no longer disables related videos (it limits them to the
    same channel).
  - modestbranding is deprecated with no effect; showinfo was removed.
  - mute is NOT on the official page. It is widely used and needed for
    muted autoplay [ASSUMED; must be verified live].
- RMF terms [DOCS]:
  - embedding clients MUST send an HTTP Referer; do not use a
    Referrer-Policy that suppresses it;
  - recommended policy: strict-origin-when-cross-origin;
  - desktop and WebView clients must set it manually: an HTTPS URL
    whose domain identifies the app;
  - viewport at least 200x200 (16:9 at least 480x270 recommended);
  - autoplay only once the player is more than half visible, and only
    one autoplaying player per page;
  - no overlays over the player.
- Error 153 ("player configuration error") is the failure reported when
  no usable referrer arrives (community sources; not on the RMF page).
- Privacy: nocookie host [ASSUMED: no cookies before playback;
  tracking still happens after playback starts].
- Muted playback: needs mute=1 [ASSUMED]. Loop: yes, via playlist.
  Fullscreen: needs allow="fullscreen" (F1); fs=0 hides the button.
- Electron: no Referer from app:// (F3). Likely Error 153 until a
  Referer is supplied [ASSUMED].
- Limitations:
  - owners can disable embedding;
  - age-restricted videos do not play embedded [ASSUMED];
  - the official iframe example uses no sandbox. Whether every player
    feature works under Layoutry's sandbox (popups stay sandboxed) is
    [ASSUMED].

5.2 VIMEO
- Public URL forms [ASSUMED]:
  - vimeo.com/ID;
  - vimeo.com/ID/HASH (unlisted);
  - vimeo.com/channels/NAME/ID;
  - vimeo.com/groups/NAME/videos/ID;
  - player.vimeo.com/video/ID?h=HASH.
  Showcase/album URLs are not single videos and are out of scope.
- Official embed URL [DOCS]: https://player.vimeo.com/video/ID?params
- ID: numeric. Unlisted videos need the h= hash. The h= parameter is NOT
  in the official parameter table [ASSUMED from Vimeo's own generated
  embed codes].
- Parameters [DOCS]:
  - free on every video: autoplay, muted, loop, dnt, playsinline,
    autopause, title, byline, portrait, keyboard, #t=1m2s (start time,
    URL fragment);
  - paid plan only (Creator or higher, owned by the VIDEO OWNER):
    controls, background, fullscreen, pip, speed, color and others.
- dnt=1 blocks session data and analytics; "some essential cookies
  will still be active" [DOCS].
- Fullscreen: official examples use allowfullscreen.
- Limitations:
  - owners can restrict embedding to specific domains [ASSUMED]. The
    editor origin, app:// and file:// will then show a privacy error.
  - Referer behavior for app:// and file:// needs live verification.

5.3 DAILYMOTION
- Embed URL [DOCS]:
  - https://geo.dailymotion.com/player/{PLAYER_ID}.html?video={ID};
  - the legacy www.dailymotion.com/embed/video/ID redirects to a
    default player from September 2025.
- Public forms: dailymotion.com/video/xID, dai.ly/xID [ASSUMED].
- Query parameters on the iframe page [DOCS]: video, playlist, and mute
  (in an example). No loop, startTime or autoplay as iframe query
  parameters; player behavior is configured per Player ID in their
  partner dashboard.
- The page states the iframe embed is appropriate only for environments
  that restrict JavaScript (AMP); they recommend their script embeds.
- Referer is REQUIRED [DOCS]: "the player will block video playback"
  without it.
- Recommended allow="autoplay; fullscreen; picture-in-picture;
  web-share" [DOCS].
- Verdict: it works without per-user configuration only through a
  default player, with almost no controllable settings.

5.4 TWITCH
- Embed URLs [DOCS]:
  - player.twitch.tv/?channel=|video=v123|collection=...&parent=DOMAIN
  - clips.twitch.tv/embed?clip=SLUG&parent=DOMAIN
- parent is REQUIRED: one per domain the site uses. Without it there is
  a playback error.
- Size: at least 400x300.
- Parameters: autoplay (live/VOD default TRUE), muted, time (VOD).
- Verdict: an exported site's domain is unknown at export time; the

5.5 WISTIA

- Options [DOCS: names listed on the options page]: autoPlay, muted,

5.6 LOOM

  - share: loom.com/share/{ID};
  - embed: loom.com/embed/{ID};
  - older docs show useloom.com/embed/{ID}.

5.8 PROVIDER SUPPORT RECOMMENDATION
-----------------------------------
Recommended: OPTION A, YouTube + Vimeo.
- Together they cover the overwhelming majority of what beginners paste
  [ASSUMED, market knowledge].
- Both have stable, documented URL parameters for exactly the settings
  in Layoutry's existing media model.
- Two providers keep the security test matrix (hostname spoofing,
  Referer, sandbox compatibility, lifecycle) manageable in all three
  engines plus Electron.

Option B (+ Dailymotion) adds little:
- its iframe embed is officially second-class;
- most settings live in a per-account player ID that Layoutry cannot
  set;
- it requires a Referer, which fails in two of Layoutry's three runtime
  contexts (desktop, local file).

Option C (all six) is not recommended:
- Twitch's parent requirement cannot be satisfied for exports;
- Wistia needs wildcard or custom hosts;
- the support matrix becomes mostly "not supported" cells, which
  invites controls that silently do nothing.

Suggested follow-on: Loom after BC-08, as a one-provider add-on.

The design in section 5.9 makes adding a provider a local change.

- an ID pattern;
- the embed host(s);

- the default title;
- the default aspect ratio.


6. URL PARSING AND NORMALIZATION DESIGN
---------------------------------------
One centralized, pure module, used by the Inspector (validation and
detection), Canvas (placeholder and Preview src), Export (markup and
diagnostics) and the desktop shell (if a host list is needed). None of
them parses URLs on its own.

Proposed: src/lib/videoEmbed/ (name for approval), framework-free:
  parseVideoEmbedUrl(input: string)
      -> { ok: true; provider; videoId; hash?; startSeconds? }
       | { ok: false; reason }
  buildVideoEmbedSrc(ref, settings)
      -> string (the only place an embed URL is ever assembled)
  detectVideoEmbed(src)
      -> the same result for a stored src
       (used by Canvas, Export and the Inspector)

Rules:
1. Parse with the WHATWG URL parser (new URL), never regexes over the
   raw string. Trim whitespace first. Reject on throw.
2. Scheme:
   - accept https:, and http: for well-known public URLs (rebuilt as
     https);
   - refuse everything else: javascript:, data:, file:, blob:, about:,
     ftp:, and custom schemes;
   - protocol-relative input ("//youtu.be/x") is refused, or resolved
     against https: only (a decision; recommend refuse, with the
     message "Paste the full link").
3. Hostname is an EXACT match after the parser's normalization.
   - The parser lowercases and converts Unicode to punycode, so
     lookalike hosts (for example a Cyrillic "о") become xn--... and
     fail the match.
   - No endsWith, includes or startsWith checks.
   - The allowed subdomains are listed explicitly (www., m., music.
     for YouTube).
4. url.username === "" and url.password === "" (refuses
   "https://youtube.com@evil.example/" and
   "https://evil.example@youtube.com/").
5. url.port === "" (refuses https://www.youtube.com:8443/...).
6. Path matched with anchored patterns per provider.
   Example: ^/watch$, ^/shorts/([A-Za-z0-9_-]{11})/?$, ^/embed/(...).
7. The video ID is validated with a strict anchored pattern:
   - YouTube [A-Za-z0-9_-]{11}; Vimeo \d{1,12}; Vimeo hash [0-9a-f]+.
   - The parser has already percent-decoded nothing in the path, so
     "%2F", "%253C" and similar fail the character class. Double
     encoding can therefore never produce a valid ID.
8. The query string is NEVER passed through.
   - Only known keys are read: v, t/start, h, list (ignored).
   - Everything else is dropped: si, utm_*, feature, pp, and any
     payload.
   - The output URL is BUILT from validated parts, never edited from
     the input.
9. No network access in the parser: no redirect following, no oEmbed
   lookup. Short links (youtu.be) are resolved by pattern, not by
   fetching.
   - A pasted URL-shortener link (bit.ly, ...) is refused: "Paste the
     video's own YouTube or Vimeo link."
   - At runtime, a provider's own redirects stay inside the sandbox and
     are already limited by will-frame-navigate on desktop.
10. Existing embed URLs are accepted:
    - youtube.com/embed/ID, youtube-nocookie.com/embed/ID;
    - player.vimeo.com/video/ID?h=...
    Their own parameters are read only where Layoutry supports them.
11. Output is always an https URL on the provider's official embed
    host, and is then also passed through resolveIframeSourcePolicy and
    checkExportUrl as today (defence in depth).

7. DOCUMENT MODEL RECOMMENDATION

9. CANVAS BEHAVIOR RECOMMENDATION
---------------------------------
Recommended for Design: a static, local placeholder for provider
embeds. It shows:
- a provider glyph, using Layoutry's own generic icon (no provider logo
  asset, so no branding);
- the provider name;
- the title;
- a settings summary ("Muted · Autoplay · Loop");

becomes unnecessary for this branch; keep it for uniformity.

Rejected alternatives:

  - third-party tracking from merely opening a project;
  - a playing video during editing;
  - cost with many embeds;

  - a sound-producing player in Design, with no lifecycle to stop it.

- "Load video" button in Design: blurs Design and Preview, and would

Generic (non-provider) Embeds keep today's live Design behavior,

10. PREVIEW BEHAVIOR RECOMMENDATION
-----------------------------------
- On Preview entry the placeholder is replaced by the real iframe:
  - src from buildVideoEmbedSrc;
  - sandbox from resolveIframeSourcePolicy, unchanged;
  - title;
  - referrerpolicy="strict-origin-when-cross-origin";
  - loading="lazy";
  - allow="fullscreen" only if approved.
- Initialization and loading are the provider's own. Layoutry loads no
  provider SDK script (section 18).
- Autoplay: the provider's autoplay and mute parameters are emitted
  only when getEffectiveAutoplay(node) is true, i.e. authored autoplay
  AND muted. Unmuted autoplay is never requested, and authored unmuted
  media is never auto-muted (BC-02.2.1).
- Do not emit allow="autoplay". Chromium allows muted autoplay without
  delegation [ASSUMED for provider players, verify in BC-08.3]. Granting
  delegation would let a provider script start sound.
- If a provider does not start muted autoplay without it, the
  recommendation is to drop autoplay for that provider, not to delegate.
- YouTube RMF also requires at most one autoplaying player per page,
  and only when visible. Layoutry should warn when two YouTube embeds
  are both muted-autoplay (an export/Inspector notice; decision).
- Stopping: see section 11 (teardown).
- Provider errors (embedding disabled, private, Error 153, offline)
  render inside the provider's frame. Layoutry cannot read them across
  origins and should not try. Preview shows whatever the provider
  shows. An offline network gives the browser's own frame error.
- Repeated Preview sessions: each entry mounts a fresh frame, so
  behavior is deterministic and nothing leaks between sessions.
- Escape: while keyboard focus is inside a cross-origin player,
  keydown never reaches the editor [CODE: frame isolation, the same
  reason the shield exists]. So Escape does not exit Preview until
  focus leaves the frame. This is a known, explainable limit, to be
  tested and mentioned in the exit hint.


11. MEDIA LIFECYCLE RECOMMENDATION
----------------------------------
Pausing a native <video> does nothing for a provider iframe (F5). The
two options:

(1) Teardown, RECOMMENDED: the iframe is rendered only while
    isPreview && !hidden.
    - Preview exit: the iframe unmounts and its sound stops at once.
    - Hidden by an interaction (RuntimeHiddenContext): the iframe
      unmounts; when shown again it mounts fresh. Muted autoplay starts
      again, from the start time.
    - Selection change: no effect (Preview has no selection; in Design
      it is a placeholder).
    - Project open/new, editor unmount: editorMode resets, so the
      iframe unmounts.
    - Reduced motion (prefers-reduced-motion: reduce): recommend
      treating it like the unmuted case, i.e. no provider autoplay
      (decision).
      Native video today does NOT do this; BC-02 only covered
      transitions. Changing it would be a policy change for native
      video too, so for parity the recommendation is an embed-only
      rule, or none, as decided.
    - Exported page: the export runtime (exportInteractionRuntime.ts)
      gets a matching rule. Hiding a target clears each provider
      iframe's src (kept in a data attribute) and showing it restores
      the src. This needs no provider API, is the same in all engines,
      and has no editor dependency.
    - Position is NOT preserved. Showing a video again restarts it.
      This is stated in the Inspector help and the report.

(2) Provider postMessage APIs, OPTIONAL later: pause/resume keeping the
    position.
    - YouTube needs enablejsapi=1&origin=... and its command message
      format. The origin parameter is meaningless for app:// and
      file:// [ASSUMED].
    - Vimeo uses {"method":"pause"}.
    - Each is provider-specific, undocumented in parts, and needs
      message listeners on the host page, which BC-02.3 deliberately
      has none of.
    Not recommended for BC-08.

Exact playback-position restoration is feasible only with (2) and is
not promised.


12. FULLSCREEN SECURITY ANALYSIS
--------------------------------
Mechanisms:
- allow="fullscreen" (Permissions Policy):
  - the current standard way to delegate the fullscreen feature to a
    cross-origin frame;
  - its default allowlist is 'self', so cross-origin frames are
    refused without it.
- allowfullscreen (HTML attribute):
  - the legacy equivalent, treated as allow="fullscreen *" for that
    frame.
- Sandbox tokens: there is NO sandbox token for fullscreen.
  Fullscreen is not one of the sandbox restrictions in current engines.
- Provider controls: the player's fullscreen button only calls
  element.requestFullscreen(), which works only if delegated.
  YouTube's fs=0 hides the button.

Live evidence [PROBE]. Setup: a sandboxed cross-origin frame with
Layoutry's exact tokens
  "allow-forms allow-popups allow-scripts allow-same-origin".
Results:

  Context                     no attribute      allow="fullscreen" / allowfullscreen
  --------------------------  ----------------  ------------------------------------
  Chromium (hosted page)      refused           fullscreenEnabled; entered
  Firefox  (hosted page)      refused           fullscreenEnabled; entered
  WebKit   (hosted page)      refused           fullscreenEnabled; entered
  Electron (app://layoutry)   refused           fullscreenEnabled = true, but
                                                requestFullscreen() never settles
                                                (hardenSession denies "fullscreen")

Required recommendation:
1. Feasibility: YES in browsers, with one attribute and no sandbox
   change. Electron: yes, but only with a permission-handler change.
2. Attribute change: add allow="fullscreen" (and no other allow
   features), only on recognized provider embeds:
   - in Preview and Export;
   - not in Design (the placeholder has no iframe);
   - not on generic embeds.
   Whether to also write allowfullscreen is a test question: only if a
   supported engine needs it (all three passed with allow alone in the
   probe).
3. Browser limits:
   - user activation is required;
   - Escape always exits, and browsers show their own "press Esc"
     notice;
   - iOS Safari only fullscreens <video>, so players do it their own
     way [ASSUMED];
   - Escape exits fullscreen first; a second Escape may exit Preview.
     To test.
4. Electron limits:
   - hardenSession must grant "fullscreen" only when ALL of these hold:
     - requesting frame is not the main frame;
     - requesting origin is an exact provider embed origin
       (www.youtube-nocookie.com, www.youtube.com, player.vimeo.com);
     - the web contents is the main window.
     Everything else stays denied.
   - The window then enters HTML fullscreen (enter-html-full-screen).
     Electron shows NO browser exit notice, so the editor should show
     its own hint ("Press Esc to exit fullscreen").
   - Window restore after exit must be tested at the minimum window
     size (DESKTOP lesson).
   - Today's hang (F2) also means an approved web-only fullscreen would
     look broken in the desktop app. So either do both together or
     omit allow= in desktop builds.
5. Security implications, overall LOW for allowlisted providers:
   - fullscreen spoofing/phishing by the embedded page (mitigated:
     only exact provider hosts get it; browsers show an exit notice);
   - no navigation, same-origin or Node.js exposure changes (sandbox,
     CSP and navigation guards are unchanged);
   - the Electron permission grant is the only new privileged surface,
     and it is scoped as above.
6. Tests: see section 19, "Fullscreen, if approved".
7. Recommendation: ENABLE, RESTRICTED.
   - Provider embeds only; Preview and Export.
   - Web browsers first (BC-08.3); Electron only in the dedicated
     desktop checkpoint (BC-08.4).
   - Until that ships, desktop builds omit allow= so nothing hangs.
   - Generic embeds keep fullscreen off.
   - This needs explicit product-owner approval. Nothing is enabled now.


13. PRIVACY ANALYSIS
--------------------
Network behavior:
- Canvas Design, today, generic Embed: loads the remote page when the
  project opens (F6).
- Canvas Design, recommended, provider embed: zero requests.
- Preview: loads the provider. Entering Preview is a deliberate user
  action. For the editor user this is a reasonable "consent" moment.
- Exported website: loads the provider when the page loads. This is
  the site owner's decision, but visitors are third parties.

Recommended baseline:
- YouTube: www.youtube-nocookie.com by default (privacy-enhanced).
  [ASSUMED] It avoids cookies until playback; after playback YouTube
  tracking applies; localStorage and other identifiers may still be
  used. Never claim "no tracking".
- Vimeo: dnt=1 by default. [DOCS] "some essential cookies will still be
  active".
- Referrer:
  - explicit referrerpolicy="strict-origin-when-cross-origin": the
    browser default, and YouTube's documented recommendation;
  - sends only the origin cross-site, never the page path;
  - protects against a site-wide no-referrer meta tag breaking
    YouTube.
- Cookies: unchanged. Third-party cookie rules are the browser's
  (BC-02.3 observed them blocked). The sandbox's allow-same-origin on
  cross-origin frames is what lets the provider use its own storage at
  all.
- No thumbnails in Design (they are third-party requests).
- Consent-before-load on exported pages (a "click to load" facade):
  - recommended as a later, optional per-embed setting, OFF by default;
  - it needs a local poster and the YouTube RMF rules for thumbnails
    (at least 120x70);
  - legal requirements such as GDPR are the site owner's
    responsibility;
  - Layoutry should not claim compliance.

Product decision, item 6.


14. EXPORT INTEGRATION
----------------------
A provider embed exports as (illustrative):

  <iframe sandbox="allow-forms allow-popups allow-scripts allow-same-origin"
          src="https://www.youtube-nocookie.com/embed/ID?mute=1&autoplay=1&playlist=ID&loop=1"
          title="YouTube video"
          referrerpolicy="strict-origin-when-cross-origin"
          loading="lazy"
          [allow="fullscreen"  only if approved]></iframe>

- src comes from buildVideoEmbedSrc, with the same parameters as
  Preview. It still passes through checkExportUrl(…, "frame") and
  resolveIframeSourcePolicy(…, EXPORTED_PAGE_ORIGIN).
- The sandbox is identical to today's. It is never weakened to make a
  player work. If a provider proves unable to work under it, that
  provider is dropped and the sandbox stays.
- The CSS is preserved: the same buildMediaFrame / wrapper styles as
  the Iframe today. Responsive sizing comes from the existing
  aspectRatio + width settings (default in section 22, item 13).
- Title: the accessible name; never empty (fallback "<Provider>
  video").
- Autoplay: only when getEffectiveAutoplay(node) is true.
  - The existing "unmuted-autoplay" warning is reused, so the wording
    is the same as for <video>.
  - An info diagnostic is reported for ignored legacy parameters
    (7.2).
- Lifecycle: the export runtime's hide/show rule for provider iframes
  (section 11). No editor runtime and no provider SDK.
- NEW diagnostic recommended, "provider-needs-hosted-page":
  - Info, for Single file and Separate files exports that contain
    YouTube or Vimeo embeds.
  - Text: "YouTube and Vimeo videos play only when the page is opened
    from a website (http or https). Opened as a local file, the player
    may refuse to play."
  - Basis: F4 [PROBE] (no Referer from file://) and [DOCS] YouTube RMF.
- Both export modes produce the same markup. Nothing is packaged as an
  asset (BC-07.3 packaging is for embedded images only).

Acceptable Canvas, Preview and Export differences:
- Design shows a placeholder.
- Preview and Export show the player with identical src, sandbox,
  allow and referrer attributes.
- Remaining differences: the exported page loads at page load, Preview
  on entry; Preview remounts per session; the host origins differ,
  which matters only for allow-same-origin, which is cross-origin in
  both.


15. ELECTRON SECURITY
---------------------
Audit result: today's protections are intact (15/15 Electron specs,
section 19).
- Webview: blocked (webviewTag: false, will-attach-webview prevented).
- Iframe navigation:
  - subframes are limited to http/https/about:blank;
  - top-level navigation is limited to app://layoutry/.
- Popups: all denied (setWindowOpenHandler). The provider's "Watch on
  YouTube" or logo links will do nothing in the desktop app [CODE].
  That is acceptable; optionally a reviewed, provider-only
  openExternal. Not recommended for BC-08.
- External links: not opened.
- Permissions: all denied, including fullscreen (F2).
- CSP: frame-src http: https: already allows provider frames. No CSP
  change is needed.
- Context isolation, sandbox, nodeIntegration false, preload in the
  main frame only: unchanged; embeds cannot reach Node.js (tested).

New risks from provider iframes:
- None to Node.js or the editor's DOM. They are cross-origin, sandboxed
  and site-isolated, exactly like any embed today.
- Referer (F3): desktop playback likely needs a Referer.
  - [DOCS] YouTube asks desktop clients to set one: an HTTPS URL whose
    domain identifies the app.
  - Mechanism: session.webRequest.onBeforeSendHeaders, adding
    Referer: https://<approved-identity-domain>/ only for requests to
    the exact provider embed hosts, never to other hosts.
  - It changes what Layoutry tells a third party. It needs product
    approval: the identity domain, and whether to do it at all.
  - If it is declined, desktop Preview shows the provider's error for
    YouTube [ASSUMED]. The editor should then show a desktop-specific
    hint.
- Fullscreen: see section 12, item 4.

Do not:
- expose Node.js;
- allow navigation;
- add allow-popups-to-escape-sandbox;
- grant any permission other than scoped fullscreen.


16. SAVE/REOPEN AND UNDO/REDO
-----------------------------
Atomic semantics, the same as the existing Inspector:
- Video URL:
  - InspectorMediaTextField commits on Enter/blur only;
  - the value is parsed first, and an invalid value shows an error and
    issues NO command, so no invalid URL ever reaches history;
  - a valid value commits ONE setElementSrc with the canonical URL;
  - re-committing the same canonical URL is a no-op (the existing
    action-level guard).
- Toggles: one command, one Undo step each. The existing autoplay,
  muted, loop and controls commands are tag-agnostic setters.
- Start time / privacy: one setElementSrc with the rebuilt canonical
  URL.
- Copy/paste and Duplicate: generic node cloning copies all fields. The
  documentSaveLimitGuard is irrelevant here (tiny strings).
- Save/reopen: plain v2 fields, no migration. A file with a provider
  iframe opens in today's build as a generic Embed showing the canonical
  embed URL live, so it degrades gracefully. That is forward
  compatibility at no cost.
- Export: reads the same fields, so it is deterministic.

Test plan (BC-08.2/08.3):
- add embed;
- paste watch URL, check the stored src is canonical;
- paste an invalid URL: no history entry;
- switch the provider;
- toggle each setting;
- resize;
- Undo and Redo for each step;
- copy/paste and Duplicate: independent nodes;
- save, reopen, deep-equal;
- export markup snapshot;
- a legacy-iframe fixture (7.2).

22. REQUIRED PRODUCT DECISIONS
------------------------------
Each item gives: the recommendation, the alternatives, and whether
approval is required. Benefits, risks and compatibility are in the
referenced sections.

1. Initial providers.
   REC: YouTube + Vimeo (Option A).
   ALT: B (+ Dailymotion), C (all). Section 5.8.
   Approval: YES.
2. URL-only versus dropdown plus URL.
   REC: URL-only, with the provider auto-detected and shown as a chip.
   ALT: a dropdown first, which adds a step and can disagree with the
   URL.
   Approval: YES (UX).
3. Existing iframe versus dedicated component.
   REC: the existing iframe tag plus a "Video Embed" toolbar card; no
   schema change.
   ALT: a new tag (format/compatibility cost), extending video (wrong
   semantics). Section 7.
   Approval: YES.
4. Canvas placeholder versus live player.
   REC: a static placeholder in Design; the live player only in
   Preview.
   ALT: live (privacy, sound, overlay issues), thumbnail (third-party
   request). Section 9.
   Approval: YES.
5. Privacy-enhanced defaults.
   REC: ON (YouTube nocookie, Vimeo dnt=1), user-switchable, with
   honest wording.
   ALT: off by default.
   Approval: YES.
6. Consent-before-load.
   REC: not in BC-08; a later optional "Load on click" for exports.
   ALT: build it now (scope), or default it ON (breaks autoplay
   entirely).
   Approval: YES.
7. Supported playback controls.
   REC: Muted, Autoplay, Loop for both; Show controls for YouTube only;
   Start at for both (in src).
   ALT: omit Start at (simpler).
   Approval: YES.
8. Autoplay enforcement.
   REC: provider autoplay only when autoplay && muted
   (getEffectiveAutoplay); never auto-mute; no allow="autoplay"; drop
   autoplay for any provider that can't honor this. Optional: a warning
   for more than one YouTube autoplay per page.
   Approval: the policy is already approved (BC-02.2.1); the extensions
   need confirmation.
9. Loop.
   REC: offered; YouTube is implemented with playlist=ID.
   ALT: none.
   Approval: confirm.
10. Fullscreen permission.
    REC: ENABLE RESTRICTED. allow="fullscreen" on provider embeds only,
    in Preview and Export; browsers in 08.3, Electron in 08.4 with a
    scoped permission. Section 12.
    ALT: defer entirely; or enable for all embeds (not recommended).
    Approval: YES, REQUIRED (security policy change).
11. Preview media cleanup.
    REC: teardown on exit and hide; position not preserved.
    ALT: postMessage APIs (provider-specific).
    Approval: YES.
12. Provider error handling.
    REC: show the provider's own error in-frame; add Layoutry hints for
    the known contexts (desktop Referer, local file).
    ALT: try to detect errors (impossible cross-origin without SDKs).
    Approval: confirm.
13. Responsive aspect ratio.
    REC: 16:9 by default (YouTube, Vimeo), using the existing
    aspectRatio setting with width 100% of its container up to 640 px;
    9:16 suggested when a Shorts URL is pasted.
    ALT: a fixed 400x300 like Embed.
    Approval: YES (UX).
14. Export sandbox policy.
    REC: unchanged sandbox, plus referrerpolicy and loading="lazy" (and
    allow="fullscreen" if item 10 is approved).
    ALT: none weaker.
    Approval: YES for the new attributes.
15. Electron permission behavior.
    REC: keep deny-all, except scoped provider fullscreen (if item 10)
    and a scoped provider-only Referer header, with the identity domain
    to be chosen.
    ALT: no Referer, accepting a documented desktop playback
    limitation.
    Approval: YES, REQUIRED.
16. (Extra) Legacy provider iframes.
    REC: detect them as provider embeds and ignore their stored
    parameters, with a diagnostic. Section 7.2.
    Approval: YES.
17. (Extra) Reduced motion.
    REC: no provider autoplay under prefers-reduced-motion. Native
    video is unchanged unless also decided.
    Approval: YES.
