LAYOUTRY — BC-06.1 NAVBAR BUTTON COUNT SELECTOR INVESTIGATION
================================================================

Checkpoint: BC-06.1 (read-only architecture and UX investigation)
Date:       2026-11-10
Base:       main @ 6e0493d (BC-05.4 committed), working tree clean
Result:     No product code changed. Two temporary probes (one Playwright
            spec, one Vitest file) were written, run and deleted.
            The working tree is clean again (section 23).


1. EXECUTIVE SUMMARY
--------------------

A Layoutry Navbar is not a component with settings. It is an ordinary
tree of document nodes, created once by a factory:

  <nav>  (Flex row, no wrap)
    <a>Home</a> <a>About</a> <a>Services</a> <a>Contact</a>

- The items are real `<a>` links, not buttons. Only "Navbar with CTA"
  ends with a real `<button>`.
- After insertion, nothing marks the nav as a Navbar. This was a
  deliberate choice in Checkpoint 1.15.6.3: no navbar flag and no
  special node type.
- A Navbar is therefore indistinguishable from any other `nav` element
  (a blank Nav, Breadcrumbs, Pagination, Sidebar Navigation, or the nav
  inside Simple Footer).
- There is no count setting today, and no Navbar-specific Inspector
  section.

What users can already do with the existing generic tools (all verified
live):
- Select a link and edit its destination (Inspector > Link >
  Destination).
- Double-click a link to edit its label.
- Add a link (insert, or Duplicate with Ctrl+D).
- Delete a link.
- Reorder links by dragging on the Canvas.

Every one of these is one Undo step. Delete removes interactions that
pointed at the deleted link. Missing today: a discoverable "how many
links" control, and any keyboard way to reorder.

Findings that shape the recommendation:

a) CONFIRMED DEFECT (pre-existing, High): BC06-D1
   - The existing count controls trim items without removing
     interactions that target them:
     - List > Items;
     - Select > Options;
     - Table > Columns / Body Rows, and the Header/Footer row toggles.
   - The project then cannot be saved: "This project couldn't be
     written … An interaction targets element "li3", which does not
     exist."
   - Probe-confirmed for List and Select; the table commands have the
     same code shape.
   - A Navbar count built by copying those commands would inherit this
     defect.

b) A pure number field is the wrong model here.
   - Navbar items are user-authored content: their own labels,
     destinations, styles, ids and interactions.
   - Typing 2 into a field showing 8 would delete six items without
     saying which ones.

c) A Flex row with no wrap has limited room, and there is no responsive
   or mobile menu.
   - On the exported page, short labels already spill out of their link
     boxes and run into each other:
     - at 5 links on a 375 px viewport;
     - at 12 links on 768 px;
     - at 16 links on 1024 px.
   - At 12 links on 375 px the whole page scrolls sideways.
   - The default 4 links are fine everywhere tested.

Recommendation:
- Option C, an item-management list: a "Navigation links" section with
  per-link rows, "Add link", per-row Remove and Move up/down, and the
  count shown in the section.
- Not a free numeric count.
- Rules:
  - New links copy the last link's style (never its id, interactions or
    destination).
  - Removal is always of a link the user chose, through the same safe
    deletion as the Delete key.
  - A hard maximum of 12 links per nav.
  - Helper text from 6 links on, pointing to Wrap.
- Fix BC06-D1 as part of the same work.
- Implement in BC-06.2, and do final QA in BC-06.3.


2. EXISTING NAVBAR ARCHITECTURE
-------------------------------

Data flow: Component Library → Canvas → Inspector → Document State →
Preview → Export.

1. Component Library
   - The Creation Toolbar has Components > Navigation, with six entries
     (creationToolbarCategories.ts:379-385):
     - Basic Navbar;
     - Navbar with CTA;
     - Centered Navbar;
     - Breadcrumbs;
     - Pagination;
     - Sidebar Navigation.
   - Each entry maps to an `elementType`:
     - basicNavbar → createBasicNavbarNode;
     - navbarWithCta → createNavbarWithCtaNode;
     - centeredNavbar → createCenteredNavbarNode.
     The map is FACTORIES_BY_TYPE (elementFactories.ts:932-937).
   - The HTML menu also has a blank "Nav" (createNavNode, which creates
     an empty block nav).

2. Insertion
   - useInsertElement (src/features/editor/hooks/useInsertElement.ts)
     calls createElementNode(type) → resolveDestinationParent → store
     insertElement(parentId, node).
   - The whole subtree is inserted in one write: one history entry, and
     the nav root is selected.
     (Tested in useEditorStore.navigationComponents.test.ts.)

3. Document state
   - The Zustand store useEditorStore, field `document`, a tree of
     EditorElementNode.
   - A Navbar has:
     - `tag: "nav"`;
     - `flowLayout: { display: "flex", flex: { direction: "row",
       wrap: "nowrap", justifyContent: start | space-between | center,
       alignItems: "center", rowGap: 24, columnGap: 24 } }`;
     - `background` #fff, a bottom `border`, and `spacing` padding of
       16/24/16/24;
     - `children`: four `{ tag: "a", text, href: "#", typography:
       { color: "#3f3f46" } }`.

4. Canvas
   - DocumentNodeRenderer → ContainerElement draws the nav, and
     LinkElement (canvas/components/document/elements/LinkElement.tsx)
     draws each item.
   - Every Flex child gets `minWidth: 0` and `minHeight: 0`
     (resolveFlexOrGridChildStyle.ts:63-72), so link boxes stay inside
     the nav. Text that doesn't fit spills out of its own link box
     (section 11).

5. Inspector
   - With a nav selected, the generic sections appear (live): Identity,
     Protection, Interactions, Size, Background, Border, Border Radius,
     Shape, Box Shadow, Visual Effects, Transition, Transform, Display &
     Visibility, Position, Spacing, Content Layout.
   - With a link selected: Identity, Interactions, Size, Flex item,
     Link, Typography, Background, Border, Border Radius, Box Shadow,
     Visual Effects, Transition, Transform, Display & Visibility,
     Position, Spacing.
   - No section knows about "navigation items".

6. Preview
   - The same React renderer runs with editorMode "preview".
   - LinkElement calls preventDefault on every click, in Preview too,
     so links never navigate. The editor URL stays the same (live).
   - Links remain keyboard-focusable, in document order (live).

7. Export
   - buildExportDocument.ts:368 writes
     `<a class="ly-link ly-link-underline ly-node-N" href="…">`, with
     the href checked by exportUrlPolicy ("link" kind; "#" when
     rejected).
   - The nav is a plain `<nav class="…">`.
   - Live export markup of a Basic Navbar:
       <nav class="ly-container-radius ly-node-2">
         <a class="ly-link ly-link-underline ly-node-3" href="#">Home</a>
         … ×4
       </nav>

The two caveats on step 8 (adding an item):
- HTML > Link with a link selected appends a NEW link at the END of
  the nav, not after the selected link. It has the generic Link
  defaults ("Link text", blue, underlined), so it does not match the
  other links (live colour lab(44 29 -86) against rgb(63,63,70)).
- Ctrl+D (Duplicate) inserts a copy right after the selected link with
  identical styling and fresh ids, but also copies its label,
  destination, authored HTML id and interactions.

Classification:
- Missing functionality:
  - no discoverable way to set or see the number of links;
  - no "add a link that matches the others";
  - no keyboard reorder.
- Not bugs: the add/duplicate behaviour above is the designed generic
  behaviour, just not tuned for navbars.
- The real bug found nearby is BC06-D1 (section 20).


4. CURRENT ITEM-COUNT BEHAVIOR
------------------------------

- There is no Navbar count setting, no count field and no limit. The
  number of links is simply `nav.children.length`, whatever the user
  made it.
- A nav may contain anything a container may contain: insertionRules
  CONTAINER_TAGS includes nav, which is not constrained. For example,
  Navbar with CTA has a Button, and Breadcrumbs has Paragraph
  separators.

The editor already has count controls for other structures. They are
the closest precedent:

  Inspector field            Store action / command                 File
  -------------------------  -------------------------------------  -----------------------------
  List > Items               setListItemCount                       documentCommands.ts:523
  Select > Options           setOptionCount                         documentCommands.ts:573
  Table > Columns            setTableColumnCount                    tableCommands.ts
  Table > Body Rows          setTableBodyRowCount                   tableCommands.ts:128
  Table > Header/Footer row  setTableHeaderEnabled / FooterEnabled  tableCommands.ts

How they all behave:
- Free numeric entry (InspectorNumberFieldRow), committed on Enter or
  blur, never live. BC-01.3 deliberately keeps structural counts
  non-live: a live "1" on the way to "12" would really delete rows.
- Rounded and clamped at ≥ 0. No upper bound.
- Growing appends fresh default children.
- Shrinking trims from the end with `slice`, silently.
- One history entry.
- They do NOT call removeInteractionsTargeting. That is BC06-D1.

6. NAVBAR ITEM DATA MODEL
-------------------------

Navbar items are regular document nodes: ordinary children of the
`nav`. They are not configuration data, not a template, and not a
hybrid.

- Order: stored explicitly as the order of the `children` array. Drag,
  insert-after and Duplicate all change that array.
- Ids: `a-xxxxxxxx` from generateNodeId at creation; stable for the
  node's life (edits never change an id). Duplicate, paste and import
  of a copy create fresh ids. Undo and Redo restore the exact earlier
  ids, because history snapshots are whole documents.
- Per item, everything is independent: text, href, typography,
  spacing, background, border, radius, dimensions, flexChild, htmlId,
  className, interactions, initialPreviewVisibility.
- Variable counts: fully supported by the model. Nothing in the
  renderer, Preview, export or persistence assumes four items.
  - The only "4" anywhere is the factory's starter content and its
    tests.
  - The live probe built navs of up to 14 items (Canvas) and 16 items
    (export). Both render and export correctly; only the layout
    capacity limits of section 11 apply.
- Assumptions the count feature must respect:
  - A nav may hold non-link children: the CTA Button, Breadcrumbs'
    "/" Paragraphs, Pagination's Previous/Next Buttons, or anything the
    user dropped in.
  - Nothing tells a Navbar apart from other navs.


7. UX OPTIONS COMPARISON
------------------------

Option A: numeric field "Navigation items"
- Discoverability: good, since it reuses the List/Select/Table
  pattern.
- Validation: same as the existing rows (Enter/blur commit; empty or
  non-numeric reverts; decimals round).
- Accidental deletion: HIGH. 8 → 2 deletes six customized links, and
  the user cannot choose which.
- Keyboard: fine (native number input).
- Existing data: can only append defaults or trim the tail.
- Undo: one step. Recoverable, but only if the user notices.
- It also has to decide what counts as an "item" when a nav holds a
  Button or separators.
- Verdict: rejected as the primary control.

Option B: stepper "Navigation items [−] 4 [+]"
- Safer than A: one item per press, so there are no large silent
  deletions.
- But "−" still removes a link the user did not pick, namely the last
  one. That can be the most customized link, or the one an
  interaction targets.
- Two icon-only buttons need visible or accessible names (this is
  solvable: "Remove last link" / "Add link").
- Verdict: acceptable as a fallback if the product owner wants a pure
  count, with the rules in section 9.

Option C: item-management list
- Shows every link: label and destination, with Select / Move up /
  Move down / Remove per row, plus "Add link".
- Removal is always explicit. The rows double as keyboard reorder,
  which fills the gap from section 3, step 10.
- Same pattern as the Box Shadow layer list users already know
  (InspectorShadowLayerList).
- The count is visible ("4 links") without being a destructive input.
- Inspector size: about 28 px per row; at the cap of 12 rows the list
  stays shorter than the existing Box Shadow lists.
- Verdict: RECOMMENDED.

Option D: count control plus list
- Two controls for one fact. The count would either duplicate "Add
  link", or reintroduce A/B's tail deletion beside an explicit Remove.
- The extra complexity is not justified for a beginner-friendly panel.
- Verdict: rejected. Option C already shows the count.


8. RECOMMENDED CONTROL DESIGN
-----------------------------

A new Inspector section, "Navigation links".

When it appears:
- For a single selected element with tag `nav`, in every case:
  Navbars, Breadcrumbs, Pagination, Sidebar Navigation, the Simple
  Footer nav, and a blank Nav.
- Not for multi-selection, the same rule the List/Table count sections
  follow.
- No Navbar marker is needed (respecting the 1.15.6.3 "no variant
  flag" decision).

What it lists:
- The nav's DIRECT `<a>` children, in document order.
- Other children are not listed and never touched: the CTA Button,
  separators, nested containers.
- Links nested inside a wrapper Container are not direct children; the
  user selects the wrapper's own nav-like structure instead. Limitation
  noted in section 20 (BC06-C2).

Row contents:
- The label text, truncated, as a "Select" button. It selects that
  link, so the existing Link and Typography sections apply.
- The destination as secondary text.
- Move up / Move down buttons.
- A Remove button.
- No inline label or destination editing in the row. The selected
  link's own Link section and Canvas text editing already do that, and
  duplicating those fields would create a second editing path.

Footer:
- An "Add link" button.
- A count line: "4 links".
- Helper text when the count is 6 or more (section 11).

Section placement: directly after "Interactions", in the semantic group
where List/Table/Select already live (InspectorNodeSummary:169-174).


9. ADD / REMOVE ITEM POLICIES
-----------------------------

ADD ("Add link")

Source: the nav's LAST direct `<a>` child is the style template.

Fields the new link keeps from the template:
- typography, spacing, background, border, borderRadius, boxShadow,
  filters, transition, transform, display, className, flexChild,
  gridChild.

Fields the new link does NOT copy:
- id: always new (generateNodeId("a")).
- text: "New link". Distinct and obvious, never a copy of
  "Contact" (two identical labels confuse both users and screen
  readers).
- href: "#" (DEFAULT_LINK_HREF), always a valid destination. Copying
  "/contact" would create two links to the same page by accident.
- htmlId: an authored id must stay unique. A duplicated id makes the
  item unreferenceable (interactionTargets: "Absent when an authored id
  exists but is duplicated").
- interactions: an item's click actions are not cloned.
- initialPreviewVisibility: a new link is never born hidden.
- dimensions and freeLayout: a resize the user made is not faked onto
  the new link.

Other cases:
- No links at all (blank Nav, or all removed): createLinkNode()
  defaults, with text "New link".
- Position: immediately after the last direct link. For Navbar with
  CTA, the new link lands before the CTA Button, keeping the CTA last.
  For Pagination, it lands after "3", before "Next".
- Selection stays on the nav, so the user can press Add repeatedly.
- One press is one history entry.
- At the maximum (12), "Add link" is disabled and its reason is shown
  (section 22).

Pattern-specific note:
- In Breadcrumbs, a new link is added without a "/" separator and
  copies the muted "current page" colour.
- That is honest (it copies what is there), but it does not produce a
  well-formed trail.
- Recommended for BC-06.2: show the section for Breadcrumbs too (it is
  just a nav), and accept that the user may add the separator. Do not
  build breadcrumb-specific logic. A product decision is listed in
  section 24.

REMOVE (per-row "Remove <label>")
- Always removes exactly the chosen link. Never "from the end".
- Must reuse the safe deletion path, the same one deleteSelection uses:
  - removeNodesByIds;
  - collectDeletedIds → removeInteractionsTargeting;
  - one pushHistory.
- So any Show/Hide/Toggle binding that targets the removed link is
  removed with it. A binding ON the removed link disappears with the
  node.
- Selection:
  - The nav stays selected.
  - If the removed link was itself part of the selection (not possible
    from this section, since a single nav is selected), fall back the
    way deleteSelection does.
- Focus moves to the next row's Remove button, or to "Add link" when
  the last row was removed, so keyboard users keep their place.
- No confirmation dialog:
  - removal is explicit, one item at a time, and one Undo step;
  - the Delete key already works this way;
  - a dialog per click would be friction without safety gain.
- Undo restores the link with its id, label, href, styles, its
  position, and any binding that was removed with it, because the
  history entry is one document snapshot.

MOVE (Move up / Move down)
- Moves the link one place among ALL the nav's children, so the CTA
  and separators keep their positions relative to the other children.
- Uses the existing moveElement command with before/after zones: one
  history entry.
- Disabled at the ends.


10. MINIMUM / MAXIMUM RECOMMENDATIONS
-------------------------------------

Minimum: 0 links is allowed.
- The Delete key can already empty a nav.
- An empty nav is valid HTML and valid in the model (createNavNode
  starts empty).
- A "Navbar" with only a CTA, or only a brand area, is a real design.
- Removing the last link therefore stays allowed, and the section then
  shows "No links yet" with "Add link".
- One link is valid.

Maximum: 12 links per nav, enforced only by "Add link". It never
deletes anything.

Justification, measured on the export of the real factory trees with
short labels:

  Links  1440px  1024px  768px   375px          320px
  -----  ------  ------  ------  -------------  --------------
  4      fits    fits    fits    fits           fits
  5      fits    fits    fits    spills         spills
  7      fits    fits    fits    spills         spills
  10     fits    fits    spills  spills         spills, page scrolls
         (CTA variant)
  12     fits    fits    spills  spills, page   page scrolls
                                 scrolls
  16     fits    spills  spills  items escape   items escape
                                 the nav        the nav

("spills" means label text overflows its own link box, so neighbours
run together. Screenshot evidence: "HomeAboutServicesContact" and
"Pricin" under the CTA at 8 links on 375 px.)

- 12 is the largest count that still fits a laptop width (1024 px) in
  both Navbar variants.
- Beyond it, links spill even on desktop layouts, and the Inspector
  list stops being scannable.
- It is a usability cap, not a performance limit: performance is fine
  far beyond it (section 18).
- Navs that already hold more than 12 links (built with Duplicate) are
  shown in full and never trimmed. Only "Add link" is disabled.

Input validation:
- The recommended design has no free numeric input, so negative,
  empty, decimal, very large and non-numeric values cannot be entered
  at all.
- If the product owner chooses Option B or A instead:
  - negative → 0;
  - decimals round;
  - empty or non-numeric reverts on Enter/blur, as
    InspectorNumberFieldRow already does;
  - values above 12 clamp to 12;
  - a decrease removes only links that are unmodified starter links;
    otherwise it is refused with a message.


11. RESPONSIVE BEHAVIOR FINDINGS
--------------------------------

What exists:
- Flex row, `flex-wrap: nowrap`, gap 24, Flex children `min-width: 0`.
- No breakpoints, no media-query authoring, no mobile/hamburger menu.
  The "Mobile Navbar" was deferred in 1.15.6.3, and "Responsive
  Breakpoints" is a disabled menu item.
- No item hiding, no horizontal scrolling container.

Behavior as the width shrinks, measured live:
1. Links shrink first. Their boxes stay inside the nav thanks to
   `min-width: 0`.
2. Multi-word labels wrap inside their link (on the Canvas, "Link
   text" became two lines).
3. Single words cannot wrap, so the text overflows its link box and
   overlaps neighbours (see the table in section 10).
4. At extreme counts, link boxes reach 0 px and escape the nav
   padding, and the page scrolls horizontally.

Narrow Canvas widths:
- The Canvas page sheet follows the editor's panel widths (920 px in a
  1600 px window). The same mechanics apply.
- With 14 links, five labels spilled on the Canvas.

This conflicts with Layoutry's own standing rule that content must
never escape its container. The cause is the Flex-row-without-wrap
layout in general, not the count feature: a user can reach it today
with Duplicate. Hence BC06-R1 is classed as a pre-existing constraint,
and the count design adds guardrails, not a layout rewrite:
- the cap of 12;
- helper text from 6 links (the first count that spills on phones):
  "Links may not fit on small screens. Turn on Wrap in Content Layout
  to let them flow onto more lines."

Making a mobile menu is explicitly out of BC-06 scope.


12. NAVIGATION SEMANTICS
------------------------

- The Navbar renders a `<nav>` landmark containing `<a href>` links.
  This is correct for navigation to destinations.
- Navbar with CTA's "Get Started" is a `<button>`.
  - Acceptable for an action.
  - If it really navigates to a sign-up page, a Link styled as a
    button would be more correct. Not changed here; noted as BC06-U3.
- Pagination already follows the link-vs-button rule: page numbers are
  Links; Previous/Next are Buttons (navigationCompositions.ts
  comments).
- No list markup (`<ul><li><a>`).
  - This cannot be built: `li` is a text leaf in this app
    (insertionRules), so `nav > ul > li > a` is not representable.
  - A flat `nav > a` is acceptable to assistive technology. Only the
    "list, N items" announcement is lost.
- The `nav` has no accessible name (no aria-label).
  - With several navs on one page (Navbar plus footer nav plus
    breadcrumbs), screen-reader users hear several unnamed
    "navigation" landmarks.
  - This needs a generic attribute system that does not exist yet.
    Noted as BC06-U2, not proposed for BC-06.
- The count feature must keep adding `<a>` elements, never buttons.


13. STYLING AND INTERACTION PRESERVATION
----------------------------------------

Styling
- All Navbar styling is ordinary per-node fields. There is no shared
  "navbar link style" object.
  - The four starter links each carry their own copy of
    `typography: { color: "#3f3f46" }`.
  - Layout comes from the nav: Flex direction, Justify, Gap, Align.
- So:
  - "New links inherit styling" means copying the last link's style
    fields (section 9).
  - Changing the count never touches the nav's own CSS or any
    surviving link.
- Per-item customizations are preserved: add only inserts, remove only
  removes the chosen node, move only reorders.
- Hover, focus and active states do not exist in the style model.
  Exported links use the browser's default focus ring. There is no
  "active page" field; an active link is shown through authored colour,
  as in Pagination. Nothing in the count design depends on states.
- Gap, Alignment and Justify live on the nav and apply to new links
  automatically.

Interactions (BC-04 rules preserved)
- Removal uses removeInteractionsTargeting in the same document write,
  as Delete and Cut do. No dangling target is possible, and the
  document stays saveable.
- Add never copies interactions or htmlId, so it creates no duplicate
  triggers and no unresolvable ids.
- Move changes order only. Interaction targets are by node id, so
  bindings survive reordering. The generated `ly-target-N` DOM ids
  re-number in document order in both Preview and Export, which share
  resolveInteractionTargets, so they still agree.
- A link that is itself a trigger keeps its bindings when moved.


14. UNDO/REDO DESIGN
--------------------

Each action is one store action with one pushHistory, the pattern
every one-shot command already uses:
- add one link → one entry;
- remove one link, plus its cleaned bindings → one entry;
- move one place → one entry.

"Increase by three" is three presses, so three entries. That is the
correct granularity for an explicit list: each Undo step reverses one
visible action.

If the product owner chooses a count control (A/B), a +3 or −2 change
must be one action call → one entry, as setListItemCount already is.

What each action guarantees:
- Undo restores the removed link with its exact id, label, href,
  styles, position and removed bindings (whole-document snapshot).
- Redo re-applies it.
- No-op guard: an action that changes nothing (Move up on the first
  row; Add at the cap) returns the same document and pushes no
  history, the action-level guard setListItemCount uses.
- No live mode and no transactions: these are discrete clicks, not
  drafts. BC-01's live-edit transactions are for continuous CSS edits
  and are not involved.
- If a Canvas text edit is open on a link when a row button is
  pressed, the existing commit-on-blur of useEditableText runs first
  (same as clicking any Inspector control today). The BC-06.2 tests
  should include this ordering.
- Selection after Undo: deleteSelection's fallback rules already avoid
  stale ids. For the nav-section actions the selection is the nav,
  which is never removed by them.

17. ACCESSIBILITY REVIEW
------------------------

The recommended section:
- Every control is a real `<button>` with a visible or accessible text
  name. No icon-only control is left unnamed (names in section 22).
  This follows the InspectorShadowLayerList precedent (aria-label
  "Move <name> up", etc.).

  moved row's button, or goes to the next row (section 9).

    count.
  - The removed item is not announced separately (avoids double

  `disabled` button is skipped by Tab and its reason is never read.
- Touch targets: Inspector rows follow the existing 24 px control
  height (size-6), consistent with every other Inspector button.
  (Layoutry's Inspector is desktop-pointer software.)
- Generated output:
  - links keep accessible names from their text;
  - "New link" is a deliberately visible placeholder, not an empty
    label;
  - the unnamed-nav concern is BC06-U2.

Responsive menu accessibility: not applicable, since no responsive
menu exists.

20. RISK REGISTER
-----------------

BC06-D1  CONFIRMED DEFECT (pre-existing) — Severity: HIGH
- What: structural count decreases leave interactions targeting removed
  children, so the project cannot be saved.
- Reproduction:
  1. Insert an Unordered List (3 items) and a Button.
  2. Button > Interactions > Add: Toggle, target the list's third
     item.
  3. Select the list and set Items = 2 (Enter).
  4. Save (Ctrl+S). The dialog says "This project couldn't be
     written" and nothing is saved. Autosave and recovery snapshots
     fail the same check.
  Same with Select > Options, and by code inspection with Table >
  Columns / Body Rows and the Header/Footer row toggles.
- Root cause: setListItemCount, setOptionCount, setTableColumnCount,
  setTableBodyRowCount and setTableHeader/FooterEnabled remove children
  (slice, or a subtree drop) without removeInteractionsTargeting. Only
  Delete and Cut call it; Paste calls
  removeInteractionsWithMissingTargets.
- User escape today: Undo, or remove the broken binding in the
  trigger's Interactions section.
- Affected: useEditorStore.ts:1345-1400, documentCommands.ts:523/573,
  tableCommands.ts.
- Mitigation: in each store action, compute the ids removed by the
  command (the before/after child difference) and apply
  removeInteractionsTargeting in the same write before pushHistory.
  The Navbar remove action uses the same helper from day one.
- Regression coverage:
  - per command, a unit test: a targeted child is trimmed → no binding
    left, serializeProject succeeds, one history entry, and Undo
    restores node and binding;
  - one e2e: list trim, then Save, succeeds.

BC06-R1  ARCHITECTURAL CONSTRAINT (pre-existing) — Severity: MEDIUM
- What: label text overflows link boxes when a no-wrap Flex nav has
  more links than fit. At extreme counts the page scrolls sideways.
- Reproduction: export a Basic Navbar with 5+ links and view it at
  375 px; or Duplicate a link until there are 14 on the Canvas.
- Root cause: Flex row `nowrap`, and Flex children `min-width: 0`
  (boxes contained, text not). No responsive or mobile-menu system.
- Affected: navigationCompositions.ts (nowrap starter),
  resolveFlexOrGridChildStyle.ts.
- Mitigation for BC-06: the cap of 12, plus helper text from 6 links
  pointing to Wrap. A real fix (wrap by default for new Navbars, or a
  mobile menu) is a separate product decision, outside BC-06.
- Regression coverage: in BC-06.3, a measured export at 1024/768/375
  for 4 and 12 links, recording the spill counts (documenting, not
  asserting a fix).

BC06-M1  MISSING FUNCTIONALITY — Severity: MEDIUM (the BC-06 request
itself)
- What: no discoverable way to see or change how many links a nav has,
  or to add a link that matches the others.
- Mitigation: the "Navigation links" section (sections 8-9).
- Coverage: unit tests for the commands and the section; e2e for
  Add/Remove/Move/Undo plus Save.

BC06-U1  UX / ACCESSIBILITY GAP — Severity: MEDIUM
- What: reordering is pointer-drag on the Canvas only. There is no
  keyboard reorder anywhere (Structure arrow keys move focus only).
- Mitigation for links: Move up/down in the new section. A general
  keyboard reorder for all elements is out of scope.
- Coverage: keyboard-only e2e (Tab to "Move About down", Enter, order
  changes, one Undo step).

BC06-U2  ACCESSIBILITY (generated output) — Severity: LOW
- What: `nav` landmarks have no accessible name, so pages with several
  navs are ambiguous for screen readers.
- Root cause: no generic attribute (aria-label) system.
- Mitigation: deferred to a future attributes/accessibility checkpoint.
  Not BC-06.

BC06-U3  UX — Severity: LOW
- What: "Add link" via HTML > Link appends at the end with generic blue
  styling. Duplicate copies label, destination, authored id and
  interactions. Neither is ideal for navbars.
- Mitigation: "Add link" in the new section, with the copy rules of
  section 9. The generic HTML > Link and Duplicate stay unchanged.
- Related: Duplicate copying an authored htmlId produces duplicate DOM
  ids. It is handled safely (the id is dropped from target resolution)
  but is surprising. Noted for a future Identity checkpoint.

BC06-C2  ARCHITECTURAL CONSTRAINT — Severity: LOW
- What: Navbars are not identifiable after insertion, and the section
  sees only direct `<a>` children. Links wrapped in a Container inside
  the nav are not listed.
- Mitigation: documented behaviour. The user selects the wrapper. No
  Navbar marker field, per the 1.15.6.3 decision.

BC06-C3  DOCUMENTATION DRIFT — Severity: TRIVIAL
- What: the navigationCompositions.ts header describes two link
  limitations that were fixed later.
- Mitigation: update the comment when BC-06.2 touches the file.
