LAYOUTRY — BC-07.3: EXPORT IMAGE ASSETS & PORTABLE WEBSITE PACKAGING
=====================================================================
Date: 2026-11-11
Type: Export engine implementation + asset packaging + compatibility + regression tests
Base commit: 6c55f28 (BC-07.2). Nothing committed.
Author: Claude (implementation engineer), for ChatGPT QA review


1. EXECUTIVE SUMMARY
--------------------
An export with "Separate files" is now a portable website:
- index.html, styles.css, script.js (when needed), and assets/ with every
  uploaded image as its own file.
- Files are named assets/image-001.png, image-002.jpg… by the engine, and
  identical images are written once.
- HTML and CSS reference these files by relative path.

How users get it:
- Browser: "Download website (.zip)", one ZIP.
- Desktop: "Save to Folder…" writes the assets folder next to the files,
  with the existing staged, confirm-before-replace, roll-back-on-failure
  write.
- The exported site works from disk, offline, without Layoutry, the
  project file or the original images. This was verified in Chromium,
  Firefox and WebKit, and from a desktop export opened in a separate
  browser.

What did not change:
- The project format (still 2) and the stored data URLs.
- The Inspector.
- The Single HTML file export: it stays one complete file with images
  embedded, and now says so.
- Pages without uploaded images export byte-for-byte as before in both
  modes.
- Remote and relative URLs are left exactly as authored.

Safety:
- Every embedded image is re-validated at export time as untrusted data:
  strict base64, a size bound, then the same byte signature, structure and
  completeness check uploads use.
- An invalid one is never dropped and never turned into a broken file
  reference. It stays embedded, as the Canvas shows it, with a warning.
- Export is read-only: no history entry, no unsaved-state change, no
  selection change. This is tested.

Validation:
- typecheck (web and desktop) and ESLint are clean;
- Vitest: 5689 passed, 1 skipped (+67 tests);
- Chromium full suite: 251/251;
- Firefox and WebKit targeted runs: 32/32;
- Electron full suite: 78 passed, 2 skipped, 1 load-only flake that passes
  6/6 alone;
- production and desktop builds succeed.

New dependency: fflate 0.8.3 (MIT, no dependencies) for the browser ZIP.

Recommendation: ready for QA review.


2. EXISTING EXPORT ARCHITECTURE FINDINGS (audit before coding)
--------------------------------------------------------------
1. Formats that exist: HTML + CSS only, in two modes.
   - "standalone": one index.html with CSS inline, and the interaction
     runtime inline when needed.
   - "separate": index.html + styles.css, plus script.js when needed.
   - There is no Tailwind, React, Vue or ZIP export.
2. Browser: one download per file ("Download all files" started N
   downloads). There was no package.
3. Electron: a single-file Save dialog, or a folder picker that writes the
   three fixed names (desktop/export/exportFileService.ts).
   - The write is token-based, staged into temporary files, renamed with
     rollback, then read back and verified.
   - Text only: the IPC accepted exactly index.html, styles.css and
     script.js as strings.
4. No ZIP library was installed.
5. Generation:
   - buildExportDocument builds the IR, validating URLs through
     checkExportUrl in checkedUrl;
   - printExportHtml and printExportStylesheet print it;
   - exportHtmlCss assembles the files. It is pure and deterministic.
6. The Export dialog has the format "HTML + CSS" and an Output radio group
   (Single HTML file / Separate files).
7. Generation is shared: the same exportHtmlCss runs in the browser and in
   Electron, and only delivery differs.
8. Resources were already in the IR as ExportAsset
   {nodeId, property, url, kind: remote|relative|data}, used for the
   dialog's "loads N files from the internet" note.

Decision: extend at the existing seams:
- packaging in the IR (checkedUrl);
- binary files as a new `assetFiles` field beside the text `files`, which
  leaves every text-file consumer untouched;
- ZIP at the browser delivery step;
- assets in the existing desktop write.

4. ASSET EXTRACTION DESIGN
--------------------------
- buildExportDocument(document, limits, { packageImages }) creates one
  createEmbeddedImagePackager() per export run
  (src/features/export/utils/packageEmbeddedImages.ts).
- exportHtmlCss sets packageImages only for "separate".
- In checkedUrl, an image-context source (<img src>, <video poster>, CSS
  background-image) that the URL policy accepted as `data` goes through
  the packager first:
  - "packaged": the IR receives the relative path; ExportAsset
    {kind: "packaged", url: path}; an info diagnostic is added if the
    declared type disagreed with the bytes.
  - "rejected": stays the data URL (exactly as before), plus a warning.
  - "not-packageable" (SVG, AVIF, BMP, non-base64): unchanged, with no
    diagnostic.
- The packager returns ExportAssetFile {path, bytes, mediaType,
  references}. exportHtmlCss exposes them as `assetFiles`, empty for
  standalone and for refused exports.
- The authored document is never mutated (tested on a deep-frozen
  document). There is no store access, no history and no dirty flag:
  export is a pure function of the document.
- Remote images are never downloaded.


5. SUPPORTED FORMATS
--------------------
- Packaged: PNG, JPEG, GIF and WebP. Extensions .png, .jpg, .gif, .webp.
- Declared types accepted for packaging: image/png, image/jpeg, image/gif,
  image/webp, plus the aliases image/jpg, image/pjpeg and image/apng.
- Not packaged (left as before): SVG, both URL-encoded and base64 (the
  default Image placeholder is an SVG data URL), AVIF, BMP, ICO, and any
  non-base64 data URL. Remote SVG URLs are unchanged.
- Upload formats are not expanded.


6. DATA URL VALIDATION (export time, untrusted)
-----------------------------------------------
1. A header `data:<type>[;params];base64`, case-insensitive, with a type
   from the allow-list above.
2. Payload length ≤ the base64 of 16 MiB (a project can't hold more
   than 12 MiB anyway), checked before decoding.
3. Strict base64: alphabet [A-Za-z0-9+/] only, ≤ 2 "=" padding, length a
   multiple of 4. Whitespace is refused.
4. Decoding (atob) happens once per distinct URL.
5. sniffRasterImage(bytes), moved to src/lib and shared with BC-07.2
   uploads:
   - signature;
   - header structure;
   - completeness (PNG IDAT before IEND, JPEG end marker after the scan,
     GIF trailer, WebP RIFF size).
   It decides format, extension and media type.
6. A declared/actual mismatch (e.g. data:image/png holding a JPEG) is
   packaged by its real type as .jpg, with the info diagnostic
   "embedded-image-type-mismatch".
7. Any failure in 1–5 for an eligible type is "rejected": the source stays
   embedded, with the warning "embedded-image-not-packaged": "…could not
   be exported as a file because <reason>. It was left embedded in the
   page, as the Canvas shows it."

Policy rationale: the documented safe fallback. It keeps the export
faithful to the Canvas (which shows the same data URL), never omits an
image, and never writes a misleading file.

Tested cases:
- HTML, text or SVG declared as PNG/JPEG;
- cut-off PNG and GIF;
- invalid characters, bad length and whitespace in the base64;
- an oversized payload;
- the mismatch case.


7. ASSET NAMING
---------------
- `assets/image-NNN.<ext>`: three or more digits, numbered by the export
  in the order it meets each distinct image (document order, CSS
  backgrounds in node order).
- Never derived from user data: no file names, ids or alt text. So there
  is no traversal, no absolute path, no separator and no unsafe character.
- No collisions: the numbers are unique, and the text files' fixed names
  are at the root.
- Stable: the same document and mode always give the same names and
  bytes. Tested in unit tests and as a byte-identical repeat ZIP in the
  browser.
- Defence in depth:
  - the ZIP builder accepts only `index.html|styles.css|script.js|
    assets/image-\d{3,6}.(png|jpg|gif|webp)`;
  - the desktop main process accepts only that asset pattern, plus a
    signature check.


8. DEDUPLICATION
----------------
- The key is the exact decoded bytes (the binary string), so identical
  bytes are one file however the URL is spelled. Tested: different case,
  parameters, the same bytes from an img and a background or poster.
- Different bytes are always different files (tested with a 1-byte
  difference).
- A per-URL cache means an exact repeated string is decoded once and only
  counted (`references`).
- Both maps live in the per-run packager. There is no global cache, and
  the result is deterministic.
- Savings measured (section 19): 22 references to 2 images give 2 files
  (9.24 MB package) instead of 135 MB of inline base64.


9. HTML REWRITING
-----------------
- Structured, not string replacement: the packaged path replaces the URL
  inside the IR before printing.
  - <img>/<video poster> attributes go through escapeHtmlAttribute.
  - CSS url() values go through escapeCssString (`url("assets/…")`, which
    resolves from styles.css at the root).
  - Paths contain no characters needing escapes, so there is no double
    escaping.
- Everything else prints exactly as before. Tested:
  - id and class kept (`<img id="hero" class="ly-node-2-media hero wide"
    src="assets/image-001.png" alt="Hero &quot;photo&quot; &amp;
    &lt;logo&gt;">`);
  - alt kept;
  - opacity/filters, object-fit and other styles kept;
  - interactions kept (script.js; the toggle works on the extracted site);
  - document order kept.
- Remote, relative and SVG placeholder sources are byte-identical.


10. BROWSER ZIP PACKAGING
-------------------------
- zipExportPackage(files, assetFiles), in
  src/features/export/utils/zipExportPackage.ts, using fflate.zipSync:
  - text is UTF-8 encoded and deflated (level 6);
  - images are stored (level 0): already compressed, never recompressed,
    copied once;
  - fixed timestamps (2000-01-01 local), so the same files give the same
    bytes;
  - path allow-list, no duplicates, index.html required.
- Errors raise ExportPackageError, which becomes "Layoutry couldn't build
  the website package. Nothing was downloaded."
- Download: src/lib/downloadBlob.ts, extracted from downloadTextFile,
  which now delegates to it with the same behaviour.
  - The Blob type is application/zip. The name is "<project name>.zip",
    sanitized (Windows/macOS/Linux-unsafe characters replaced, trimmed,
    at most 100 characters, "website.zip" fallback).
  - Message: "Download of My Site.zip started. Unzip it and open
    index.html; keep the assets folder next to it."
  - A browser refusal becomes "The browser refused the download. Nothing
    was downloaded." (role=alert).
- The ZIP is built from the snapshot on screen; a stale preview still
  blocks it, as for every transfer.
- Why fflate:
  - the brief prefers an established, maintained library;
  - it is about 8 KB gzip in the client bundle, MIT, no transitive
    dependencies;
  - npm audit doesn't flag it (all audit findings are pre-existing:
    next, zod, postcss and others);
  - the alternative was a hand-written ZIP writer.


11. ELECTRON EXPORT PACKAGING
-----------------------------
- Destination policy: unchanged. Separate files uses the folder picker,
  and the website is written into that folder, with assets/ inside it. No
  ZIP on desktop: the least disruptive choice, since a folder is what the
  existing flow produces.
- The IPC surface is unchanged: the same two channels, with payload keys
  still exactly {token, files, overwrite}. Images travel in `files` as
  {path, bytes}:
  - preload copyExportFiles copies the bytes into a fresh Uint8Array and
    passes nothing else;
  - the renderer bridge sends {path, bytes} for assets and {path, content}
    for text.
- Main-process validation (expectFiles):
  - names must match `assets/image-\d{3,6}.(png|jpg|gif|webp)`;
  - bytes must be a Uint8Array, 1 B–16 MiB each, at most 64 MiB and 4,096
    images in total;
  - the file signature must match the extension (PNG, JPEG FFD8FF,
    GIF87a/89a, RIFF…WEBP);
  - no duplicates, exactly {path, bytes} keys;
  - images are refused for a single-file destination;
  - a text file sent as an image, or an image sent as text, is refused.
- Target paths are joined inside `<folder>/assets` and re-checked to stay
  there.


12. DESTINATION AND OVERWRITE SAFETY
------------------------------------
- `assets` must be missing (it is then created with a non-recursive mkdir)
  or a real folder.
  - A junction or symbolic link is refused before anything is read or
    written through it (tested with a real junction: nothing appears in
    its target).
  - A file named `assets` is refused ("…is a file, so the exported images
    can't go in an assets folder there…"); nothing is written.
- Existing assets/image-NNN files join the existing conflict question
  ("assets/image-001.png, assets/image-002.jpg, styles.css, index.html
  already exist in “Site”. Replace them?").
  - Keep existing files writes nothing; Replace writes them.
- Other files in the folder or in assets/ are never touched (tested: notes.txt,
  assets/logo.svg).
  - Consequence: images left over from an older export with more images
    remain in assets/. They are unused and harmless, and not deleted by
    design, since Layoutry never deletes files it didn't write in this
    export.


13. FAILURE RECOVERY
--------------------
Order:
1. Validate the payload.
2. Check the folder and the assets folder.
3. Read the targets (conflict check).
4. Create assets/ if missing.
5. Stage every file to a temporary next to its target and flush it.
6. Rename images first, then styles.css, script.js, and index.html last.
7. Read back every file and compare SHA-256 hashes.

Failures:
- While staging (disk full, permissions): the temporaries are removed,
  and an assets folder this export created is removed (rmdir, only if
  empty). Nothing visible changed. Tested with an injected ENOSPC: the
  folder is empty afterwards.
- While renaming: the replaced files are put back (earlier bytes restored,
  new files removed only if still exactly what was written) and the
  created assets folder is removed if empty. The message says what
  happened. Tested with EACCES on index.html: styles.css is restored, no
  assets folder is left.
- Success is reported only after the read-back verification of every
  file.
- A cancelled dialog gives "Save cancelled. Nothing was saved." (tested in
  Electron).
- Limit (as before): Windows has no atomic multi-file or directory
  replace. The staged rename with rollback is the documented strategy.

20. SECURITY REVIEW
-------------------
- Embedded data is untrusted at export:
  - strict parsing;
  - the size bound comes before decoding;
  - the bytes decide the type;
  - incomplete or forged images are not packaged.
- No user-controlled names anywhere in the package. Allow-listed paths
  are enforced in the ZIP builder and in the main process.
- Electron:
  - no new channels and no path from the renderer;
  - asset bytes are validated (name, size, signature);
  - writes stay inside <folder>/assets;
  - links and files at assets are refused;
  - staged writes with rollback; other files are never touched.
  - Sandbox, context isolation, CSP and fuses are unchanged.
- Exported files are written, never opened or executed. SVG is never
  packaged.
- New dependency: fflate, zero transitive dependencies, used in the
  renderer only.
